# Output Color Space

`img2sixel -U` selects the RGB representation of the palette written to a SIXEL stream. Palette export with `-M` has its own sRGB interchange boundary. For normal terminal display, leave `-U` at its default, `gamma`. Use another output space only when the consumer's interpretation of those numbers is known. Ordinary SIXEL defines no color space for its register values; treating them as sRGB by default is libsixel's [interpretation](../../sixel-format/specification-layers.md#interpretation-1-register-rgb-values-default-to-srgb), not part of the format.

```text
-U COLORSPACE
--output-colorspace=COLORSPACE
```

| Value | Output representation | Intended use |
| --- | --- | --- |
| `gamma` | Gamma-encoded sRGB channels. | Default output for consumers expecting ordinary RGB code values. |
| `linear` | Linear-light RGB with the sRGB primary basis. | A consumer explicitly configured to interpret linear-light channel values. |
| `smpte-c` | libsixel's SMPTE-C primary conversion and gamma encoding. | A consumer expecting that specific RGB representation. |
| `display-p3` | Standard Display P3 primaries, D65 white and sRGB transfer encoding. | The [limited CPU float path](#display-p3-selected-cpu-float-path) and a receiver explicitly configured for P3 input. |
| `auto[:timeout_ms=N]` | CLI negotiation resolves to gamma sRGB or standard Display P3. | Only images sent directly to stdout as a TTY; other destinations retain gamma sRGB. |

The parser also accepts `smptec` as an alias for `smpte-c`, folds letter case, and uses the shared [choice prefix-matching policy](../../cli/prefix-matching.md). Full names are preferable in durable commands. A repeated `-U` replaces the earlier value. `oklab`, `cielab`, and `din99d` are working/clustering choices, not accepted output choices. `-U` takes a required name, not a numeric gamma exponent or an ICC profile path.

`-U` and `-_` are not generally mutually exclusive. The selected Display P3 path rejects active snap, including when CLI negotiation selects P3; gamma, linear and SMPTE-C remain compatible with snap. The [snap/output boundary](../palette-construction/snap-policy/README.md#output-conversion-and-the-display-p3-boundary) explains why an earlier sRGB snap does not establish a P3 grid guarantee.

## Where the conversion happens

For the legacy `gamma`, `linear` and `smpte-c` palette paths, the relevant data flow is:

```text
Loaded image with a known color interpretation
    |
    +--> Palette construction in -X --> Palette in -W
    |                                       |
    +--> Image pixels in -W -----------------+
                                            |
                                  Lookup and dithering
                                            |
                               Pixel indices + working palette
                                            |
                               Convert a palette copy to -U
                                            |
                               Optional exact-snap finalization
                                            |
                         SIXEL color definitions
```

`-X` controls the geometry used to construct a palette. `-W` controls the geometry used to choose a palette index and propagate dither error. In these legacy paths, `-U` converts the resulting palette for output; it does not rerun either operation. Changing only `-U` can therefore change the displayed colors while retaining the index assignments for a static image. The selected native float paths cache a separate serialized palette before lookup without changing its working coordinates, as described below.

Unlike the implicit coupling from an explicit `-W` to an unspecified `-X`, `-U` does not change either earlier choice. For example:

```sh
img2sixel -Xgamma -Woklab -Ugamma image.png
```

This builds the palette in gamma coordinates, applies it in Oklab, and writes gamma RGB output. Keeping `-Ugamma` does not cancel the effect of `-Woklab`. Conversely, `-Ulinear` alone does not make lookup, dithering, resize, or alpha compositing operate in linear light. Those stages have their own controls; see [Working color space](../palette-application/working-colorspace/README.md), [Crop and resize](../preprocessing/crop-resize/README.md), and [Alpha policy](../../loader/alpha-policy/README.md).

## Legacy representations

### `gamma`: sRGB encoding

The name `gamma` denotes libsixel's sRGB transfer curve, including its linear segment near black. It is not simply a power of `1/2.2`. For a normalized linear-light channel `l` in `[0, 1]`, the corresponding sRGB channel `g` is:

```text
g = 12.92 * l                       when l <= 0.0031308
g = 1.055 * l^(1 / 2.4) - 0.055    otherwise
```

The inverse is:

```text
l = g / 12.92                      when g <= 0.04045
l = ((g + 0.055) / 1.055)^2.4      otherwise
```

The [W3C sRGB definition](https://www.w3.org/TR/css-color-4/#predefined-sRGB) describes the primary basis, D65 white point, and transfer function. libsixel's conversion implementation is in [`src/colorspace.c`](../../../src/colorspace.c), with typed float paths and byte lookup-table paths.

### `linear`: linear-light sRGB

`linear` uses the same RGB basis without the sRGB transfer encoding. A gamma channel near `0.5` corresponds to only about `0.214` in linear light. Thus an output palette can change from roughly `50%` to `21%` without intending to change the physical color: the recipient must apply the matching interpretation.

If a receiver instead treats that linear `21%` as an ordinary sRGB code value, the result is much darker. This follows from applying the sRGB decoding curve to a number that was already linear. It is an interpretation mismatch, not evidence that the encoder chose a worse palette.

### `smpte-c`: primary conversion and a power curve

Output conversion first converts the working color to linear sRGB and applies the fixed `sixel_linear_srgb_to_smptec_matrix` in [`src/colorspace.c`](../../../src/colorspace.c), followed by a power `1/2.2` encoding. Typed float conversion preserves signed extended values through the matrix and transfer function; byte conversion remains bounded by its storage representation. The selected output path clamps only the wire copy immediately before RGB101 rounding. The inverse uses the power `2.2` and the inverse primary-conversion matrix. See [color-space handling](../colorspace-handling/README.md) for the shared float arithmetic contract.

Consequently, `-Usmpte-c` can change channel balance as well as tone response. It is not an alternative spelling for `gamma`, a generic CRT correction, an HDR mode, or a destination ICC transform. The fixed matrix and curve describe libsixel's implementation; this option does not measure or calibrate a monitor, or establish that a particular DEC terminal expects these values.

## `display-p3`: selected CPU float path

The selected P3 path supports static and animated RGB input, including the separated masks and packed alpha normalization described below, automatic or explicit float precision, independent clustering and working coordinates chosen from gamma, linear, Oklab, CIELAB and DIN99d, CPU K-means, K-center, K-medoids or Heckbert (including the existing `auto` resolver) with any sampling policy and the solver-specific binning choices below, `none`, `certlut`, `5bit`, `6bit`, `auto`, `vptree`, `rbc`, `mahalanobis`, `eytzinger` or `fhedt` lookup, and no dithering or CPU spatial error diffusion (`fs`, `atkinson`, `jajuni`, `stucki`, `burkes`, `sierra:variant=1`, `sierra:variant=2`, `sierra:variant=3`, or `lso2`), or [CPU positional dithering](../palette-application/dithering/README.md#positional-candidate-precision) (`a_dither`, `x_dither`, `bluenoise`). `auto` retains the existing palette-count selection of Atkinson or FS. Ward merge, default/AUTO cover (resolved to off on native float), and [soft or hard cover](../palette-construction/cover-policy/README.md#hard-mode-on-native-float-palettes) are supported; an omitted active-cover mode resolves to soft, and active snap is excluded. A zero snap approach rate is an identity and selects the same path as `-_none`. It emits normal RGB or HLS SIXEL, or retains the palette-free foreground mask selected by `-e`; either can be wrapped in [terminal macros](terminal-macros.md#native-float-palettes-and-color-interpretation). K-means feedback is disabled. The selected path also accepts [built-in `-b` tables](../palette-construction/fixed-palettes.md#native-float-application-and-display-p3) and fixed palettes through `-m` with all four admitted solver families and AUTO; their interpretation and image-map construction are specified in [External palette input and output](../palette-construction/external-palettes.md#display-p3-output). Other combinations fail before SIXEL output starts. `-M` exports sRGB8 rather than unmarked P3 values, clipping colors outside sRGB. Opaque [OR-mode output](or-mode/README.md#native-float-palettes) is also supported with its distinct index-composition semantics; preserved masks and `-e` remain excluded from native OR output. Opaque [DRCS output](drcs.md#native-float-palettes-and-color-interpretation) also uses the selected path, with the glyph-specific exclusions documented there. [PNG snapshots](../../writers/png/README.md#native-float-snapshots) also preserve the ordinary native palette path and tag P3 output. [Delta encoding](delta-encoding.md#display-p3-history-interpretation) supports ordinary RGB or HLS SIXEL with output-aware retained history; palette-free `-e`, OR `-O` and DRCS `-@` are incompatible with delta preservation; macro `-u`/`-n` output is also rejected because the current emitter does not track invocation bases. PNG snapshots also reject delta because their standalone decoder has no retained base. Other alternate delta transports remain excluded. Interframe dithering and GPU are outside this selected path. The separate [high-color P3 path](high-color/README.md#display-p3-boundary) supports ordinary or macro-wrapped SIXEL, opaque DRCS bodies and direct PNG snapshots, with its own narrower admission contract.

The default palette type and explicit `-tauto` resolve to RGB before capability validation, including the direct frame API; `-trgb` is not required. Explicit `-thls` uses [native HLS serialization](#native-hls-serialization), with direct destination rounding and the same receiver interpretation of reconstructed RGB.

The selected loader integration tests use libpng P3 ICC RGB8/RGB16, an untagged sRGB RGB8 PNG, and a static RGB16 TIFF with orientation 6. They explicitly select builtin CMS, canonical linear output and `prefer_8bit=0`. These tests do not establish wide-gamut support for every loader, source domain, resizing filter or optional backend. The native palette stage consumes RGB888 and the five typed three-component float32 formats; packed alpha-bearing input reaches that stage through the normalization below. The selected encoder path converts source samples into the requested `-X` coordinates before palette construction.

```sh
./converters/img2sixel --threads=1 \
  -L 'libpng:cms_engine=builtin:cms_target=linear:prefer_8bit=0!' \
  -j scalar:resize_precision=float --precision=auto \
  -Q kmeans:seed=1 -X linear -W gamma -U display-p3 \
  --sampling-policy=full-frame --binning-policy=none \
  -F none -a off -_ none '-~none' -d fs -t rgb \
  tests/data/color-numeric/png-p3-16-rgb.png > output.six
```

The frame retains its typed coordinates. In gamma or linear sRGB coordinates, negative and above-one components preserve P3 colors; Oklab, CIELAB and DIN99d retain their corresponding extended coordinates. The output definition is a separate job policy. All four admitted solver families retain extended values through candidate construction and float palette export. A failure in the selected float solver is reported; it cannot silently retry a byte solver or a different solver. The output-specific state is scoped to the palette build attempt; it does not change the [ordinary typed float contracts](../palette-construction/quantization/README.md#ordinary-float-iterative-solvers) of subsequent calls.

Before index selection, the palette owner prepares a separate RGB101 serialization cache: it converts the canonical palette to P3, clamps only that output copy to the destination gamut, and rounds each channel to an integer in `0..100`. Both the authoritative float working palette and its compatibility byte view remain unchanged. Lookup and diffusion consume the original working coordinates. The writer consumes the cached codes without another color transform or byte round trip; palette compaction, reordering and cache reuse are disabled in this path. Early preparation of wire codes does not enable [palette snapping](../palette-construction/snap-policy/README.md); this selected path requires disabled snapping (`-_none` or a zero approach rate).

For example, linear gray centers `0.1` and `0.11` produce P3 code values `35%` and `37%`. With snap disabled, a query of `0.106` still selects the second original center. Substituting the inverse-decoded wire colors would move the decision boundary above `0.106` and incorrectly select the first center. The direct palette tests protect unchanged float and byte working views and unchanged lookup results. Primary and intermediate-color wire tests independently protect the destination conversion.

P3 requires an effective float working format even for `-Wgamma` and an explicit `--precision=8bit` preference. The byte preference does not override precision required by color conversion. Requested precision stays separate from this output requirement, so leaving P3 restores the effective format required by the remaining precision and working-space settings. An explicit float request remains float after leaving P3; automatic gamma working coordinates return to the ordinary byte preference.

Gamma working coordinates use the existing sRGB transfer function with sign-preserving extended values. FS computes its error against the unrounded working palette. [Dither clamp policy](../palette-application/clamp-policy.md) controls feedback while retaining original extended coordinates; `-0none` propagates the unrestricted residual. For example, errors `(0.125, -0.125, 0.0625)` sent to a following source `(1, -0.03125, 0.125)` with the FS right-neighbor weight `7/16` produce `(1.0546875, -0.0859375, 0.15234375)` before that next lookup. The direct test observes this input to the real lookup. The CLI two-color test checks independently derived source-group means, paint-time wire agreement with a raster FS reference calculation, and actual FS dispatch. Its painted result is also unchanged when error propagation is omitted, so detecting missing propagation or an intermediate clamp belongs to the direct next-lookup test and its code mutations. The other few-color CLI witnesses can optimize FS away because every source color fits in the palette; they establish option acceptance and wire values, not error diffusion. Nonfinite working samples or errors fail instead of entering lookup, and a later valid apply on the same policy recovers. The same feedback policy applies to ordinary output; it is independent of the output primaries.

Repeated `-U` settings replace the output definition. Reusing one encoder and output object for P3, gamma and P3 again restores the corresponding behavior on each job. The private precision opt-in is scoped to one palette-generation call and does not change the installed component request structures.

Ward merge retains the same nominal channel scales and `channel_l` weights as the existing merge path, while preserving signed, above-range and fractional centers. K-means counts actual retained coordinates when deciding whether merge is necessary; byte projection cannot collapse distinct float colors for that decision. K-medoids expands candidate-bin addresses independently of its Ward metric. K-means also preserves signed sums during empty-cluster repair and post-merge Lloyd refinement. See [Final palette merge policy](../palette-construction/merge-policy/README.md#float-coordinate-preservation) for the numeric contract and tests.

## Selected ordinary sRGB float path

The same extended-palette/RGB101 preparation is selected for `-Ugamma`, `-Ulinear` and `-Usmpte-c` when a static or animated RGB job requires float through the source, an image map, packed alpha composition, a non-gamma generated-palette clustering view or explicit float precision, and the options match one of the four CPU solver families described above: any of the five clustering/working spaces, any sampling policy, the supported binning choices below and lookup policies above, none, the CPU spatial diffusion methods listed above (including `auto`), or the three positional methods, none or Ward merge, default/AUTO, off or explicitly selected soft/hard cover, and disabled snap. It does not promote a job with byte-eligible source/map data and operations merely to select this algorithm. A float image map can require float palette application while the source image plan remains RGB888. Other settings retain their existing path. All four admitted solver families and AUTO also accept ordinary sRGB mapfile jobs under the same frame/precision conditions, as described in [selected float mapfile application](../palette-construction/external-palettes.md#selected-ordinary-srgb-output). The P3 and selected sRGB image-map builders both use the extended path. [Built-in `-b` tables](../palette-construction/fixed-palettes.md#native-float-application-and-display-p3) also retain an authoritative float working view under these frame/precision conditions while bypassing construction and cover. The separate [monochrome foreground-mask path](../palette-construction/fixed-palettes.md#native-monochrome-application) uses the same typed endpoint preparation without sending RGB definitions.

Generated palettes also retain native float coordinates when `-Xlinear`, `-Xoklab`, `-Xcielab` or `-Xdin99d` requires a float clustering view but `-Wgamma` leaves the image plan at RGB888. The palette returns to gamma through the extended transform; lookup promotes its byte source queries to match that float palette. This preserves sub-byte centroids and negative components produced by the inverse transform, without changing the requested precision or the source buffer. `-.8bit` does not discard the precision required by this calculation. An otherwise byte-eligible `-Xgamma` job keeps its byte palette; an unused `-X` setting on a built-in table does not change its representation. Source-image generation is distinct from image-map construction, whose admission remains specified by [External palette input and output](../palette-construction/external-palettes.md#selected-ordinary-srgb-output).

Omitted cover and plain `-aauto` select this path without an explicit mode. Their native repair budget is zero, as defined by [Cover policy](../palette-construction/cover-policy/README.md). Palette construction for qualifying float jobs, including ordinary sRGB defaults, therefore differs from the legacy byte-projected construction; identical palette entries, dither patterns or perceptual scores are not promised. Byte-eligible jobs keep their existing precision decision. [Terminal macro output](terminal-macros.md#native-float-palettes-and-color-interpretation) uses the same admission and palette preparation as ordinary output. Opaque [OR output](or-mode/README.md#native-float-palettes) also retains native palettes, including serial fallback for offsets. Opaque [DRCS output](drcs.md#native-float-palettes-and-color-interpretation) retains the native SIXEL body under its separate glyph envelope.

These legacy output definitions share the same native construction and application whether snap is disabled or active at its supported final stage. Changing only `-U` changes the wire conversion, while the working palette and sRGB8 `-M` export remain output-independent. Linear and SMPTE-C receivers must interpret the transmitted components accordingly. Byte-eligible jobs keep their existing output conversion; selecting either output alone does not promote the source.

Palette generation retains extended coordinates. A separate destination copy is clamped and rounded to RGB101 once; preparing it does not change the working palette used for lookup and error diffusion. The writer emits the stored codes directly. Source color interpretation, working coordinates and destination RGB definition remain separate decisions. The `dither_contract` trace reports `rgb101=1` for this path and `rgb101=0` for legacy palette finalization.

For gamma, linear and SMPTE-C output, [native final snap](../palette-construction/snap-policy/README.md#native-float-final-snap-for-srgb-output) is also supported for generated palettes with `timing=once` and cover default/AUTO, off or soft/hard cover. The P3 active-snap restriction is unchanged.

The selected lookup classes consume the authoritative float palette even when its byte projection happens to be black and white. The default `certlut` and explicit `auto` (resolved to `6bit`) remain distinct choices. Their distance geometry and focused integration tests are owned by [Lookup policy](../palette-application/lookup-policy/README.md#extended-float-coordinates).

Ordinary RGB/HLS [native delta](delta-encoding.md#linear-and-smpte-c-output-history) also supports these linear and SMPTE-C output representations, retaining the selected output interpretation for threshold comparisons and converting kept colors back into the working space. Alternate delta transports remain outside that migration.

### Library entry points

The encoder-managed native path above serves CLI, file, frame and byte-buffer jobs subject to its admission conditions. Standalone `sixel_dither_new()` → `sixel_dither_initialize()` → `sixel_encode()` also retains a native palette for ordinary CPU RGBFLOAT32, LINEARRGBFLOAT32, OKLABFLOAT32, CIELABFLOAT32 or DIN99DFLOAT32 initialization with the default AUTO/Heckbert builder and inactive snap. The palette keeps finite signed and sub-byte working coordinates, and RGB/HLS serialization rounds a separate gamma-sRGB output copy. Linear and perceptual palette representatives retain their initialized coordinates during lookup and diffusion; only the separate output cache converts them to gamma sRGB. The palette owns its initialization domain independently of a later query-format setter or a shared output object. The public `unsigned char *` input parameter carries storage, not an 8-bit precision promise: initialization or `sixel_dither_set_pixelformat()` supplies the actual layout. A float array can be passed through that pointer type; `sixel_encode()`'s legacy `depth` argument is unused.

`sixel_dither_get_palette()` exposes mutable compatibility bytes. Reading them leaves the native float palette intact. The next apply or encode detects an actual change to that byte view and makes the complete byte palette authoritative. `sixel_dither_set_palette()` explicitly replaces float precision even when the assigned bytes equal the compatibility view. Reinitialization invalidates a previously borrowed palette pointer. For a native linear palette, compatibility bytes decode as `byte / 255`. Perceptual lightness also decodes as `byte / 255`; opponent coordinates decode as `(byte / 255 - 0.5) * scale`, where scale is 1 for Oklab, 3 for CIELAB and 2 for DIN99d. These are working coordinates, not gamma-encoded sRGB colors. Assigning or modifying these bytes rebuilds lookup values in the recorded domain and refreshes the gamma output cache; it does not change the palette domain. A read-only getter still causes no rebuild. Detection stores at most 768 shadow bytes, a count and the initialization-format tag per dither object, compares only occupied entries, and introduces no per-pixel buffer or getter allocation.

Successful reinitialization selects the representation again: a genuine RGB888 palette stays byte-based, and typed float initialization can restore native precision. A failed native build or typed byte-view rebuild cannot be encoded as a partial or fallback palette; initialize successfully or supply an explicit byte palette before reuse. The legacy byte setter has no status return, so a failed rebuild leaves a context that rejects subsequent encoding until recovery. Separate dither objects own independent state. RGB888 query storage can be used against an already native gamma palette without discarding it; every other native palette requires queries in its initialized float format. Changing the query format to another color space requires reinitialization, including RGB888 or gamma float queries against a linear/perceptual palette, or changing between perceptual spaces. Byte-view reconciliation does not bypass this domain check. As with other low-level encoding, input storage is mutable, so comparisons between calls must restore their original pixels.

Active snap, deprecated temporal application and GPU work retain their separate compatibility scope. Changing a native standalone context to temporal/GPU application is rejected before output rather than silently discarding its palette. The wider typed-space/output-definition contract remains available through `sixel_encoder_encode_frame()` under the encoder's documented selection. High-color encoding has its own [precision boundary](high-color/README.md#destination-samples-and-precision). Neither retaining a float palette nor preparing its wire cache implies palette snapping.

The standalone perceptual numeric witnesses use independent inverse-matrix and scalar equations, with no production converter in the oracle. Palette coordinates allow an absolute error of `2e-6` over the tested `[-3, 3]` range for normalization and float stores. The two chromatic wire witnesses and the byte-replacement witness budget `0.002` percentage points or degrees for propagated conversion error; their nearest RGB101/HLS rounding boundary is more than `0.016` units away. Lookup and one-row FS tests use independent opponent-axis decision margins. These tests establish arithmetic and state behavior, not photographic quality rankings. Finite source coordinates can still produce an unrepresentable nonlinear output transform; such initialization fails without publishing a usable palette, and later valid initialization recovers.

### Sampling and retained precision

For generated palettes, the selected float path accepts all three sampling policies. `full-frame` builds from the preprocessed frame. `adaptive-grid` copies selected loaded-frame pixels before preprocessing and retains their typed float coordinates, including negative and above-one components. This copy does not normalize or clamp samples. The existing solid-region augmentation applies to byte RGB/RGBA input; it is not applied to typed float samples. `auto` retains the resource-aware choice described in the [execution map](../execution-map/README.md).

Whether an adaptive palette is built synchronously or on a worker, an already-float source remains float even when base precision is `auto` or `8bit`. A byte-eligible gamma job retains its byte path. Thread-creation failure rebuilds from the same owned sample synchronously. Other worker failures fall back to the preprocessed full frame only for `auto`; an explicitly requested adaptive policy reports the error without starting SIXEL output. The fallback rebuild retains the same precision and separate RGB101 output boundary. Automatic fallback may change the palette because its sample source changes; it does not promise identical colors to adaptive sampling.

The direct sampling tests check exact membership after cropping and bit-preserving copies in each of the five float formats. Whole-encoder tests check independently derived centroids and RGB101 values across synchronous and worker execution, automatic selection, retained source precision and injected failures. These tiny fixtures exercise palette construction and output, not meaningful error diffusion; the spatial tests below and external multi-image comparisons cover that separately.

### Separate alpha-zero masks

The selected native path also accepts RGB888 or typed float RGB frames with a complete, separate alpha-zero mask when using a generated palette, cover default/AUTO, off or soft/hard cover, and at least two requested palette slots. P3 output and explicit float requests require float application; an otherwise byte-eligible ordinary-sRGB job retains its byte path. Packed RGBA/gray-alpha input is normalized as described below; generated and fixed animation follow their frame/cache contracts below. Loader-side fractional-alpha composition remains governed by [Alpha policy](../../loader/alpha-policy/README.md).

Direct frame and byte API calls resolve an omitted palette capacity to the same default as file encoding before admission and omission-slot reservation, without rewriting the encoder request.

Palette construction compacts only visible samples after conversion to the requested clustering coordinates. Hidden RGB values neither affect representatives nor consume color slots. All-transparent input uses one finite black candidate and still omits every image pixel. The compact construction buffer retains three float components per visible sample, or three bytes on a byte-eligible RGB888 path (one dummy sample for empty coverage); the image and its mask retain their original geometry for lookup and spatial error diffusion.

One palette slot is reserved for omission. Cover repairs only the real palette, using a 255-color growth ceiling so that the later omission slot still fits. This capacity is private build-attempt state; public API signatures and component request layouts are unchanged. Cover growth retains its existing permission to exceed the quantizer request, while non-growing cover keeps the real entry count fixed. Appending it preserves the authoritative working float entries; only the reserved entry is derived from the independent sRGB background hint. Exhaustive and prepared lookup tables exclude that slot from visible nearest-color queries. Output conversion then caches RGB101 values without replacing the working palette. `clear` emits P2=0 and `keep` emits P2=1 while both leave masked pixels unpainted; a background hint cannot make them visible. A present mask with no set bits may still reserve its slot. Each new encode rebuilds the native palette, avoiding stale mask/key state when one encoder alternates masked and opaque input.

Fixed `-m` and `-b` palettes accept the same separated-mask storage on the selected native path. They retain every original entry and its order, including all 256 colors when present. No alpha slot is appended or excluded from lookup. Palette application skips masked samples using a temporary placeholder index, and the normal SIXEL writer independently omits those positions using the borrowed source mask. Thus visible pixels can still select entry zero and entry 255. The mask stays in source coordinates across serial/parallel six-line bands and transparent output margins, and is cleared from the output context before reuse. Size-oriented fill optimization cannot paint through its holes. An all-transparent image retains the fixed palette while painting nothing. Native `-e`/`-e -i` also accept separate masks: source holes are omitted in addition to the mode's existing non-painted entry zero. Their foreground convention is unchanged; see [fixed palettes](../palette-construction/fixed-palettes.md#native-monochrome-application).

Fixed palette selection does not itself promote byte input. This extension covers masked fixed palettes when the source, image map or processing already selects native float application; the legacy byte fixed-palette transparency path is not migrated here. Fixed palettes bypass cover, so omit explicit `-a` options as described in [external palettes](../palette-construction/external-palettes.md).

### Packed alpha normalization

The selected CPU palette path and [ordinary high-color path](high-color/README.md#packed-source-alpha) accept gamma-coordinate `RGBA8888`, `BGRA8888`, `ARGB8888`, `ABGR8888`, `GA88` and `AG88` frames. Before sampling, crop/resize planning or palette work, they separate this storage into RGB plus a binary omission mask. The existing frame transparency metadata decides whether the alpha bytes are interpreted. If alpha interpretation is disabled, the RGB/gray coordinates are retained and the alpha bytes neither blend nor hide pixels. An existing separate mask remains effective in either case. This is an internal normalization step; public frame formats and encoder API signatures are unchanged.

This low-level packed-frame boundary preserves its existing composition convention: interpreted zero alpha becomes an omitted pixel; nonzero fractional alpha blends in gamma coordinates against the encoder background hint, or black when no hint exists. Gray-alpha first converts that background to the legacy integer gray `(299R + 587G + 114B + 500) / 1000`. For source byte `S`, background byte `B` and alpha byte `A`, the retained float sample is `(S*A + B*(255-A)) / 65025`. Intermediate arithmetic uses double and only the final float32 store rounds. This is a compatibility rule for unresolved packed frames, not a replacement for [loader-owned alpha composition](../../loader/alpha-policy/README.md). Already resolved RGB frames are not blended again.

Fractional composition requires float even under `-.8bit`; binary/opaque packed input with no float-requiring operation remains exact RGB888. `-.float32`, Display P3 output, or non-gamma working coordinates require float. Non-gamma clustering coordinates also require float for palette construction; high color bypasses clustering. Packed layout alone does not force it. The mask combines interpreted alpha-zero positions with any existing separate holes. Hidden coordinates cannot enter palette construction or cover repair. Generated and fixed palettes then use the [separate-mask contract](#separate-alpha-zero-masks), including their distinct reserved-slot rules. High color uses its [existing skip register](high-color/README.md#separated-source-masks). Changing `-A` between clear and keep changes the SIXEL request, not whether source alpha is interpreted.

Normalization publishes pixels and mask together. Allocation failure emits no image output and leaves the original packed frame available for retry. Borrowed input bytes are never modified. The admission limits above still apply: GPU and nonstandard output modes retain their previous path, and this extension does not change standalone low-level `sixel_dither_*` packed-input handling.

### Generated palettes in animation

Generated-palette animation uses the same selected native path as static frames. Each delivered RGB/typed-float frame owns its palette construction, visible-sample selection, cover reservation, working palette and destination RGB101 copy. Spatial diffusion starts with fresh residual buffers for each frame; positional dithering retains its existing frame/coordinate rules. A later frame or loop replay does not reuse a generated palette or the preceding frame's omission slot. True byte-only work stays eligible for its byte path, including binary packed alpha; animation alone does not require float.

This scope includes the ordinary gamma/linear/SMPTE-C outputs and Display P3 with the option restrictions above. It does not change loader composition, frame timing, loop counts or terminal placement. A shared loader frame is copied before preprocessing that mutates its storage, including packed-alpha separation when no explicit float, resize or workspace change otherwise requires a copy. Already resolved RGB input is not alpha-composited again. [Animation playback](../animation.md) owns loader and playback behavior; [animation threading](../../threading/animation.md) owns queue ordering and lifetime.

Fixed palettes follow the [animation source-cache contract](#fixed-palettes-in-animation). Interframe/STBN, GPU and special output modes are not enabled by this extension.

### Binning and extended coordinates

For K-means, the selected float path accepts `none`, `exact`, `hard`, `soft` and `auto` binning. `exact` combines identical coordinates with their multiplicities. `hard` and `soft` retain source coordinates in their weighted sums; only their bin addresses use a normalized grid. For each axis, the addressing interval starts at the nominal bounds of its typed color space and expands to include finite sample extrema when necessary. Thus distinct out-of-range colors can occupy different cells instead of all saturating into an edge cell. Inputs contained in the nominal interval retain the established grid. Soft binning retains the existing fractional trilinear weights.

This interval extension changes neither the requested grid depth and mapping curve nor the clustering coordinates, distance metric, convergence scale or compatibility byte projection. It does not guarantee distinct cells for every distinct source color: finite-resolution binning can still merge nearby colors, and a distant outlier can make cells coarser. `auto` retains its existing resolution to hard binning for K-means. This is separate from the proposed [adaptive hard-binning depth design](../palette-construction/clustering-colorspace/README.md#adaptive-hard-binning-design).

The binning tests independently check unequal-population means in all five typed spaces, separated colors outside both ends of each nominal axis, and ordinary sRGB/P3 wire values. Edge tests use a controlled PCA initializer to avoid treating stochastic K-means convergence as a bin-address guarantee. A nominal gamma fixture compares the legacy and extended builders; invalid-input cases check rejection followed by valid reuse, without promising identical error codes between binning implementations. These small fixtures are arithmetic and state tests, not image-quality evidence.

### Heckbert representatives

`-Qheckbert` and `auto` resolved to Heckbert use the selected float path. Its native histogram preserves finite input coordinates and exact occurrence counts; lookup grid depth does not quantize that histogram. All split, representative and profile choices remain available, as described in [Native float Heckbert](../palette-construction/quantization/README.md#native-float-heckbert). Top-level binning is `none` (`auto` resolves to `none`); unsupported binning remains an error. Omitted/auto/none binning resolves `-Qauto` to Heckbert; exact/hard/soft binning resolves it to K-means and uses that solver's admitted native path. The requested policy stays automatic and is resolved per frame. The byte-eligible histogram path is unchanged.

### K-center and K-medoids representatives

The selected path also accepts `-Qcenter` and `-Qmedoids`. This includes K-center's `auto`, `fft`, `swap` and `hybrid` modes, and K-medoids' `auto`, `pam`, `sample` (CLARA), `random` (CLARANS) and `bandit` (BanditPAM) modes. Their objectives and search budgets remain those of the [quantization algorithms](../palette-construction/quantization/README.md).

| Solver | Top-level binning on the selected path | Retained coordinates |
| --- | --- | --- |
| K-means | `none`, `exact`, `hard`, `soft`; `auto` resolves to hard. | Weighted native coordinates and generated centers. |
| K-center | `none`, `exact`, `hard`; `auto` resolves to hard. | Source coordinates or weighted bin means, transformed by the existing fixed per-axis scales for solver geometry and restored for float export. |
| K-medoids | `none`; `auto` resolves to none. | Observed native source representatives selected through the existing private candidate histogram. This histogram remains active even without a shared binning artifact. |

K-center's shared hard-bin addresses and K-medoids' private candidate-bin addresses expand their nominal intervals to include finite sample extrema, using the same addressing rule as K-means. The coordinates used for distance calculations are not rescaled to those expanded bounds. K-center retains its established byte-scaled double geometry, including opponent-axis scales; K-medoids retains native double coordinates. This path preserves extended samples without redefining either solver's metric. K-center bounds candidate-stratum indices before unsigned conversion even for extreme finite coordinates; this does not clamp the color itself. The compatibility byte palette remains bounded, but it is not used to reconstruct the authoritative float palette on this path.

A K-center hard-bin representative is the population mean of its cell; it need not be an observed source color. K-medoids instead chooses an observed source sample nearest its private bin mean before discrete optimization. Their representative tests deliberately distinguish those contracts. Separate reduced-color tests exercise selection when the requested palette is smaller than the candidate set. Wire tests cover each clustering space, mixed clustering/working choices, synchronous and worker execution, ordinary sRGB and Display P3. Byte-eligible gamma jobs still use the existing byte path. Implicit active cover and earlier snap timing remain outside the selected path, as do the additional binning choices not listed for each solver. Final snap follows the ordinary-output scope above; P3 plus active snap remains unsupported.

The solver value fixtures use binary-exact inputs in `[-4, 4]` and compare native components with an absolute tolerance of `2e-6` (about four binary32 ULPs at magnitude four), covering nominal scale/offset round trips and final float storage. The one-bin mean and observed-representative witnesses use `5e-7`. These budgets remain much smaller than either byte projection or clipping errors. The large finite pruning fixture checks membership on its exact power-of-two source grid and retains an independent tolerance on the small opponent components. P3 primary wire checks reuse the [independent P3 red coordinates](../../../tests/data/color-numeric/p3-palette.h). The endpoint code values `(100, 0, 0)` have a `0.005` encoded-channel margin to the next RGB101 rounding boundary; exact wire comparisons do not require bit-identical intermediate transforms. No perceptual metric substitutes for these value assertions.

### Spatial diffusion and the working palette

Each admitted spatial kernel consumes the authoritative, unrounded float working palette. Its residual is computed against those coordinates, including canonical negative or above-one values for P3. No byte palette round trip is inserted. Keeping a separate output cache changes neither the lookup/error reference nor the kernel weights or clamp policy. The Stucki and Sierra-2 names retain the [documented libsixel coefficient variants](../palette-application/dithering/README.md); LSO2 retains its error-dependent coefficient table. `auto` retains the completed-palette-count rule, with the existing exact-color optimization still able to disable unnecessary diffusion.

The whole-encoder tests independently fix the extended source centroid and final wire values for each method, both output definitions and the gamma/linear working transfers. The K-means color-space matrix tests separately cover all 25 `-X`/`-W` combinations with both outputs, independent native-space centroids and immutable lookup palettes. Separate two-pixel kernel tests fix the next lookup value from a nonzero residual against the unrounded working palette. The perceptual-space residual tests cover all nine admitted kernels, including LSO2's lightness-only propagation. These tests cover horizontal propagation; existing [clamp tests](../palette-application/clamp-policy.md#test-coverage) cover limiting, FS vertical/serpentine taps and parallel overlap separately. This is not exhaustive stencil, animation, low-color quality or parallel-boundary coverage for every kernel.

### Fixed palettes in animation

The selected CPU path also accepts animated `-m`, `-b` and `-e` sources. It retains the initially selected palette independently of the mutable per-frame dither object. Structured maps and built-in/monochrome tables retain their original sRGB8 entries; image maps retain the palette constructed on first use, in its original working space and precision. Output RGB101 codes, palette compaction and working-space conversions never replace this source. A structured stdin map such as `-m gpl:-` is read once across all frames and loop replays.

An unchanged working space, output definition and native/byte requirement reuses the application object and its prepared lookup input. A change to those values derives a new application palette from the retained source. Changing `-W`, `-U` or precision between direct frame calls does not accumulate transforms, reconstruct native image-map floats from bytes, or reload the map. A byte-eligible source and structured/table palette can return to byte application; an initially native image-map palette remains a float requirement. The first image-map construction fixes its colors: later construction/loader settings do not regenerate that animation palette. Selecting a map again, changing the built-in selection or monochrome inversion, starting a new file encode, or encoding a static frame resets the source cache. Static map reload behavior is unchanged.

Frame geometry, masks and spatial diffusion remain frame-local. Complete omission masks do not reserve or remove a fixed entry. Excluded legacy temporal/GPU/output paths retain their existing behavior; this contract does not certify transitions into those modes. The source cache belongs to each encoder and adds no public API or process-global palette state.


## SIXEL syntax and receiver interpretation

With `-t rgb`, a palette definition has this form:

```text
# index ; 2 ; red ; green ; blue
```

Each RGB component is an integer percentage in `0..100`. The `2` selects the RGB form of the color definition. It does not identify sRGB, linear RGB, SMPTE-C, Display P3, a transfer curve, or a display profile. SIXEL provides no ICC payload or output-space tag for the receiver to recover the `-U` setting. See [SIXEL color registers](../../sixel-format/README.md#graphics-color-introducer).

`-t hls` instead serializes the converted output RGB triplet as DEC HLS coordinates. It changes the syntax of the color definition; it does not make `-U` an HLS working-space selector or add color-management metadata.

### Native HLS serialization

The selected CPU float path accepts `-t hls` for gamma, linear, SMPTE-C and explicit Display P3 output. The construction, working palette, lookup and diffusion contracts above are unchanged. Where those sections describe RGB101 serialization, HLS instead uses a separate destination RGB float view produced by the same output transform. It clamps that output copy to the destination RGB cube, then rounds the DEC hue, lightness and saturation fields directly. It does not first round RGB percentages or reconstruct RGB from compatibility bytes. RGB output retains its existing RGB101 codes. Both cached views share one palette-owned publication and invalidation boundary; neither changes the working palette or enables snap. The additional cache is 3 KiB per palette at the 256-entry limit, not per image pixel, and adds no installed public interface.

DEC hue uses blue at 0, red at 120 and green at 240; hue rounds to an integer degree modulo 360, and lightness/saturation round to integer percentages. Exact grays use hue and saturation zero. The HLS coordinates describe the RGB basis selected by `-U`; the receiver must interpret the reconstructed RGB in that basis. There is no new embedded profile or negotiation grammar.

For example, the extended linear samples `(2, 0.1, 0.1)` and `(-0.25, 0.1, 0.1)` have centroid `(0.875, 0.1, 0.1)`. Its sRGB output is HLS `(120, 65, 84)`, while P3 is `(122, 62, 67)`. Premature RGB101 rounding would change saturation to 83 and 66 respectively. This is a final-output precision distinction; the unrounded centroid still governs index selection.

Ordinary and macro output retain their existing mask support. Opaque DRCS and native OR output use the same HLS destination view and retain their existing composition exclusions. Serial and threaded native OR both honor HLS; legacy byte OR retains its historical RGB serialization. True byte-eligible jobs remain byte. Changing between RGB/HLS or sRGB/P3 on a reused encoder rebuilds the appropriate output view. Native HLS delta uses the separately documented [retained-color model](delta-encoding.md#hls-retained-color-model), including its decoder approximation and syntax-switch behavior. Active snap retains its existing admission and sRGB target semantics: it does not promise that a subsequent HLS round trip preserves an exact RGB101 grid. `-Uauto` retains the session scope described below; enabling HLS does not add automatic DRCS or OR negotiation.


Display behavior therefore depends on the receiving terminal and display stack. A browser preview or a decoded PNG that treats all three streams as ordinary RGB does not show three correctly color-managed renditions. For a meaningful comparison of alternative output spaces, the consumer must know the chosen space outside the SIXEL stream.

### Negotiation through the proposed color protocol

The [Terminal graphics color management proposal](../../protocols/graphics-color-management.md) defines a receiver-independent agreement for these RGB numbers. It separates an explicit sRGB policy from a reported device-input definition, provides DECRQSS save/restore for each target's policy, and specifies dedicated color-definition queries. Protocol support must be established by the session's replies; a P3-capable display alone does not establish the receiver's input interpretation.

For ordinary SIXEL, a controller using this proposal can display the selected `-Udisplay-p3` output with the following transaction. `CSI`, `DCS`, and `ST` denote the control bytes defined in the proposal, and `M` is the exact saved policy.

| Step | Exchange or action |
| --- | --- |
| Discover target 1 | Send `CSI ?1./r`; require a complete valid reply with `A=1`, `S2=1`, and `C=4`. For example, `DCS 1;1;1;1;4./r ST` also advertises expansion support. |
| Save policy | Send `DCS $q1./p ST`; save `M` from `DCS 1$r1;M./p ST`, preserving `0` versus `1`. |
| Select device input | Send `CSI 1;2./p`; query again and require policy `2`. |
| Display | Send the bytes generated with `-Udisplay-p3`; new RGB definitions are interpreted as standard Display P3. |
| Restore | Send `CSI 1;M./p`; verify the saved value, including on recoverable errors. |

For a color-preserving sRGB comparison, generate `-Ugamma` output and set and verify policy `1`. Feeding gamma sRGB values under a P3 device policy reinterprets those values in the wider basis; it does not establish correct sRGB rendering. Policy `3` explicitly requests the proposal's component expansion and serves a different purpose from source-to-destination color conversion.

Explicit `img2sixel -Udisplay-p3` and `-Ugamma` perform none of these color-protocol exchanges. The CLI-only `-Uauto` manages discovery and the transaction above, accepting the named sRGB and Display P3 definitions. An available target with an unsupported definition uses verified policy `1` and gamma output; P3 requires both `C=4` and `S2=1`. A final automatic request cannot be combined with DRCS (`-@`): the implemented transaction is for ordinary SIXEL (`T=1`), while DRCS uses a separate `T=2` policy. This combination fails before any color query or image output, regardless of the eventual advertised definition. A later explicit `-Ugamma` clears auto. Explicit `-Udisplay-p3` also emits DRCS under its [native palette contract](drcs.md#native-float-palettes-and-color-interpretation), without any color-protocol exchange; the caller configures the separate DRCS receiver policy. Neither the library `setopt` API nor bindings accept `auto`.

The reply parser enforces the proposal's [numeric field and simple-RGB rules](../../protocols/graphics-color-management.md#simple-rgb-definition), including rejection of the reserved saturation value `9999`. A simple definition has eight to ten fields: the five common fields, three mandatory base-9999 gamma limbs, and optional primaries/white identifiers. It remains an unsupported transform and therefore uses verified sRGB fallback only after its syntax and reconstructed gamma range pass validation. The five-field named sRGB/P3 replies and their negotiation steps above are unchanged.

The automatic route is limited to images sent to stdout as a TTY, with no `-o` option or with every `-o` argument exactly `-`. Any other outfile argument excludes negotiation, including `-o file -o -`, whose actual output remains a file under the existing outfile semantics. File/pipe destinations keep the interchange default, gamma sRGB, regardless of a terminal attached to stderr. An explicit `-Udisplay-p3` remains a user-selected representation even when saving a file; it requires a consumer that knows how to interpret that file.

During the POSIX query phases, the CLI temporarily disables the terminal's suspend character so a protocol SUB byte reaches the reply parser without suspending the process or flushing input. A keyboard suspend key, normally Ctrl-Z, consequently becomes protocol input during those phases. Each request/reply exchange shares one deadline across its request write and reply reads; a separate control write has its own deadline. Each deadline can be configured up to ten seconds, and a phase containing multiple exchanges has no combined ten-second limit. The original suspend character and other terminal settings are restored before synchronous encoding and during cleanup. Signal handling remains enabled, and SIGINT or SIGTERM can cancel the exchange.

The transport blocks SIGINT and SIGTERM while checking cancellation, then uses `pselect` to restore the caller's signal mask atomically with the I/O wait. A cancellation signal enabled by that mask therefore cannot be lost between the check and the wait, even when output is blocked. Every return restores the caller's mask, and unrelated signals remain enabled according to that mask. Both build systems require this `pselect` surface through the shared terminal-I/O capability probe.

The default remains `-Ugamma`. `SIXEL_OUTPUT_COLORSPACE` supplies a CLI default using the same case folding, unambiguous prefixes and named choices; it takes only a base name, without suboptions. An explicit `-U` overrides that environment value, and the last `-U` replaces the whole earlier request. Empty environment values are unset. `-Uauto:timeout_ms=N` and compact `-Uauto:TN` set a decimal deadline in `1..10000` milliseconds, overriding `SIXEL_OUTPUT_COLORSPACE_AUTO_TIMEOUT_MS`; the default is 200 ms. The timeout environment is relevant only to a final automatic request, and an explicit timeout overrides even an invalid environment timeout. These CLI settings also work through `--env NAME=VALUE` without outranking explicit options.

Only a completely silent first capability exchange, a valid unavailable reply, or unavailable local TTY access allows unconfirmed legacy gamma output. This does not prove that the receiver currently interprets RGB as sRGB. A partial or malformed response fails before sending an image. After a timeout or loss of reply correlation, no later query is issued on that job/TTY; saved policy restoration is write-only and bounded. An available target whose policy cannot be saved or verified receives no image. Normal restoration is queried and verified, and restoration or terminal-settings failure cannot produce a successful exit.

Capability may be reused within one invocation, but each image's current policy is saved and restored separately. The CLI releases its reader and terminal settings before synchronous encoding, allowing the existing library OSC11/CPR handling to retain its own lifecycle. Encoding conditions remain those of the selected P3 path: an incompatible input or option can fail after the policy was selected. The CLI preserves that error and restores the original policy without rereading the input or retrying gamma encoding. When a failed control write or encode may leave SIXEL/control framing unfinished, bounded CAN/ST precedes recovery. SIGINT/SIGTERM observed during negotiation, encoding or restoration stops subsequent inputs.

## Precision, rounding, and cost

The legacy output encoder converts a private palette copy and preserves the reusable dither palette in working coordinates. When a usable float32 palette is available, it converts those typed values before packing bytes. Otherwise it converts the byte palette. The selected P3 and ordinary sRGB float paths prepare only a separate RGB101 wire cache before lookup; the working palette is not replaced. Increasing working precision can reduce conversion rounding, but it cannot increase the precision of SIXEL's integer percentage fields.

For RGB definitions, the byte path rounds a channel `b` with integer arithmetic:

```text
percentage = (b * 100 + 127) / 255
```

The float path rounds a clamped normalized channel directly with `floor(channel * 100 + 0.5)`. An exported 8-bit palette and a decoded SIXEL palette can therefore differ through their respective byte and percentage quantization steps. They are not generally byte-identical merely because both use the same `-U` value.

In legacy palette paths, generated palettes with exact [snap policy](../palette-construction/snap-policy/README.md) enabled at `rate=1` receive output finalization that follows the `-U` conversion and puts the palette onto the reversible RGB percentage grid. The native final-snap path instead retains the snapped working palette and converts only its wire copy directly to RGB101. Both cases include SMPTE-C output. It prevents the conversion from leaving the final palette off that grid; it does not remove clipping or make every earlier color conversion lossless.

For `K` palette entries, this conversion is `O(K)` work and uses `O(K)` palette storage, rather than converting all `N` image pixels again. `-U` alone does not request a float32 image buffer. This cost model applies to the ordinary palette path; it is not a measured whole-program speed comparison. Different numeric color definitions can change serialized byte length even when index assignment is unchanged.

## Fixed palettes and palette export

`-M` always exports sRGB8 in ACT, JASC PAL, RIFF PAL and GPL. This applies to every `-U` choice, including the selected Display P3 path. It converts the prepared working palette before wire-specific conversion and final rounding. See [External palette input and output](../palette-construction/external-palettes.md#exporting-a-palette-with-m) for the interchange contract and its wide-gamut limitation.

The preparation of fixed palettes also matters:

| Palette source | Current preparation and output boundary |
| --- | --- |
| Generated palette | Constructed in `-X` and prepared for `-W`. The selected native float paths finalize RGB101 before application; other paths convert to `-U` afterward. |
| Image mapfile, such as `-m swatches.png` | Loaded as an image and prepared in the selected working representation before output conversion. Loader/CMS settings can affect its colors. |
| Structured ACT/PAL/GPL input or built-in `-b` palette | sRGB8 entries are converted to `-W` once. The selected native path retains float coordinates even for gamma work; genuinely byte-eligible gamma jobs keep their byte view. Entries are never interpreted as native working-space bytes. |
| Monochrome `-e` | Uses assumed sRGB black/white endpoints for mapping, with a native working view on the selected float path. It emits a foreground mask with no RGB definitions; `-U` cannot set the receiver foreground. See [native monochrome application](../palette-construction/fixed-palettes.md#native-monochrome-application). |

Fixed palettes bypass generated-palette snap processing. Structured-file and built-in entries retain their sRGB interpretation under `-Wlinear`; image mapfiles still pass through their separate image-loader and palette-construction route.

## Scope and current gaps

Ordinary generated and supplied palettes have distinct working and serialization representations. The selected float path prepares its destination cache before lookup; `sixel_encode_dither` consumes that cache without converting the working palette again. Compatibility paths convert an output copy in `sixel_encode_dither`. High-color has its own destination-sample preparation; an option being accepted does not establish that every alternate encoder consumes it.

The `-I` [high-color path](high-color/README.md#destination-samples-and-precision) converts source samples to gamma, linear, SMPTE-C or Display P3 before key selection, preserving float representatives through wire rounding on its no-diffusion path. Its precision and low-level byte-diffusion boundary are owned by that reference. High-color P3 admission and its exclusions are described in the same reference.

`-U` does not embed a profile in the SIXEL stream, configure a separately invoked decoder, or change loader CMS. Encoder-owned [PNG snapshots](../../writers/png/README.md#native-float-snapshots) explicitly pass P3 interpretation to their decoder and PNG writer; other definitions retain the existing sRGB snapshot interpretation. The static-image stage explanation should not be extended to [delta encoding](delta-encoding.md) without accounting for its retained display-color state across frames.

### Storage and compatibility boundaries

Float source storage, float diffusion and native float palette ownership are separate decisions. A float diffusion buffer alone does not establish that palette construction or output conversion preserves sub-byte values. The [selected ordinary path](#selected-ordinary-srgb-float-path) and [library entry points](#library-entry-points) define which jobs retain an authoritative float palette. Remaining byte operations have the following scopes:

| Boundary | Meaning | Owning contract |
| --- | --- | --- |
| Byte-eligible source and operations | A gamma job that needs no higher precision can retain byte construction and application. Explicit float precision selects the supported float route. | [Encoder precision](../precision/README.md#requested-precision-and-effective-format) |
| Explicit byte storage or palette assignment | Byte components cannot retain signed or sub-byte coordinates. A compatibility getter read alone does not narrow an existing native palette. | [Frame storage](../../concepts/pixelformat-precision/README.md#float-frame-coordinate-changes), [palette access](#library-entry-points) |
| Legacy mapfile export | Metadata-free palette files store sRGB8; conversion and rounding belong to that file boundary. | [External palettes](../palette-construction/external-palettes.md) |
| Wire serialization and retained display history | RGB101/HLS quantization applies to destination values. Delta history models painted colors; ordinary lookup continues to use working coordinates. | [Rounding](#precision-rounding-and-cost), [delta encoding](delta-encoding.md) |
| Policies outside native admission | Early snap, quantizer feedback, GPU and temporal combinations do not acquire extended palette preservation merely from float input. Their compatibility branches remain reachable. | [Native admission](#display-p3-selected-cpu-float-path), [snap](../palette-construction/snap-policy/README.md), [standalone restrictions](#library-entry-points) |
| Low-level high-color diffusion | The explicit legacy 15bpp diffusion routines use a bounded byte plane; high-level no-diffusion output has a separate float representative path. | [High-color precision](high-color/README.md#destination-samples-and-precision) |
| Loader conversion | Encoder palette preservation cannot recover precision or gamut already discarded during loading. Backend and source-format coverage must be checked separately. | [Loader precision](../../loader/precision-policy.md) |

The public color converter uses [common extended arithmetic for float input](../../concepts/pixelformat-precision/README.md#float-conversion-arithmetic), independently of native palette admission. Bounded byte conversion remains an explicit storage operation. Removing bounded float arithmetic alone does not establish end-to-end palette preservation: non-admitted generation policies still retain their own solver restrictions.

Generated float palette entries retain the generation request's typed coordinates even when no native output cache is selected. K-means, K-center and K-medoids undo their solver-local scales before exporting those coordinates; dither initialization does not discard the export or reconstruct it from compatibility bytes. K-center projects its compatibility bytes from the exported float values, so scale/unscale rounding near a byte midpoint does not look like a caller edit. Compatibility Heckbert retains its typed export too, but its non-native byte histogram has already rounded those samples. This retention does not enable extended solver arithmetic, change early snap or feedback policy, or promote a genuinely byte-only palette generation request.

Before CPU palette application, compatibility-byte changes are reconciled with the working float view. Reading an unchanged byte view preserves its float fractions. Changing bytes through the mutable getter replaces the complete float view with the assigned byte coordinates in the current working format, so lookup and serialization agree. Explicit `sixel_dither_set_palette()` assignment is a byte precision boundary even when the assigned bytes equal the existing projection. Indexed serialization, which can bypass application, performs the same reconciliation before copying the working entries. An unchanged entry count and order after application do not invalidate prepared output values. Native standalone palettes retain their separately described domain and byte-shadow rules.

### Defensive and malformed-input tests

The [packed-alpha suite](../../../tests/quant/palette/packed_alpha) also checks short-mask rejection and failures of either normalization allocation, including unchanged original pixels/metadata and successful helper retry.

The [fixed-mask suite](../../../tests/quant/palette/fixed_mask) also checks incomplete mask extents and unsupported OR output at the private mask boundary, followed by successful masked and opaque reuse of the same handles.

The [separate-mask palette suite](../../../tests/quant/palette/alpha_float) also injects a one-shot allocation failure before visible-sample construction. It checks that no image bytes are emitted, a caller's quantizer override is unchanged, and the same encoder and frame succeed on retry.

The [automatic CLI cases](../../../tests/cli/color/session) also reject malformed timeout numbers and keys. The controller boundary cases in the same category compile the actual controller with isolated dependency calls, deterministically cancelling during restoration writes or final terminal release while preserving original encoder errors and preventing another image. These are control-flow observations; real process-signal tests are identified above. The [TTY transport tests](../../../tests/cli/color/tty) separately cover absolute deadlines, backpressure, framing, stale bytes, identity/foreground changes and exact state restoration.

### Coverage audit boundary

The first five tests assert exact exported entries. OC-06 checks the output grid and export/wire agreement; it does not independently validate the SMPTE-C conversion matrix. OC-02 and OC-03 establish byte preservation for the named configurations, not perceptual correctness of all non-gamma fixed-palette combinations. OC-05 is not evidence that a CMS transform ran.

P3 values, lookup and reuse are directly covered by OC-07 through OC-28. General defaults, alias and case handling, invalid values, legacy repeated-option precedence, unchanged legacy static index assignment, the numeric example are inspectable in the owning code or reproducible with CLI probes, but are not each covered by an independent `-U` regression in this inventory. High-color destination values and reuse have their own [behavioral coverage](high-color/README.md#test-coverage). Multi-input/animation reuse and cross-frame delta interactions also lack an exhaustive output-space matrix here. OC-29 through OC-55 exercise the actual CLI against scripted PTY replies for the selected libpng RGB16 route. P3 pixels use the existing independent wire oracle; gamma fallback/routing compares complete SIXEL frame bytes with an explicit gamma control, with terminal cleanup sequences checked separately. These scripted peers do not establish support in arbitrary terminal products or measure a physical display. C1/C2 transforms remain unimplemented. No image-quality threshold or terminal-compatibility result is inferred from the exact palette checks.

### Unsnapped linear and SMPTE-C native output

The two-color fixtures preserve one extended and one fractional sample in all five typed spaces. Native singleton centers are checked against independently stored binary32 source values with absolute tolerance `2e-5`; wire codes come from Decimal transfer/matrix equations in `tools/generate_output_native_fixtures.py`, with a rounding-boundary margin exceeding `0.02` percentage units for linear/SMPTE-C. The SMPTE-C oracle evaluates the existing option matrix as its contract; it does not independently calibrate that matrix. Palette order may vary between solvers. The checks match each working entry to its source and verify the corresponding cache and emitted definition. These tiny no-dither images establish numeric preparation, not spatial-diffusion quality. Export comparisons establish consistency across output choices.
