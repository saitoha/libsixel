# Output Color Space

`img2sixel -U` selects the RGB representation of the palette written to a SIXEL stream. Palette export with `-M` has its own sRGB interchange boundary. For normal terminal display, leave `-U` at its default, `gamma`. Use another output space only when the consumer's interpretation of those numbers is known.

```text
-U COLORSPACE
--output-colorspace=COLORSPACE
```

| Value | Output representation | Intended use |
| --- | --- | --- |
| `gamma` | Gamma-encoded sRGB channels. | Default output for consumers expecting ordinary RGB code values. |
| `linear` | Linear-light RGB with the sRGB primary basis. | A consumer explicitly configured to interpret linear-light channel values. |
| `smpte-c` | libsixel's SMPTE-C primary conversion and gamma encoding. | A consumer expecting that specific RGB representation. |
| `display-p3` | Standard Display P3 primaries, D65 white and sRGB transfer encoding. | The [limited CPU float path](#display-p3-selected-cpu-float-path) and a receiver explicitly configured for P3 input. |
| `auto[:timeout_ms=N]` | CLI negotiation resolves to gamma sRGB or standard Display P3. | Only images sent directly to stdout as a TTY; other destinations retain gamma sRGB. |

The parser also accepts `smptec` as an alias for `smpte-c`, folds letter case, and uses the shared [choice prefix-matching policy](../../cli/prefix-matching.md). Full names are preferable in durable commands. A repeated `-U` replaces the earlier value. `oklab`, `cielab`, and `din99d` are working/clustering choices, not accepted output choices. `-U` takes a required name, not a numeric gamma exponent or an ICC profile path.

`-U` and `-_` are not generally mutually exclusive. The selected Display P3 path rejects active snap, including when CLI negotiation selects P3; gamma, linear and SMPTE-C remain compatible with snap. The [snap/output boundary](../palette-construction/snap-policy/README.md#output-conversion-and-the-display-p3-boundary) explains why an earlier sRGB snap does not establish a P3 grid guarantee.

## Where the conversion happens

For the legacy `gamma`, `linear` and `smpte-c` palette paths, the relevant data flow is:

```text
Loaded image with a known color interpretation
    |
    +--> Palette construction in -X --> Palette in -W
    |                                       |
    +--> Image pixels in -W -----------------+
                                            |
                                  Lookup and dithering
                                            |
                               Pixel indices + working palette
                                            |
                               Convert a palette copy to -U
                                            |
                               Optional exact-snap finalization
                                            |
                         SIXEL color definitions
```

`-X` controls the geometry used to construct a palette. `-W` controls the geometry used to choose a palette index and propagate dither error. In these legacy paths, `-U` converts the resulting palette for output; it does not rerun either operation. Changing only `-U` can therefore change the displayed colors while retaining the index assignments for a static image. The selected native float paths cache a separate serialized palette before lookup without changing its working coordinates, as described below.

Unlike the implicit coupling from an explicit `-W` to an unspecified `-X`, `-U` does not change either earlier choice. For example:

```sh
img2sixel -Xgamma -Woklab -Ugamma image.png
```

This builds the palette in gamma coordinates, applies it in Oklab, and writes gamma RGB output. Keeping `-Ugamma` does not cancel the effect of `-Woklab`. Conversely, `-Ulinear` alone does not make lookup, dithering, resize, or alpha compositing operate in linear light. Those stages have their own controls; see [Working color space](../palette-application/working-colorspace/README.md), [Crop and resize](../preprocessing/crop-resize/README.md), and [Alpha policy](../../loader/alpha-policy/README.md).

## Legacy representations

### `gamma`: sRGB encoding

The name `gamma` denotes libsixel's sRGB transfer curve, including its linear segment near black. It is not simply a power of `1/2.2`. For a normalized linear-light channel `l` in `[0, 1]`, the corresponding sRGB channel `g` is:

```text
g = 12.92 * l                       when l <= 0.0031308
g = 1.055 * l^(1 / 2.4) - 0.055    otherwise
```

The inverse is:

```text
l = g / 12.92                      when g <= 0.04045
l = ((g + 0.055) / 1.055)^2.4      otherwise
```

The [W3C sRGB definition](https://www.w3.org/TR/css-color-4/#predefined-sRGB) describes the primary basis, D65 white point, and transfer function. libsixel's conversion implementation is in [`src/colorspace.c`](../../../src/colorspace.c), with typed float paths and byte lookup-table paths.

### `linear`: linear-light sRGB

`linear` uses the same RGB basis without the sRGB transfer encoding. A gamma channel near `0.5` corresponds to only about `0.214` in linear light. Thus an output palette can change from roughly `50%` to `21%` without intending to change the physical color: the recipient must apply the matching interpretation.

If a receiver instead treats that linear `21%` as an ordinary sRGB code value, the result is much darker. This follows from applying the sRGB decoding curve to a number that was already linear. It is an interpretation mismatch, not evidence that the encoder chose a worse palette.

### `smpte-c`: primary conversion and a power curve

Output conversion first converts the working color to linear sRGB and applies the fixed `sixel_linear_srgb_to_smptec_matrix` in [`src/colorspace.c`](../../../src/colorspace.c), followed by a power `1/2.2` encoding. The legacy converter bounds intermediate values; the selected native float path preserves signed extended values through the matrix and transfer function and clamps only the wire copy immediately before RGB101 rounding. The legacy inverse uses the power `2.2` and the inverse primary-conversion matrix.

Consequently, `-Usmpte-c` can change channel balance as well as tone response. It is not an alternative spelling for `gamma`, a generic CRT correction, an HDR mode, or a destination ICC transform. The fixed matrix and curve describe libsixel's implementation; this option does not measure or calibrate a monitor, or establish that a particular DEC terminal expects these values.

## `display-p3`: selected CPU float path

The selected P3 path supports opaque static RGB input, automatic or explicit float precision, independent clustering and working coordinates chosen from gamma, linear, Oklab, CIELAB and DIN99d, CPU K-means, K-center, K-medoids or Heckbert (including the existing `auto` resolver) with any sampling policy and the solver-specific binning choices below, `none`, `certlut`, `5bit`, `6bit`, `auto`, `vptree`, `rbc`, `mahalanobis`, `eytzinger` or `fhedt` lookup, and no dithering or CPU spatial error diffusion (`fs`, `atkinson`, `jajuni`, `stucki`, `burkes`, `sierra:variant=1`, `sierra:variant=2`, `sierra:variant=3`, or `lso2`), or [CPU positional dithering](../palette-application/dithering/README.md#positional-candidate-precision) (`a_dither`, `x_dither`, `bluenoise`). `auto` retains the existing palette-count selection of Atkinson or FS. Ward merge and [explicit soft or hard cover](../palette-construction/cover-policy/README.md#hard-mode-on-native-float-palettes) are supported; implicit active cover and active snap are excluded. A zero snap approach rate is an identity and selects the same path as `-_none`. It emits normal RGB SIXEL, or retains the palette-free foreground mask selected by `-e`. K-means feedback is disabled. The selected path also accepts [built-in `-b` tables](../palette-construction/fixed-palettes.md#native-float-application-and-display-p3) and fixed palettes through `-m` with all four admitted solver families and AUTO; their interpretation and image-map construction are specified in [External palette input and output](../palette-construction/external-palettes.md#display-p3-output). Other combinations fail before SIXEL output starts. `-M` exports sRGB8 rather than unmarked P3 values, clipping colors outside sRGB. Interframe dithering, GPU, high-color, HLS, DRCS, macros, delta encoding, animation and alpha-bearing frames are outside this selected path.

The default palette type and explicit `-tauto` resolve to RGB before capability validation, including the direct frame API; `-trgb` is not required. An explicit `-thls` remains unsupported on this selected path. This is an implementation boundary, not an inherent limitation of Display P3: HLS output would require its own connected serialization/rounding path and an agreed receiver interpretation of the reconstructed RGB values.

The selected loader integration tests use libpng P3 ICC RGB8/RGB16, an untagged sRGB RGB8 PNG, and a static RGB16 TIFF with orientation 6. They explicitly select builtin CMS, canonical linear output and `prefer_8bit=0`. These tests do not establish wide-gamut support for every loader, source domain, resizing filter or optional backend. The accepted opaque frame storage forms are RGB888 and the five typed three-component float32 formats. The selected encoder path converts source samples into the requested `-X` coordinates before palette construction.

```sh
./converters/img2sixel --threads=1 \
  -L 'libpng:cms_engine=builtin:cms_target=linear:prefer_8bit=0!' \
  -j scalar:resize_precision=float --precision=auto \
  -Q kmeans:seed=1 -X linear -W gamma -U display-p3 \
  --sampling-policy=full-frame --binning-policy=none \
  -F none -a off -_ none '-~none' -d fs -t rgb \
  tests/data/color-numeric/png-p3-16-rgb.png > output.six
```

The frame retains its typed coordinates. In gamma or linear sRGB coordinates, negative and above-one components preserve P3 colors; Oklab, CIELAB and DIN99d retain their corresponding extended coordinates. The output definition is a separate job policy. All four admitted solver families retain extended values through candidate construction and float palette export. A failure in the selected float solver is reported; it cannot silently retry a byte solver or a different solver. The opt-in is scoped to the palette build attempt, so subsequent legacy and extended builds retain their respective contracts.

Before index selection, the palette owner prepares a separate RGB101 serialization cache: it converts the canonical palette to P3, clamps only that output copy to the destination gamut, and rounds each channel to an integer in `0..100`. Both the authoritative float working palette and its compatibility byte view remain unchanged. Lookup and diffusion consume the original working coordinates. The writer consumes the cached codes without another color transform or byte round trip; palette compaction, reordering and cache reuse are disabled in this path. Early preparation of wire codes does not enable [palette snapping](../palette-construction/snap-policy/README.md); this selected path requires disabled snapping (`-_none` or a zero approach rate).

For example, linear gray centers `0.1` and `0.11` produce P3 code values `35%` and `37%`. With snap disabled, a query of `0.106` still selects the second original center. Substituting the inverse-decoded wire colors would move the decision boundary above `0.106` and incorrectly select the first center. The direct palette tests protect unchanged float and byte working views and unchanged lookup results. Primary and intermediate-color wire tests independently protect the destination conversion.

P3 requires an effective float working format even for `-Wgamma` and an explicit `--precision=8bit` preference. The byte preference does not override precision required by color conversion. Requested precision stays separate from this output requirement, so leaving P3 restores the effective format required by the remaining precision and working-space settings. An explicit float request remains float after leaving P3; automatic gamma working coordinates return to the ordinary byte preference.

Gamma working coordinates use the existing sRGB transfer function with sign-preserving extended values. FS computes its error against the unrounded working palette. [Dither clamp policy](../palette-application/clamp-policy.md) controls feedback while retaining original extended coordinates; `-0none` propagates the unrestricted residual. For example, errors `(0.125, -0.125, 0.0625)` sent to a following source `(1, -0.03125, 0.125)` with the FS right-neighbor weight `7/16` produce `(1.0546875, -0.0859375, 0.15234375)` before that next lookup. The direct test observes this input to the real lookup. The CLI two-color test checks independently derived source-group means, paint-time wire agreement with a raster FS reference calculation, and actual FS dispatch. Its painted result is also unchanged when error propagation is omitted, so detecting missing propagation or an intermediate clamp belongs to the direct next-lookup test and its code mutations. The other few-color CLI witnesses can optimize FS away because every source color fits in the palette; they establish option acceptance and wire values, not error diffusion. Nonfinite working samples or errors fail instead of entering lookup, and a later valid apply on the same policy recovers. The same feedback policy applies to ordinary output; it is independent of the output primaries.

Repeated `-U` settings replace the output definition. Reusing one encoder and output object for P3, gamma and P3 again restores the corresponding behavior on each job. The private precision opt-in is scoped to one palette-generation call and does not change the installed component request structures.

Ward merge retains the same nominal channel scales and `channel_l` weights as the existing merge path, while preserving signed, above-range and fractional centers. K-means counts actual retained coordinates when deciding whether merge is necessary; byte projection cannot collapse distinct float colors for that decision. K-medoids expands candidate-bin addresses independently of its Ward metric. K-means also preserves signed sums during empty-cluster repair and post-merge Lloyd refinement. See [Final palette merge policy](../palette-construction/merge-policy/README.md#float-coordinate-preservation) for the numeric contract and tests.

## Selected ordinary sRGB float path

The same extended-palette/RGB101 preparation is selected for `-Ugamma`, `-Ulinear` and `-Usmpte-c` when a static opaque RGB job requires float through the source, an image map or explicit float precision, and the options match one of the four CPU solver families described above: any of the five clustering/working spaces, any sampling policy, the supported binning choices below and lookup policies above, none, the CPU spatial diffusion methods listed above (including `auto`), or the three positional methods, none or Ward merge, off or explicitly selected soft/hard cover, and disabled snap. It does not promote a job with byte-eligible source/map data and operations merely to select this algorithm. A float image map can require float palette application while the source image plan remains RGB888. Other settings retain their existing path. All four admitted solver families and AUTO also accept ordinary sRGB mapfile jobs under the same frame/precision conditions, as described in [selected float mapfile application](../palette-construction/external-palettes.md#selected-ordinary-srgb-output). The P3 and selected sRGB image-map builders both use the extended path. [Built-in `-b` tables](../palette-construction/fixed-palettes.md#native-float-application-and-display-p3) also retain an authoritative float working view under these frame/precision conditions while bypassing construction and cover. The separate [monochrome foreground-mask path](../palette-construction/fixed-palettes.md#native-monochrome-application) uses the same typed endpoint preparation without sending RGB definitions.

These legacy output definitions share the same native construction and application whether snap is disabled or active at its supported final stage. Changing only `-U` changes the wire conversion, while the working palette and sRGB8 `-M` export remain output-independent. Linear and SMPTE-C receivers must interpret the transmitted components accordingly. Byte-eligible jobs keep their existing output conversion; selecting either output alone does not promote the source.

Palette generation retains extended coordinates. A separate destination copy is clamped and rounded to RGB101 once; preparing it does not change the working palette used for lookup and error diffusion. The writer emits the stored codes directly. Source color interpretation, working coordinates and destination RGB definition remain separate decisions. The `dither_contract` trace reports `rgb101=1` for this path and `rgb101=0` for legacy palette finalization.

For gamma, linear and SMPTE-C output, [native final snap](../palette-construction/snap-policy/README.md#native-float-final-snap-for-srgb-output) is also supported for generated palettes with `timing=once` and cover off or explicit soft/hard cover. The P3 active-snap restriction is unchanged.

The selected lookup classes consume the authoritative float palette even when its byte projection happens to be black and white. The default `certlut` and explicit `auto` (resolved to `6bit`) remain distinct choices. Their distance geometry and focused integration tests are owned by [Lookup policy](../palette-application/lookup-policy/README.md#extended-float-coordinates).

### Sampling and retained precision

For generated palettes, the selected float path accepts all three sampling policies. `full-frame` builds from the preprocessed frame. `adaptive-grid` copies selected loaded-frame pixels before preprocessing and retains their typed float coordinates, including negative and above-one components. This copy does not normalize or clamp samples. The existing solid-region augmentation applies to byte RGB/RGBA input; it is not applied to typed float samples. `auto` retains the resource-aware choice described in the [execution map](../execution-map/README.md).

Whether an adaptive palette is built synchronously or on a worker, an already-float source remains float even when base precision is `auto` or `8bit`. A byte-eligible gamma job retains its byte path. Thread-creation failure rebuilds from the same owned sample synchronously. Other worker failures fall back to the preprocessed full frame only for `auto`; an explicitly requested adaptive policy reports the error without starting SIXEL output. The fallback rebuild retains the same precision and separate RGB101 output boundary. Automatic fallback may change the palette because its sample source changes; it does not promise identical colors to adaptive sampling.

The direct sampling tests check exact membership after cropping and bit-preserving copies in each of the five float formats. Whole-encoder tests check independently derived centroids and RGB101 values across synchronous and worker execution, automatic selection, retained source precision and injected failures. These tiny fixtures exercise palette construction and output, not meaningful error diffusion; the spatial tests below and external multi-image comparisons cover that separately.

### Binning and extended coordinates

For K-means, the selected float path accepts `none`, `exact`, `hard`, `soft` and `auto` binning. `exact` combines identical coordinates with their multiplicities. `hard` and `soft` retain source coordinates in their weighted sums; only their bin addresses use a normalized grid. For each axis, the addressing interval starts at the nominal bounds of its typed color space and expands to include finite sample extrema when necessary. Thus distinct out-of-range colors can occupy different cells instead of all saturating into an edge cell. Inputs contained in the nominal interval retain the established grid. Soft binning retains the existing fractional trilinear weights.

This interval extension changes neither the requested grid depth and mapping curve nor the clustering coordinates, distance metric, convergence scale or compatibility byte projection. It does not guarantee distinct cells for every distinct source color: finite-resolution binning can still merge nearby colors, and a distant outlier can make cells coarser. `auto` retains its existing resolution to hard binning for K-means. This is separate from the proposed [adaptive hard-binning depth design](../palette-construction/clustering-colorspace/README.md#adaptive-hard-binning-design).

The binning tests independently check unequal-population means in all five typed spaces, separated colors outside both ends of each nominal axis, and ordinary sRGB/P3 wire values. Edge tests use a controlled PCA initializer to avoid treating stochastic K-means convergence as a bin-address guarantee. A nominal gamma fixture compares the legacy and extended builders; invalid-input cases check rejection followed by valid reuse, without promising identical error codes between binning implementations. These small fixtures are arithmetic and state tests, not image-quality evidence.

### Heckbert representatives

`-Qheckbert` and `auto` resolved to Heckbert use the selected float path. Its native histogram preserves finite input coordinates and exact occurrence counts; lookup grid depth does not quantize that histogram. All split, representative and profile choices remain available, as described in [Native float Heckbert](../palette-construction/quantization/README.md#native-float-heckbert). Top-level binning is `none` (`auto` resolves to `none`); unsupported binning remains an error. Omitted/auto/none binning resolves `-Qauto` to Heckbert; exact/hard/soft binning resolves it to K-means and uses that solver's admitted native path. The requested policy stays automatic and is resolved per frame. The byte-eligible histogram path is unchanged.

### K-center and K-medoids representatives

The selected path also accepts `-Qcenter` and `-Qmedoids`. This includes K-center's `auto`, `fft`, `swap` and `hybrid` modes, and K-medoids' `auto`, `pam`, `sample` (CLARA), `random` (CLARANS) and `bandit` (BanditPAM) modes. Their objectives and search budgets remain those of the [quantization algorithms](../palette-construction/quantization/README.md).

| Solver | Top-level binning on the selected path | Retained coordinates |
| --- | --- | --- |
| K-means | `none`, `exact`, `hard`, `soft`; `auto` resolves to hard. | Weighted native coordinates and generated centers. |
| K-center | `none`, `exact`, `hard`; `auto` resolves to hard. | Source coordinates or weighted bin means, transformed by the existing fixed per-axis scales for solver geometry and restored for float export. |
| K-medoids | `none`; `auto` resolves to none. | Observed native source representatives selected through the existing private candidate histogram. This histogram remains active even without a shared binning artifact. |

K-center's shared hard-bin addresses and K-medoids' private candidate-bin addresses expand their nominal intervals to include finite sample extrema, using the same addressing rule as K-means. The coordinates used for distance calculations are not rescaled to those expanded bounds. K-center retains its established byte-scaled double geometry, including opponent-axis scales; K-medoids retains native double coordinates. This change preserves extended samples without redefining either solver's metric. K-center bounds candidate-stratum indices before unsigned conversion even for extreme finite coordinates; this does not clamp the color itself. The compatibility byte palette remains bounded, but it is not used to reconstruct the authoritative float palette on this path.

A K-center hard-bin representative is the population mean of its cell; it need not be an observed source color. K-medoids instead chooses an observed source sample nearest its private bin mean before discrete optimization. Their representative tests deliberately distinguish those contracts. Separate reduced-color tests exercise selection when the requested palette is smaller than the candidate set. Wire tests cover each clustering space, mixed clustering/working choices, synchronous and worker execution, ordinary sRGB and Display P3. Byte-eligible gamma jobs still use the existing byte path. Implicit active cover and earlier snap timing remain outside the selected path, as do the additional binning choices not listed for each solver. Final snap follows the ordinary-output scope above; P3 plus active snap remains unsupported.

The solver value fixtures use binary-exact inputs in `[-4, 4]` and compare native components with an absolute tolerance of `2e-6` (about four binary32 ULPs at magnitude four), covering nominal scale/offset round trips and final float storage. The one-bin mean and observed-representative witnesses use `5e-7`. These budgets remain much smaller than either byte projection or clipping errors. The large finite pruning fixture checks membership on its exact power-of-two source grid and retains an independent tolerance on the small opponent components. P3 primary wire checks reuse the [independent P3 red coordinates](../../../tests/data/color-numeric/p3-palette.h). The endpoint code values `(100, 0, 0)` have a `0.005` encoded-channel margin to the next RGB101 rounding boundary; exact wire comparisons do not require bit-identical intermediate transforms. No perceptual metric substitutes for these value assertions.

### Spatial diffusion and the working palette

Each admitted spatial kernel consumes the authoritative, unrounded float working palette. Its residual is computed against those coordinates, including canonical negative or above-one values for P3. No byte palette round trip is inserted. Keeping a separate output cache changes neither the lookup/error reference nor the kernel weights or clamp policy. The Stucki and Sierra-2 names retain the [documented libsixel coefficient variants](../palette-application/dithering/README.md); LSO2 retains its error-dependent coefficient table. `auto` retains the completed-palette-count rule, with the existing exact-color optimization still able to disable unnecessary diffusion.

The whole-encoder tests independently fix the extended source centroid and final wire values for each method, both output definitions and the gamma/linear working transfers. The K-means color-space matrix tests separately cover all 25 `-X`/`-W` combinations with both outputs, independent native-space centroids and immutable lookup palettes. Separate two-pixel kernel tests fix the next lookup value from a nonzero residual against the unrounded working palette. The perceptual-space residual tests cover all nine admitted kernels, including LSO2's lightness-only propagation. These tests cover horizontal propagation; existing [clamp tests](../palette-application/clamp-policy.md#test-coverage) cover limiting, FS vertical/serpentine taps and parallel overlap separately. This is not exhaustive stencil, animation, low-color quality or parallel-boundary coverage for every kernel.

## SIXEL syntax and receiver interpretation

With `-t rgb`, a palette definition has this form:

```text
# index ; 2 ; red ; green ; blue
```

Each RGB component is an integer percentage in `0..100`. The `2` selects the RGB form of the color definition. It does not identify sRGB, linear RGB, SMPTE-C, Display P3, a transfer curve, or a display profile. SIXEL provides no ICC payload or output-space tag for the receiver to recover the `-U` setting. See [SIXEL color registers](../../sixel-format/README.md#graphics-color-introducer).

`-t hls` instead serializes the converted output RGB triplet as DEC HLS coordinates. It changes the syntax of the color definition; it does not make `-U` an HLS working-space selector or add color-management metadata.

Display behavior therefore depends on the receiving terminal and display stack. A browser preview or a decoded PNG that treats all three streams as ordinary RGB does not show three correctly color-managed renditions. For a meaningful comparison of alternative output spaces, the consumer must know the chosen space outside the SIXEL stream.

### Negotiation through the proposed color protocol

The [Terminal graphics color management proposal](../../protocols/graphics-color-management.md) defines a receiver-independent agreement for these RGB numbers. It separates an explicit sRGB policy from a reported device-input definition, provides DECRQSS save/restore for each target's policy, and specifies dedicated color-definition queries. Protocol support must be established by the session's replies; a P3-capable display alone does not establish the receiver's input interpretation.

For ordinary SIXEL, a controller using this proposal can display the selected `-Udisplay-p3` output with the following transaction. `CSI`, `DCS`, and `ST` denote the control bytes defined in the proposal, and `M` is the exact saved policy.

| Step | Exchange or action |
| --- | --- |
| Discover target 1 | Send `CSI ?1./r`; require a complete valid reply with `A=1`, `S2=1`, and `C=4`. For example, `DCS 1;1;1;1;4./r ST` also advertises expansion support. |
| Save policy | Send `DCS $q1./p ST`; save `M` from `DCS 1$r1;M./p ST`, preserving `0` versus `1`. |
| Select device input | Send `CSI 1;2./p`; query again and require policy `2`. |
| Display | Send the bytes generated with `-Udisplay-p3`; new RGB definitions are interpreted as standard Display P3. |
| Restore | Send `CSI 1;M./p`; verify the saved value, including on recoverable errors. |

For a color-preserving sRGB comparison, generate `-Ugamma` output and set and verify policy `1`. Feeding gamma sRGB values under a P3 device policy reinterprets those values in the wider basis; it does not establish correct sRGB rendering. Policy `3` explicitly requests the proposal's component expansion and serves a different purpose from source-to-destination color conversion.

Explicit `img2sixel -Udisplay-p3` and `-Ugamma` perform none of these color-protocol exchanges. The CLI-only `-Uauto` manages discovery and the transaction above, accepting the named sRGB and Display P3 definitions. An available target with an unsupported definition uses verified policy `1` and gamma output; P3 requires both `C=4` and `S2=1`. A final automatic request cannot be combined with DRCS (`-@`): the implemented transaction is for ordinary SIXEL (`T=1`), while DRCS uses a separate `T=2` policy. This combination fails before any color query or image output, regardless of the eventual advertised definition. A later explicit `-Ugamma` clears auto and retains the existing DRCS behavior. Neither the library `setopt` API nor bindings accept `auto`.

The reply parser enforces the proposal's [numeric field and simple-RGB rules](../../protocols/graphics-color-management.md#simple-rgb-definition), including rejection of the reserved saturation value `9999`. A simple definition has eight to ten fields: the five common fields, three mandatory base-9999 gamma limbs, and optional primaries/white identifiers. It remains an unsupported transform and therefore uses verified sRGB fallback only after its syntax and reconstructed gamma range pass validation. The five-field named sRGB/P3 replies and their negotiation steps above are unchanged.

The automatic route is limited to images sent to stdout as a TTY, with no `-o` option or with every `-o` argument exactly `-`. Any other outfile argument excludes negotiation, including `-o file -o -`, whose actual output remains a file under the existing outfile semantics. File/pipe destinations keep the interchange default, gamma sRGB, regardless of a terminal attached to stderr. An explicit `-Udisplay-p3` remains a user-selected representation even when saving a file; it requires a consumer that knows how to interpret that file.

During the POSIX query phases, the CLI temporarily disables the terminal's suspend character so a protocol SUB byte reaches the reply parser without suspending the process or flushing input. A keyboard suspend key, normally Ctrl-Z, consequently becomes protocol input during those phases. Each request/reply exchange shares one deadline across its request write and reply reads; a separate control write has its own deadline. Each deadline can be configured up to ten seconds, and a phase containing multiple exchanges has no combined ten-second limit. The original suspend character and other terminal settings are restored before synchronous encoding and during cleanup. Signal handling remains enabled, and SIGINT or SIGTERM can cancel the exchange.

The transport blocks SIGINT and SIGTERM while checking cancellation, then uses `pselect` to restore the caller's signal mask atomically with the I/O wait. A cancellation signal enabled by that mask therefore cannot be lost between the check and the wait, even when output is blocked. Every return restores the caller's mask, and unrelated signals remain enabled according to that mask. Both build systems require this `pselect` surface through the shared terminal-I/O capability probe.

The default remains `-Ugamma`. `SIXEL_OUTPUT_COLORSPACE` supplies a CLI default using the same case folding, unambiguous prefixes and named choices; it takes only a base name, without suboptions. An explicit `-U` overrides that environment value, and the last `-U` replaces the whole earlier request. Empty environment values are unset. `-Uauto:timeout_ms=N` and compact `-Uauto:TN` set a decimal deadline in `1..10000` milliseconds, overriding `SIXEL_OUTPUT_COLORSPACE_AUTO_TIMEOUT_MS`; the default is 200 ms. The timeout environment is relevant only to a final automatic request, and an explicit timeout overrides even an invalid environment timeout. These CLI settings also work through `--env NAME=VALUE` without outranking explicit options.

Only a completely silent first capability exchange, a valid unavailable reply, or unavailable local TTY access allows unconfirmed legacy gamma output. This does not prove that the receiver currently interprets RGB as sRGB. A partial or malformed response fails before sending an image. After a timeout or loss of reply correlation, no later query is issued on that job/TTY; saved policy restoration is write-only and bounded. An available target whose policy cannot be saved or verified receives no image. Normal restoration is queried and verified, and restoration or terminal-settings failure cannot produce a successful exit.

Capability may be reused within one invocation, but each image's current policy is saved and restored separately. The CLI releases its reader and terminal settings before synchronous encoding, allowing the existing library OSC11/CPR handling to retain its own lifecycle. Encoding conditions remain those of the selected P3 path: an incompatible input or option can fail after the policy was selected. The CLI preserves that error and restores the original policy without rereading the input or retrying gamma encoding. When a failed control write or encode may leave SIXEL/control framing unfinished, bounded CAN/ST precedes recovery. SIGINT/SIGTERM observed during negotiation, encoding or restoration stops subsequent inputs.

## Precision, rounding, and cost

The legacy output encoder converts a private palette copy and preserves the reusable dither palette in working coordinates. When a usable float32 palette is available, it converts those typed values before packing bytes. Otherwise it converts the byte palette. The selected P3 and ordinary sRGB float paths prepare only a separate RGB101 wire cache before lookup; the working palette is not replaced. Increasing working precision can reduce conversion rounding, but it cannot increase the precision of SIXEL's integer percentage fields.

For RGB definitions, the byte path rounds a channel `b` with integer arithmetic:

```text
percentage = (b * 100 + 127) / 255
```

The float path rounds a clamped normalized channel directly with `floor(channel * 100 + 0.5)`. An exported 8-bit palette and a decoded SIXEL palette can therefore differ through their respective byte and percentage quantization steps. They are not generally byte-identical merely because both use the same `-U` value.

In legacy palette paths, generated palettes with exact [snap policy](../palette-construction/snap-policy/README.md) enabled at `rate=1` receive output finalization that follows the `-U` conversion and puts the palette onto the reversible RGB percentage grid. The native final-snap path instead retains the snapped working palette and converts only its wire copy directly to RGB101. Both cases include SMPTE-C output. It prevents the conversion from leaving the final palette off that grid; it does not remove clipping or make every earlier color conversion lossless.

For `K` palette entries, this conversion is `O(K)` work and uses `O(K)` palette storage, rather than converting all `N` image pixels again. `-U` alone does not request a float32 image buffer. This cost model applies to the ordinary palette path; it is not a measured whole-program speed comparison. Different numeric color definitions can change serialized byte length even when index assignment is unchanged.

## Fixed palettes and palette export

`-M` always exports sRGB8 in ACT, JASC PAL, RIFF PAL and GPL. This applies to every `-U` choice, including the selected Display P3 path. It converts the prepared working palette before wire-specific conversion and final rounding. See [External palette input and output](../palette-construction/external-palettes.md#exporting-a-palette-with-m) for the interchange contract and its wide-gamut limitation.

The preparation of fixed palettes also matters:

| Palette source | Current preparation and output boundary |
| --- | --- |
| Generated palette | Constructed in `-X` and prepared for `-W`. The selected native float paths finalize RGB101 before application; other paths convert to `-U` afterward. |
| Image mapfile, such as `-m swatches.png` | Loaded as an image and prepared in the selected working representation before output conversion. Loader/CMS settings can affect its colors. |
| Structured ACT/PAL/GPL input or built-in `-b` palette | sRGB8 entries are converted to `-W` once. The selected native path retains float coordinates even for gamma work; genuinely byte-eligible gamma jobs keep their byte view. Entries are never interpreted as native working-space bytes. |
| Monochrome `-e` | Uses assumed sRGB black/white endpoints for mapping, with a native working view on the selected float path. It emits a foreground mask with no RGB definitions; `-U` cannot set the receiver foreground. See [native monochrome application](../palette-construction/fixed-palettes.md#native-monochrome-application). |

Fixed palettes bypass generated-palette snap processing. Structured-file and built-in entries retain their sRGB interpretation under `-Wlinear`; image mapfiles still pass through their separate image-loader and palette-construction route.

## Reproducible numeric example

Run the following from the repository root, using the converter built in that checkout. It supplies a two-entry byte palette with `-Wgamma`, so quantizer choices do not obscure the output conversion:

```sh
./converters/img2sixel --threads=1 --gpu-policy=off --diffusion=none \
  -Wgamma -Ulinear -t rgb -m pal:- -M pal:- -o /dev/null \
  tests/data/inputs/snake_16.png <<'PAL'
JASC-PAL
0100
2
128 64 32
0 0 0
PAL
```

The exported first entry is `128 64 32`; the black entry stays `0 0 0`. Replacing only `-Ulinear` gives:

| Output option | First entry in the exported PAL | First SIXEL RGB definition |
| --- | --- | --- |
| `-Ugamma` | `128 64 32` | `#0;2;50;25;13` |
| `-Ulinear` | `128 64 32` | `#0;2;22;5;2` |
| `-Usmpte-c` | `128 64 32` | `#0;2;51;25;15` |

To inspect the wire definitions, replace `-M pal:- -o /dev/null` with `-o output.six` and inspect that file. The table describes the byte-palette path with snap bypassed; it is not an expected-value table for arbitrary generated or float32 palettes. Its purpose is to show separately the RGB conversion, 8-bit export, and percentage serialization boundaries.

## Scope and current gaps

The conversion described here belongs to `sixel_encode_dither`, including ordinary generated and supplied palette output. An option being accepted does not establish that every alternate encoder consumes it.

The current `-I` [high-color path](high-color/README.md) dispatches to `sixel_encode_highcolor`, which normalizes pixel format and emits changing palette registers without the legacy `source_colorspace` to output `colorspace` conversion above. Changing only a legacy `-U` choice currently does not provide the requested output-space conversion on that path. This is an implementation gap. The P3 path explicitly rejects high-color output.

Likewise, `-U` does not configure decoder interpretation, embed an output ICC profile, change loader CMS, or replace the [PNG writer's snapshot policy](../../writers/png/README.md). The static-image stage explanation should not be extended to [delta encoding](delta-encoding.md) without accounting for its retained display-color state across frames.

### Defensive and malformed-input tests

The [automatic CLI cases](../../../tests/cli/color/session) also reject malformed timeout numbers and keys. The controller boundary cases in the same category compile the actual controller with isolated dependency calls, deterministically cancelling during restoration writes or final terminal release while preserving original encoder errors and preventing another image. The [TTY transport tests](../../../tests/cli/color/tty) separately cover absolute deadlines, backpressure, framing, stale bytes, identity/foreground changes and exact state restoration.

### Coverage audit boundary

The first five tests assert exact exported entries. OC-06 checks the output grid and export/wire agreement; it does not independently validate the SMPTE-C conversion matrix. OC-02 and OC-03 establish byte preservation for the named configurations, not perceptual correctness of all non-gamma fixed-palette combinations. OC-05 is not evidence that a CMS transform ran.

P3 values, lookup and reuse are directly covered by OC-07 through OC-28. General defaults, alias and case handling, invalid values, legacy repeated-option precedence, unchanged legacy static index assignment, the numeric example, and the high-color gap are inspectable in the owning code or reproducible with CLI probes, but are not each covered by an independent `-U` regression in this inventory. Multi-input/animation reuse and cross-frame delta interactions also lack an exhaustive output-space matrix here. OC-29 through OC-55 exercise the actual CLI against scripted PTY replies for the selected libpng RGB16 route. P3 pixels use the existing independent wire oracle; gamma fallback/routing compares complete SIXEL frame bytes with an explicit gamma control, with terminal cleanup sequences checked separately. These scripted peers do not establish support in arbitrary terminal products or measure a physical display. C1/C2 transforms remain unimplemented. No image-quality threshold or terminal-compatibility result is inferred from the exact palette checks.

### Unsnapped linear and SMPTE-C native output

The two-color fixtures preserve one extended and one fractional sample in all five typed spaces. Native singleton centers are checked against independently stored binary32 source values with absolute tolerance `2e-5`; wire codes come from Decimal transfer/matrix equations in `tools/generate_output_native_fixtures.py`, with a rounding-boundary margin exceeding `0.02` percentage units for linear/SMPTE-C. The SMPTE-C oracle evaluates the existing option matrix as its contract; it does not independently calibrate that matrix. Palette order may vary between solvers. The checks match each working entry to its source and verify the corresponding cache and emitted definition. These tiny no-dither images establish numeric preparation, not spatial-diffusion quality. Export comparisons establish consistency across output choices.
