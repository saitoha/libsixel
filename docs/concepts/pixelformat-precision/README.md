# Pixel-Format Precision

For backend representation, color/alpha preservation and byte-path eligibility, see the [loader precision policy](../../loader/precision-policy.md).

Pixel-format precision describes how a decoded or intermediate color sample is stored. It is distinct from the color space that gives the sample meaning, the number of colors in the final palette, and the number of palette indices used by a packed pixel format. In libsixel, the important encoder distinction is between three unsigned 8-bit channels (`rgb888`) and three float32 channels (`rgb-f32` or a color-space-specific float format).

This document explains the storage contract and the operations that can promote a nominally 8-bit pipeline to float32. The broader effect of `--precision-policy` on quantization, dithering, lookup, speed, and SIXEL size is measured in [Encoder working precision](../../encoder/precision/README.md). The interpretation of gamma, linear RGB, Oklab, CIELAB, DIN99d, and ICC profiles is defined in [Color spaces](../colorspace/README.md) and [Color management basics](../color-management/README.md).

## Storage and meaning are separate

`RGB888` stores red, green, and blue as integers from 0 through 255. It occupies three bytes per pixel, before stride, alignment, ownership metadata, and any concurrent buffers are counted. The name means 8 bits per channel, not 8 bits per complete pixel.

The float32 family stores three 32-bit floating-point channels and therefore occupies twelve bytes per pixel under the same simplifying assumptions. The format name also identifies the coordinates:

| Pixel format | Storage | Color-space interpretation |
| --- | --- | --- |
| `RGB888` | 3 x unsigned 8-bit | gamma-encoded sRGB |
| `RGBFLOAT32` (`rgb-f32` in planner diagnostics) | 3 x float32 | gamma-encoded sRGB |
| `LINEARRGBFLOAT32` (`linear-f32`) | 3 x float32 | linear-light sRGB primaries |
| `OKLABFLOAT32` (`oklab-f32`) | 3 x float32 | Oklab |
| `CIELABFLOAT32` (`cielab-f32`) | 3 x float32 | CIELAB |
| `DIN99DFLOAT32` (`din99d-f32`) | 3 x float32 | [DIN99d](../din99d/README.md), with all three native coordinates divided by 100 |

A float32 value is not automatically linear light, and an 8-bit triplet cannot be reinterpreted as Oklab merely by changing a label. Every conversion must know both the source and destination color spaces. Palette-index formats such as `PAL8` describe index storage rather than color-sample precision and belong to the separate [pixel-format and alpha contract](../pixelformat.md).

For a normalized encoded channel `x`, the byte boundary applies approximately

```text
q8(x) = round(255 * clamp(x, 0, 1)) / 255
```

so one crossing has at most `1 / 510` encoded-coordinate rounding error before clipping. The error is not uniform in linear light because the sRGB transfer curve is nonlinear. A normal float32 value carries 24 bits of significand precision, but this does not guarantee a 24-bit-accurate final color: transform approximations, clipping, palette reduction, 101-level SIXEL palette serialization, lookup, and dithering impose separate errors. The practical advantage is that intermediate transforms can retain far more information and avoid repeated byte quantization until a boundary that truly requires it.

## Storage precision and arithmetic precision

A float32 path describes the stored samples, not the required type of every intermediate expression. Color-space conversion can require `double` for matrix products, chromatic adaptation, transfer functions, and accumulation even when both input and output buffers are float32. Signed matrix terms can nearly cancel, and a sequence of nonlinear and inverse operations can magnify earlier rounding. A result that fits float32 does not establish that all intermediate float32 operations are accurate or even finite.

Widen the operands before the sensitive calculation. Assigning an already rounded or overflowing float expression to a double variable cannot recover its information. Likewise, promoting an image after an earlier byte conversion or gamut clamp cannot undo that loss. The internal `sixel_color_convert_rgbf32()` in [`src/colorspace.c`](../../../src/colorspace.c) loads float samples into double triplets, performs the coordinate conversion there, validates the result, and only then stores float samples. This does not imply double image buffers or that every CMS/SIMD backend uses identical arithmetic.

Keep coordinate conversion ahead of storage reduction. For example, linear `0.001` becomes encoded sRGB `0.01292`, which rounds to byte 3; rounding the linear value to an 8-bit index first produces zero, and a subsequent byte transfer lookup cannot recover it. An explicit frame setter request for `RGB888` now reads the original float coordinates into double triplets, converts directly to gamma sRGB, and clips and rounds only the final byte values. It does not require an intermediate gamma float32 allocation. Gamma float input already has the requested coordinates and bypasses a transfer roundtrip. The libpng and builtin PNG explicit 8-bit CMS targets perform their source interpretation and composition before reaching this boundary.

Widening also matters during the final byte rounding itself. The stored gamma float with bits `0x3b008080` is exactly `0.0019607841968536376953125`. Multiplying by 255 and adding 0.5 in double remains below 1 and produces byte 0. The same multiplication and addition in float round up to 1 and produce byte 1. A float image buffer therefore does not imply that its final rounding arithmetic should also use float.

The explicit float-to-byte setter publishes its new buffer and gamma tags only after every triplet succeeds. Allocation failure, nonfinite source samples, a coordinate-domain or double overflow failure, or invalid dimensions leave the original pixels, pointer, dimensions, tags, transparency mask, and ownership unchanged. Successful conversion releases owned source pixels once and leaves borrowed source storage untouched. A finite intermediate value may exceed `FLT_MAX` yet fit double and produce a valid bounded byte; such a value does not require float32 storage on this path. The private storage normalizer and byte resize API retain their separate contracts.

The independent [byte-boundary fixtures](../../../tests/data/color-numeric/frame-byte.json) start from exact stored IEEE binary32 bits. The generator solves the forward Oklab and legacy Lab matrices independently, evaluates inverse coordinate equations in Decimal, and computes final gamma/byte values without calling production transforms. Gamma and linear cases include the nearest float and its two adjacent values at all 255 half-byte boundaries, as well as dark, negative, above-one, and finite extreme inputs. The tests compare final bytes exactly through direct, interface, borrowed, owned, and cloned frames; failed conversions also preserve the full original state.

The fixture's `half_byte_distance` is the distance from `255 * clamp(gamma, 0, 1)` to the half-integer boundary in its byte interval, expressed in byte-code units. It is a rounding margin, not a tolerance for the preceding transform. The checked-in linear cases include a margin of approximately `2.2474e-9` byte-code units; the float-coordinate tests' `1e-6` tolerance therefore cannot be reused to justify these exact bytes. Gamma input `0.5` is an exactly representable tie: the explicit setter uses half-up rounding and expects byte 128. This rule is separate from the FPU's intermediate rounding mode. The fixture records margins and high-precision references, but does not supply a complete propagated error bound for each transform and supported math library. Exact fixture agreement is consequently not proof of correctly rounded output for every float input or every platform.

For IEEE binary32 and binary64, normal values have 24 and 53 significant binary digits, respectively. These are relative precisions: the spacing between representable numbers grows with their magnitude. A wider exponent range reduces overflow risk, while more significant digits reduce rounding error; neither property makes arbitrary arithmetic exact. Goldberg's [What Every Computer Scientist Should Know About Floating-Point Arithmetic](https://docs.oracle.com/cd/E19957-01/806-3568/ncg_goldberg.html) explains the distinction between representable range, rounding, and cancellation.

### Double does not eliminate cancellation

Let `M = 2^100`, which is exactly representable in both binary32 and binary64. With binary64 operations and ordinary round-to-nearest evaluation:

```text
exact arithmetic:   M + (1 - M) = 1
binary64:           1 - M rounds to -M; the final sum is 0
```

The problem is the difference in scale between `M` and `1`, not whether either input fits in storage. Converting the final zero to float32 cannot restore the lost one. In a color matrix or a weighted sum, a small component can similarly disappear between large positive and negative terms. Mathematically equivalent rearrangements therefore need not have equivalent numerical behavior.

Resampling is the weighted mean `sum(w_i * x_i) / sum(w_i)`. Rewriting it as `a + sum(w_i * (x_i - a)) / sum(w_i)` introduces an arbitrary reference value `a`; it is not a required neighboring-pixel difference operation. If a zero-weight extreme sample supplies `a`, this rearrangement can erase the sole contributing ordinary sample. Direct compensated accumulation, excluding zero-weight terms, and preserving one-contributor or constant identities address different failure modes. Symmetric filter weights also need symmetric evaluation: compensation for addition cannot repair coefficients that were already rounded differently. The implemented choices and their storage limits are in [Float geometry and failure state](#float-geometry-and-failure-state).

Underflow is a separate concern. Two contributions of half the smallest positive float32 subnormal can each round to zero even though their sum should be that subnormal. A SIMD recovery decision must account for this absolute rounding error as well as cancellation between normal values. Wider arithmetic and recovery checks also have a cost; measure ordinary images as well as extreme numerical specimens before adopting an implementation strategy.

### Numerical validation follows the operation

The [testing guide](../../testing/guide.md#intermediate-floating-point-error) owns the treatment of intermediate arithmetic, platform variation and quantization boundaries. This document's [coordinate](#behavioral-contract-tests) and [geometry](#float-geometry-contract-tests) inventories specify the current frame-test tolerances. Those limits apply to the listed vectors and stored coordinate units, not to every representable float32 value, every CMS backend, or final byte rounding. The `1 / 510` bound above describes one unclipped byte quantization step; it does not bound accumulated transform error.

Validate color conversion with independent expected coordinates in each direction, including mixed channels, transfer-curve boundaries, negative and above-one values, and mathematical-domain failures. A forward/reverse pair can share an error and still roundtrip successfully. Validate resampling with independent weights, zero-weight extremes, small residuals between opposite large contributions, constants, and subnormal inputs. Compare a small expected residual at its own scale; a tolerance scaled by the largest input can accept its complete loss. The [coordinate and geometry coverage](#test-coverage) separates these value contracts from image-quality thresholds and checks the executed SIMD or scalar path.

Numerical range checks and color-gamut decisions are separate. Keeping extended coordinates does not mean accepting NaN, infinity, undefined nonlinear operations, or a value that cannot fit the next storage representation. Conversely, clamping finite coordinates into `[0,1]` is not a numerical-accuracy repair. See [Out-of-gamut and imaginary colors](../colorspace/README.md#out-of-gamut-and-imaginary-colors) for the color meaning of those intermediates.

## Float conversion arithmetic

`sixel_helper_convert_colorspace()` and internal float-buffer conversion share the same extended arithmetic. Choosing a palette solver, snap timing or output representation does not select a bounded float converter. Gamma sRGB, linear sRGB, Oklab, CIELAB and DIN99d retain finite signed and above-one coordinates; the public storage converter also accepts SMPTE-C through the common output/inverse transform. Byte formats retain their LUT/SIMD implementations and explicit storage limits.

A nontrivial float conversion validates every result before publishing any original-buffer write. Parallel workers write disjoint scratch slices; serial conversion validates before its write pass. NaN, infinity, an undefined transform domain, an invalid color-space identifier or float32 overflow returns `SIXEL_BAD_INPUT` without changing samples. The size argument counts bytes and must contain complete three-component float pixels. Equal source and destination identifiers retain the established no-op behavior, including bit preservation without numerical validation. This arithmetic contract does not guarantee that a later palette operation retains its float view.

Float adapters accelerate the same arithmetic without changing result bits within a build and floating-point environment. A thread-safe, once-initialized 256-entry sRGB decode table is computed by the analytic transfer function from `(double)(float)(i / 255.0)`. A channel uses that table only when it exactly equals the promoted float grid; adjacent floats, off-grid 16-bit fractions, negative and extended values retain analytic decoding. Signed zero is preserved. Byte tables and the analytic single-triplet API keep their own arithmetic; no approximate cube-root table is used for float conversion.

Each execution slot processing at least 1024 float pixels may own a fixed 16384-entry direct-mapped memo (448 KiB with 32-bit fields). A pool worker holds its optional memo through all chunks of one conversion transaction; the controller owns a separate memo for its chunks. Initial and added workers receive a zero-initialized owner record through the thread-pool workspace, then lazily allocate the zero-initialized table at first use. The pool cleanup callback releases worker memos after joining; the controller releases its memo before returning. Serial calls own one memo through their validation and write passes. No memo survives its conversion or is shared between workers or source/target pairs. Keys compare all 96 input bits, including zero signs; collisions replace entries only after a successful conversion. Cached float results have already passed the domain, finiteness and float32-range checks. Failed optional-table allocation disables caching for that owner without retrying on every chunk or failing conversion. Invalid inputs retain the existing diagnostic and all-or-nothing publication behavior. These optimizations promise exact equivalence to the uncached conversion in the same build, not portable bit identity across compilers, math libraries or floating-point environments.

The public coordinate fixtures use independent Decimal-derived values. Signed sRGB and SMPTE-C triplets start from exactly representable binary32 inputs and allow `2e-7` absolute error for final storage and double math. Perceptual forward/inverse fixtures allow `5e-6` in their normalized coordinate units for stored-input rounding and inverse sensitivity over the specified fixture range. These budgets remain much smaller than the premature-clamp errors they target. Error-state and no-op preservation use exact byte comparisons; byte storage has independently fixed LUT outputs.

## Float frame coordinate changes

Converting an existing float frame between gamma sRGB, linear sRGB, Oklab, CIELAB, and DIN99d preserves finite RGB values below zero and above one. These are intermediate coordinates, not a request to store a bounded device RGB value. The conversion validates the entire result before modifying the frame; a nonfinite input, a mathematical domain error, or a result that cannot fit finite float32 returns `SIXEL_BAD_INPUT` and preserves the pixel buffer and its format/color-space tags. Serial conversion repeats the arithmetic to avoid allocating another full image buffer; parallel conversion uses transactional scratch storage as described in [encoder threading](../../threading/encoder.md).

The frame component's pixel view exposes the current float storage and its matching tags. A clone owns an independent copy of those float samples. Converting that clone to `RGB888` intentionally clips and quantizes the clone while the original float frame retains its samples. Callers must keep the original frame when they need both representations; converting the original frame to bytes is a destructive storage boundary. These frame guarantees do not by themselves establish source-loader, alpha-composition, resize, queue, or palette preservation.

## Float geometry and failure state

Float frame resize retains negative components and values above one in both separable filter passes. The internal extended RGB scaler is distinct from the bounded float helper used for transparent-mask coverage and historical resampling measurements. The latter continues to clamp coverage in each pass, then the frame classifies coverage at or above one half as transparent. Color samples do not determine that mask threshold. The caller still supplies the intended RGB resampling basis; the operation preserves the frame's typed RGB format and colorspace.

A resize that changes dimensions requires finite source components, including for nearest neighbor, and finite float32 horizontal and final results. An intermediate outside float32 storage is an error even if another filter pass might later reduce it. Ordinary magnitudes retain the selected eligible SIMD implementation; very large magnitudes use compensated double sums so a representable average does not fail merely because an unnormalized float sum overflows. Extended-color footprints with unresolved SIMD cancellation also use that scalar calculation. The dispatch decision uses a bound on accumulated float roundoff, including an absolute gradual-underflow term and does not relax the finite-result or float32-storage requirements. Zero-weight samples do not contribute. Scalar constant footprints, including `FLT_MAX`, and single-contributor footprints preserve their sample value exactly. A request with unchanged dimensions performs no arithmetic and does not revalidate sample values.

For a normally initialized float frame, any resize allocation or numeric failure preserves the original pixel pointer and every sample, transparent-mask pointer and bytes, transparency marker, dimensions, pixelformat, and colorspace. This applies to both borrowed and frame-owned pixels. The new buffers become visible only after color and mask processing succeed. This guarantee does not redefine the existing permissive handling of malformed mask metadata.

Crop performs no numeric conversion: it moves the selected float bytes and mask bytes, including NaN, infinity, and signed zero. Direct float frame crop requires a positive rectangle wholly inside the source and rejects an invalid rectangle before changing frame state. Bounds checks subtract an already validated origin instead of adding possibly overflowing signed coordinates. The CLI crop filter retains its documented behavior of trimming oversized rectangles and skipping empty intersections before calling the frame operation; see [crop and resize](../../encoder/preprocessing/crop-resize/README.md#cropping).

## Requested precision bounds palette application only

`--precision-policy=8bit` fixes palette application to gamma `RGB888`. It is not a prohibition on float32 intermediates: loader CMS output, high-depth source samples, linear-light resizing and non-gamma clustering keep the float32 storage they require, and only their result is rounded to gamma bytes immediately before palette application. Because that rounding is defined only for gamma coordinates, `8bit` rejects a non-gamma working space and a named output destination instead of rounding linear or Lab-family coordinates into an undefined byte format. `--precision-policy=auto` promotes wherever processing requires float32 and keeps that precision through palette application. The [encoder precision reference](../../encoder/precision/README.md#requested-precision-and-effective-format) owns the complete policy table.

`--precision-policy=float32` requests gamma `RGBFLOAT32` for the main encoder work buffer. It does not imply that the loader must decode every source directly to float32, so a planner report can legitimately show `source=rgb888 work=rgb-f32`. Conversion at the boundary is explicit.

The following simplified flow shows the independently typed boundaries:

```text
encoded image
    |
    v
loader decode -- optional ICC/CMS transform --> source frame
    |
    v
optional pre-resize conversion --> resize --> optional post-resize conversion
    |
    v
working frame --> sampling/binning --> clustering-space palette view
    |
    v
palette application/dither --> output-space conversion --> SIXEL palette + indices
```

The `source`, resize input/output, main `work`, and clustering palette view need not share one format. Reporting only the command-line request loses information about the path that actually ran.

For why linear RGB is needed and when the planner inserts or skips conversions, see [Lazy conversion at operation boundaries](../../encoder/colorspace-handling/README.md#lazy-conversion-at-operation-boundaries). A mathematical linear RGB or XYZ intermediate can exist inside a single-pixel transform without allocating a separate image buffer; precision promotion describes the storage that a processing stage actually requires.

## Operations that promote to float32

### Linear-light resize

The normal filtered-resize path converts a gamma byte source to `LINEARRGBFLOAT32`, resamples linear-light values, and converts to the requested working format afterward. With `--precision-policy=8bit -Wgamma`, the float buffer is transient: planner diagnostics report `source=rgb888 work=rgb888 scale_out=linear-f32`. This is an implicit high-precision operation even though the main work buffer remains byte-based.

`-j auto:resize_precision=preserve` explicitly keeps an integer source in `RGB888` while resizing. It reduces the storage of each affected RGB buffer from twelve to three bytes per pixel, but interpolation then averages gamma-encoded values rather than light. This mode is a memory-recovery policy with an accuracy cost, not an equivalent implementation of the default.

`-j auto:resize_precision=float` retains a float32 main work buffer after linear-light resizing. Explicit `--precision-policy=float32` also selects the float work path. If allocation of the required float buffer fails, libsixel stops rather than silently falling back to `preserve`; the diagnostic identifies the lower-memory command so the user makes the quality trade-off deliberately.

### Working color-space conversion

`-Wlinear`, `-Woklab`, `-Wcielab`, and `-Wdin99d` require color-space-specific float32 work formats. Under `auto` they promote the work buffer; `8bit` rejects them. `-Wgamma` is the only working space that can use either `RGB888` or `RGBFLOAT32`.

This rule is why these two commands have the same effective linear work format and the same output:

```sh
img2sixel --precision-policy=auto -Xlinear -Wlinear image.png
img2sixel --precision-policy=float32 -Xlinear -Wlinear image.png
```

The same equality holds for the Oklab pair. It shows that automatic precision does not truncate a float-only working space; it does not prove that every option outside the controlled pair is irrelevant.

`-X` selects the clustering coordinates rather than the main work coordinates. A non-gamma `-X` can create a float32 palette-construction view while `-Wgamma` remains byte-based. The detailed ownership and cost model are in [Palette clustering color space](../../encoder/palette-construction/clustering-colorspace/README.md).

### Output color definition

A [named RGB output destination](../../encoder/output/output-colorspace.md#named-destination-definitions) requires an effective float working format, even with `-Wgamma`, because its palette is converted and rounded to the sent destination values with extended intermediate coordinates; `--precision-policy=8bit` therefore rejects it. The requested precision is kept separately, so leaving named output restores the format required by the remaining settings. The legacy `gamma`, `linear` and `smpte-c` outputs convert only the final palette and do not request a float image buffer. See [Output color space](../../encoder/output/output-colorspace.md#display-p3-selected-cpu-float-path).

### Loader CMS output

When a loader applies an ICC transform, `cms_target` selects the target color space and `prefer_8bit` selects the requested representation after that transform. With `prefer_8bit=0`, gamma produces `RGBFLOAT32` and linear or Lab-family targets produce their typed float32 formats. A float source frame remains float through the planner and palette construction under every policy, so the encoder cannot silently down-convert it before construction. Under `-.8bit` it is rounded to gamma bytes only at palette application; `prefer_8bit=1` is the boundary to use when the CMS output itself should be bytes.

`prefer_8bit=1` requests `RGB888`, even when `cms_target` names a non-gamma space. This is intentionally a request for an 8-bit gamma storage boundary, not an 8-bit encoding of linear RGB or Oklab. A later `-Wlinear` or Lab-family working-space conversion may promote that byte frame again, but information rounded at the CMS boundary cannot be reconstructed.

CMS promotion occurs only when the selected loader actually applies a color transform. A plain image without an applicable profile may remain `RGB888`; the presence of `--cms-engine` or a float-capable target name alone does not prove that a transform ran.

### Native loader intermediates

PNG chromaticities also illustrate the difference between exact classification and numerical evaluation. After the external getter and coordinate checks, the libpng adapter reconstructs the 100000-scale integers and rejects exactly collinear primaries using an `int64_t` signed area. A mathematically zero determinant can acquire a floating residual larger than a singularity tolerance. Each integer product is bounded by `1e10` and the uncoupled subtraction by `2e10`, so a 32-bit intermediate is insufficient. This guard preserves the surviving-metadata [fallback contract](../../loader/png-color-metadata.md#exact-collinear-fallback-contracts); it does not improve the subsequent floating matrix solve, change coefficient storage, or remove the pre-matrix float32 store.

A float output buffer does not by itself prove that earlier native drawing or color-conversion stages retained source precision. The [CoreGraphics PNG source path](../../loader/coregraphics.md#why-a-float-destination-is-insufficient) reads original integer samples and keeps alpha separate before explicit float CMS conversion. Its observed native drawing controls are scoped to the tested path, while source normalization, canonical storage and final byte conversion remain distinct boundaries.

The [native RGB power preparation](../../loader/color-management/README.md#behavioral-contract-tests) copies source float bits when a paired channel/profile exchange is necessary; it does not predecode into another float buffer. This avoids adding an intermediate rounding or underflow point before the native matrix. Remaining native arithmetic is a separate precision boundary: subnormal results and small residuals from large matrix cancellation can still be lost or inaccurate. The dark relative tests cover their stated original 16-bit vectors and ordinary stored matrices, not every representable normalized float.

## Measured resize quality

The resize experiment uses a deterministic one-pixel black-and-white checker. Each 2-by-2 source cell contains equal black and white energy. The physically meaningful average is therefore linear intensity `0.5`, which the sRGB transfer function maps to `187.516...` and the reference rounds to byte tone `188`. Gamma-space averaging instead treats encoded channel numbers as light values.

![Quality of byte-preserving and float32 linear-light resize paths](measurements/pixelformat-precision-resize.png)

The default automatic path resolves to a transient `linear-f32` resize even though the command requests `--precision-policy=8bit`. It raises MS-SSIM from `0.961644` to `0.999993` and lowers mean Delta E00 from `9.971917` to `0.168512` against the analytical reference. Retaining float32 for the later work path produces the same quantized output on this fixture, so the gain here comes from linear-light resizing rather than from a different palette or dither policy.

This is deliberately a stress test at the spatial Nyquist limit, not an estimate of the average improvement on photographs. It isolates the mathematical error, while the large margin makes a regression easy to detect. The experiment fixes bilinear filtering, `K=256`, K-means with a fixed seed, hard binning, exact lookup, dither off, one thread, and CPU execution. MS-SSIM describes the spatial result, while mean Delta E00 describes pointwise perceptual color error. The raw measurements are in [`pixelformat-precision-resize.csv`](measurements/pixelformat-precision-resize.csv).

## Cost model and policy choice

For `N` pixels, a three-channel `RGB888` buffer requires approximately `3N` bytes and a three-channel float32 buffer requires approximately `12N` bytes. Conversion is `O(N)`. Resampling remains linear in output pixels for a fixed-support filter, but float arithmetic and pre/post color conversion increase its constant cost. Peak memory can include source, converted input, resized output, work, palette, and threaded scratch buffers simultaneously, so multiplying one buffer size is not a complete peak-memory estimate.

Use the default resize policy when accuracy is the priority. Use `resize_precision=preserve` only when the lower peak-memory path is needed and the gamma-space interpolation error is acceptable. Use `--precision-policy=float32` when later quantization, lookup, or dithering should also remain in the high-precision gamma path. Use `--precision-policy=8bit` when CMS, high-depth decoding, resizing and clustering should keep their float32 precision but palette application, lookup and dithering should run on gamma bytes. Selecting a non-gamma `-W` already requires float32, so adding `--precision-policy=float32` documents intent but does not create a distinct lower-level implementation.

## Observing the resolved path

Verbose planner output is the authoritative local check:

```sh
img2sixel --precision-policy=8bit -Wgamma -w50% -v -o /dev/null image.png
```

Read all of these fields together:

```text
formats: source=rgb888 work=rgb888 scale_out=linear-f32
resize: mode=2 input=linear-f32
```

`work=rgb888` alone would miss the transient float resize. For loader CMS work, enable the stable loader trace as well:

```sh
SIXEL_TRACE_TOPIC=loader_contract img2sixel \
  --cms-engine=builtin \
  -L 'builtin:cms_engine=builtin:cms_target=oklab:prefer_8bit=0!' \
  -Xoklab -Woklab -v -o /dev/null image.png
```

## Reproduction and validation

Commit the implementation being measured, provide Python with Matplotlib, and run from a tracked-clean worktree:

```sh
PYTHON=.venv/bin/python tools/reproduce_pixelformat_precision_measurements.sh
```

The runner rebuilds `img2sixel` and `lsqa`, removes inherited `SIXEL_*` and `LSQA_*` policy variables, generates the checker and analytical reference in a temporary directory, records stable planner/loader contracts, creates the figure and CSV files, and validates the result. Source revision, input and executable hashes, host information, and the complete protocol are stored in [`pixelformat-precision-run.json`](measurements/pixelformat-precision-run.json).

The recorded perceptual scores are measurement results, not portable exact floating-point expectations. The artifact checker requires finite scores, the stated quality direction relative to the `preserve` control, and matching output hashes between selected equivalent paths within the same run. It does not compare a new run's floating-point scores or output hashes exactly against the recorded host's results. These comparisons do not establish the arithmetic error bounds of an individual color conversion or resampling operation.

Validate an existing artifact directory without Matplotlib:

```sh
python3 tools/check_pixelformat_precision_measurements.py \
  docs/concepts/pixelformat-precision/measurements
```

Rerun the measurement after changes to loader CMS output selection, frame pixel-format conversion, resize planning or filtering, working-space resolution, palette construction, palette application, SIXEL writing, `lsqa`, or the measurement tools.

### Float geometry contract tests

The [tests/_support/processing/frame/0098_frame_float_dynamic_range.c](../../../tests/_support/processing/frame/0098_frame_float_dynamic_range.c) checks small results independently of large noncontributors and cancelling terms. A final footprint with one contributing RGB sample must return exactly `(1, 0.25, -0.5)`, including an unchanged axis. Three- and seven-sample symmetric triangle reductions must retain that small sample with weights `3/7` and `7/37`, respectively, in both horizontal and vertical passes. The seven-sample case places the cancelling extremes at mirrored inner taps (indices 2 and 4, each weight `6/7`), with zeros elsewhere except the center. This distinguishes symmetric distance evaluation from independently rounded divided coordinates. The absolute tolerance is `2e-6` on the small result; it is never scaled by the cancelling `FLT_MAX` or `1e20` magnitude. Each case exercises both the frame API and its internal extended helper under scalar and automatic dispatch. Compensated direct sums, symmetric filter distances, and local SIMD recovery preserve these residuals; constant and unary footprints avoid roundoff at the float32 storage limits. Bounded mask arithmetic retains its existing order.

The [tests/_support/processing/frame/0018_frame_float_resampling.c](../../../tests/_support/processing/frame/0018_frame_float_resampling.c) uses constant preservation, independent triangle weights, and the existing cubic kernel's exact rational quarter-pixel weights. It compares channel- and pixel-varying values with a `2e-6` absolute tolerance; the finite `FLT_MAX` constant average uses a `2e-7` relative bound. Nonconstant extreme inputs normalize by their exact float magnitude before comparison at the same `2e-6` bound. The mixed-sign downscale has independent normalized results `3/7, 3/7, 1/49`; the large cubic case uses fields `2*x-1, 2*y-1, (2*x-1)*(2*y-1)` scaled by `FLT_MAX/8`. Bilinear downscale uses separable weights `2:3:2`. For cubic enlargement, the right-hand source weights are `-3/16, 1/4, 3/4, 19/16`; RGB fields `x, y, x*y` distinguish both axes and intermediate clipping. These are formula-derived values, not saved scaler output. Single-pixel Gaussian enlargements additionally require exact identity: `1→6` at `FLT_MAX` rejects phantom scalar overflow from multiply/divide roundoff, while `1→2` checks ordinary non-binary fractions and subnormal samples against the original stored float values. Both axes and scalar/automatic dispatch are covered. Two-source triangle means separately check subnormal constants, mixed subnormals, and zero at exact endpoint/halfway values. The constant channels have magnitude `2^-149`, so both half-weighted contributions round to zero in float SIMD; unweighted nonzero source information distinguishes them from an exactly zero channel. The mixed center is `(3,4,-5) * 2^-149`, derived from endpoint triples `(1,2,-3) * 2^-149` and `(5,6,-7) * 2^-149`; no CMS or scaler output supplies the expectation.

The exact identity and subnormal-mean assertions above have zero numerical tolerance: their selected inputs and expected results are representable in binary32, and losing them is the defect under test. These numerical equality checks do not assert a particular sign bit for zero. Clone, crop and failure-state storage comparisons instead require identical bytes, including any signed-zero or nonfinite representation carried by the fixture.

The [tests/_support/processing/frame/0054_frame_float_geometry_state.c](../../../tests/_support/processing/frame/0054_frame_float_geometry_state.c) compares pixel and mask storage exactly after failures and crop. Its successful resize independently interpolates a linear color ramp with a `2e-6` absolute tolerance per component and checks binary checker coverage against the exact mask decision at `0.5`. The fixture's coverage values stay at least `1/32` away from that decision boundary; the color tolerance is not a tolerance on mask bytes. SIMD-specific owners explicitly skip when either the compiled implementation or CPU path is unavailable; an `auto` or ceiling request alone is not evidence that AVX, SSE2, or NEON executed. All small buffers are also exercised by the sanitizer build.
