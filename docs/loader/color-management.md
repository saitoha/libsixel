# Loader Color Management: builtin and Little CMS

For the implementation model and exact support boundaries, see [Builtin CMS specification and architecture](builtin-cms.md).

For the foundations, start with [primaries, white point, and transfer function](../concepts/colorspace.md#primaries-white-point-and-transfer-function), followed by [PCS: the connection between color profiles](../concepts/colorspace.md#pcs-the-connection-between-color-profiles). These explain why source normalization can require transfer decoding, primary conversion, and D50/D65 chromatic adaptation, and how the ICC connection differs from the encoder's working color space.

The [libpng adapter](libpng.md#color-management-and-precision) shares color interpretation between static images and animation rectangles. Its internal gray-float CMS format packs one gray sample per pixel without truncating sixteen-bit source values; alpha remains outside the transform. A profile rejected by libpng is not re-read from raw iCCP bytes to bypass that validation.

The builtin gray TRC fallback scales the PCS D50 white, rather than treating the profile's `wtpt` media white as PCS coordinates. This keeps valid gray profiles neutral when they carry a D65 media white. The libpng float-gray regression probes exercise this conversion with and without Little CMS; the [Little CMS gray input pipeline](https://github.com/mm2/Little-CMS/blob/master/src/cmsio1.c) uses the same PCS-illuminant interpretation.

## Why loader CMS matters

Loader CMS primarily protects the intended color interpretation of input images. Files authored for wider RGB gamuts or different transfer functions cannot safely be treated as ordinary sRGB just because they decode to three channels. Interpreting those samples directly as sRGB can change hue, saturation, brightness, and the balance between colors. CMS uses an applicable source profile or supported color metadata to normalize those samples into libsixel's known sRGB basis before the encoder makes palette and dithering decisions. Its purpose here is faithful normalization, not increasing saturation or extending the display gamut.

For example, Display P3 and sRGB have different primaries: the same RGB triplet need not describe the same color. Similarly, a source with a different gamma needs the appropriate transfer conversion even if its primaries match the destination. Correct conversion changes the numbers to preserve the intended colors where the destination can represent them. Colors outside sRGB must be mapped or clipped according to the available profile, intent, and implementation; CMS cannot preserve every wide-gamut source color in an sRGB result.

The default output contract is gamma-encoded sRGB palette values (`-Ugamma`), subject to palette reduction and SIXEL component quantization. An internal `cms_target=linear` or a perceptual working space changes the calculation representation, not that output contract or the display gamut. The explicit alternative `-U` modes are described in the [color-space guide](../concepts/colorspace.md); they do not provide an ICC-tagged wide-gamut display protocol. CMS establishes the input interpretation needed to honor the default output contract, but it cannot guarantee normalization when metadata is missing, unsupported, or skipped.

The receiving terminal and display stack own the mapping from those output values to the physical display. On a wide-gamut device, faithful rendering of sRGB and an optional enhancement that expands sRGB colors into a larger gamut are different policies: the former preserves the requested colors, while the latter deliberately changes them. Such display enhancement belongs to the terminal/device side and is not enabled by libsixel's loader CMS. SIXEL carries no source ICC profile or explicit color-space tag with which to negotiate it, so libsixel also cannot guarantee how every terminal will render its palette values.

## This already affects ordinary web images

You do not need to create wide-gamut artwork yourself to encounter this problem. A browser may already be interpreting an image's color metadata for you. Downloading that image and passing it through a different decoding API does not automatically preserve that behavior. The visible symptom can be “the downloaded image has different colors from the browser,” even when both programs successfully decode the file.

### Published prevalence, with a defined denominator

The [2024 Web Almanac media chapter](https://almanac.httparchive.org/en/2024/media#image-color-spaces) reports the following for its mobile image sample:

| Observation | Reported share or derivation |
| --- | --- |
| No ICC profile | 87.7% |
| ICC profile present | Approximately **12.3%**, calculated as `100 - 87.7` |
| Wide-gamut ICC profile | Approximately **1 in 80 images** (1.25%) |
| Adobe RGB (1998) profile | 0.7% |
| Display P3 profile | 0.4% |

These categories overlap: Adobe RGB and Display P3 are examples within wide-gamut ICC usage, which is itself within ICC usage. Most profiled images in this report use sRGB or an sRGB-like profile. **12.3% is not the percentage of images that visibly fail without CMS.** The report places CICP-only images in the no-ICC category, so its wide-gamut count does not cover every signaling method.

This is a historical June 2024 crawl, not a census of all Internet images or a current 2026 estimate. The [published SQL](https://github.com/HTTPArchive/almanac.httparchive.org/blob/main/sql/2024/media/color_spaces_and_depth.sql) counts image request records with ImageMagick colorspace metadata and more than one pixel, grouped by client and ICC description; it does not deduplicate all copies into unique image artworks. The [crawl methodology](https://almanac.httparchive.org/en/2024/methodology#websites) describes the selected public pages and logged-out lab conditions. Do not turn these percentages into the probability that a particular user's photo collection needs conversion.

No representative web-wide prevalence estimate for PNG `gAMA` alone, or for the union of ICC, `gAMA`, `sRGB`, `cHRM`, and CICP declarations, was established by the sources reviewed for this guide. An image contains color metadata, not a CMS: the CMS is the software interpreting it. An ICC-only statistic therefore cannot answer “how many images have gamma information?” Conversely, a `gAMA` declaration can describe an ordinary sRGB-like transfer and does not by itself establish a visible mismatch. The [PNG specification](https://www.w3.org/TR/png-3/#11gAMA) defines it separately from ICC and other color declarations.

A small local check with Pillow 12.2.0 confirmed the distinction: a PNG sample `(128,128,128)` with `gAMA=1.0` still decoded to `(128,128,128)` through `convert("RGB")`; reading the gamma value did not convert that linear sample to sRGB. Separately, the repository's Adobe-RGB [profiled fixture](../../images/measurements/palette-pipeline/a98-gamut-600x450.png) produced different pixels with explicit `ImageCms.profileToProfile(..., sRGB)` than with plain RGB mode conversion. These are narrow checks, not a complete tool conformance suite.

The everyday lesson is to preserve source color interpretation across tool boundaries. A browser can make profile handling invisible to its user, while a script receiving only RGB bytes can lose it. CMS is what connects those two workflows without unintentionally changing the image's colors.

### How the examples are made

The generator explicitly treats the RGB bytes of the repository's [snake fixture](../../images/snake.png) as an sRGB reference, independently of its approximate PNG gamma declaration. It converts that reference to floating-point source samples and then takes two paths: apply the inverse source interpretation to recover sRGB, or use those source samples directly as sRGB preview values. All figure PNGs carry an sRGB chunk, including the deliberately wrong panels, so the viewer does not correct the illustrated mistake a second time.

For Display P3, the calculation decodes the sRGB transfer function, converts linear sRGB through D65 XYZ to P3 primaries, and re-encodes with the same transfer function. The correct path reverses this conversion. The primaries and transfer definition follow [CSS Color 4](https://www.w3.org/TR/css-color-4/#predefined-display-p3). Starting from sRGB colors avoids out-of-gamut clipping and isolates misinterpretation from gamut mapping. For gamma 1.8, source values are `linear_sRGB ** (1 / 1.8)`; for linear light they are simply `linear_sRGB`. Correct interpretation decodes that source representation and applies sRGB encoding. Values are rounded to bytes only when producing the previews.

These are analytical illustrations before palette reduction, not screenshots, measurements of `img2sixel --cms-engine=none`, or a comparison of builtin and lcms2 accuracy. Actual loader fallback can interpret other metadata instead of treating samples as sRGB. The examples do not test ICC parsing, rendering intents, terminal gamut mapping, or SIXEL quantization. Their purpose is to make the cost of a wrong source interpretation visible on an ordinary sRGB display.

The [generator](../../tools/plot_loader_cms_examples.py) creates wide and stacked mobile layouts and checks that correct conversions recover the reference within `1e-12` before byte rounding. The [numerical record](cms-examples/examples.json) contains source and output hashes, chromaticities, and patch values. Regenerate or verify with Python, NumPy, and Pillow (the committed figures use NumPy 2.3.5 and Pillow 12.2.0 with its bundled font):

```sh
python3 tools/plot_loader_cms_examples.py
python3 tools/plot_loader_cms_examples.py --check
```

## Why ship a builtin CMS despite the additional attack surface?

Successful decoding does not prove correct color interpretation. Without an available CMS, a profiled image can still look plausible: its objects and detail remain recognizable, while its brightness or color balance is slightly wrong. A user can reasonably mistake that result for a correctly loaded image and attribute the difference to the source, quantizer, terminal, or quality metric. A silent interpretation error is therefore a practical correctness problem, even when it does not prevent opening the file.

Little CMS cannot be assumed to be installed in every supported environment. Making it mandatory would turn a missing color-management dependency into an inability to build or use libsixel at all. That tradeoff is particularly costly on platforms with limited package availability and in cross-compilation or WebAssembly builds, where a usable host installation is not enough: dependencies also need compatible target binaries, headers, and build/link configuration. WebAssembly does not make Little CMS impossible to use; it makes an additional dependency something that the target build must provision and maintain. The project supports [Emscripten targets](../platform-support.md), and both [Autotools](../../configure.ac) and [Meson](../../meson.build) allow builds without lcms2.

| Design choice | Benefit | Cost |
| --- | --- | --- |
| Require Little CMS | Ensure the external CMS dependency is present. | Exclude otherwise usable builds when that dependency cannot be provisioned; presence alone still does not guarantee every loader/profile combination is supported. |
| Keep Little CMS optional without a builtin CMS | Avoid maintaining an additional in-project profile interpreter. | When no external CMS is available, lose that normalization path and risk plausible-looking, incorrectly interpreted images. |
| Keep Little CMS optional and provide builtin CMS | Preserve build availability while retaining normalization for supported profiles without the external dependency. | Add profile-parsing and transform code, security exposure, maintenance, and a smaller compatibility envelope than Little CMS. |

The builtin engine deliberately accepts the third tradeoff. It supplies a useful baseline of color interpretation across dependency-constrained builds; it is not a claim that a smaller CMS is inherently safer, or that it replaces Little CMS's broader support. ICC metadata is untrusted input, and adding an interpreter increases libsixel's attack surface. Bounds and size checks, malformed-profile tests, fuzzing, and continued maintenance are necessary costs of this choice, not proof that the implementation is free of vulnerabilities. See the support limits and defensive coverage below.

This rationale also does not turn a successful load into a certification of color accuracy. Builtin CMS must be enabled to help, unsupported profiles remain possible, and fallback can still produce an image without applying the intended profile. The `img2sixel` and `lsqa` defaults are `auto`; library API loader defaults remain disabled. Documentation and reproducible measurements must distinguish the selected engine, the profiles it can interpret, and whether normalization actually occurred.

## CMS in quality measurements

`lsqa -# ENGINE` and `lsqa --cms-engine=ENGINE` select the process-wide loader CMS default for **both the reference and the target**, including a target read from standard input. Accepted engines are `none`, `auto`, `builtin`, `lcms2`, and `colorsync`; `off` and `disabled` alias `none`, `lcms` aliases `lcms2`, and `color-sync` aliases `colorsync`. Repeated selections use the last value. Omitting the option selects `auto` unless an explicit environment setting overrides it. Library API loader defaults are unchanged.

An explicit option overrides `SIXEL_LOADER_CMS_ENGINE`, including assignments through `--env`, regardless of argument order. Loader-specific environment settings and `-L` suboptions retain their normal higher priority. Engine availability and fallback follow the same loader rules as `img2sixel`. Use matching settings in both programs when measuring profile-aware encoding:

```sh
img2sixel --cms-engine=builtin source.png | lsqa --cms-engine=builtin source.png -
```

Use `--cms-engine=none` in both commands when deliberately measuring the legacy interpretation. Record the selected engine and loader-specific overrides alongside the metric. CMS interprets source metadata during loading; `lsqa -W` and `-P` choose the comparison colorspace and precision after loading. Those comparison options cannot repair source values that were already interpreted incorrectly. SIXEL input has no embedded ICC profile to recover: its decoded palette is compared with the normalized reference.

## Diagnosing ignored ICC features

Enable `SIXEL_TRACE_TOPIC=loader` to record builtin ICC parser decisions on stderr:

```sh
SIXEL_TRACE_TOPIC=loader img2sixel --cms-engine=builtin image.png > image.six
```

Records use `LSXCMS1|engine=builtin`. `event=ignored-tag` includes `tag`, payload `type`, and a `reason`: `unsupported-pipeline-type` (including `mpet`), `unsupported-intent-slot` (including D2B3/B2D3), `tag-not-consumed`, or `invalid-tag-bounds`. Tag and type signatures are eight hexadecimal digits, not raw untrusted text: D2B0 is `44324230` and mpet is `6d706574`. Descriptive `desc`, `cprt`, `dmnd`, and `dmdd` tags are omitted from this audit. `tag-not-consumed` means this parser does not read that tag; it does not assert that the tag is invalid or that ignoring it changes the image.

A present transformation slot that fails parsing or channel validation emits `event=pipeline-rejected` with its tag and `reason=invalid-or-unsupported-pipeline`. The parser may still accept another path. `event=profile-rejected` identifies an unsupported PCS or the absence of a usable profile path; an invalid tag table emits `event=invalid-table`. These messages do not distinguish every malformed nested element from every unsupported feature, and a successfully parsed profile is not proof that a loader ultimately applied it. They describe the builtin parser, not decisions inside Little CMS or ColorSync. Profiles that do not reach the parser, including CMS-disabled loads, are outside this diagnostic boundary.

The facade separately emits `LSXCMS2|event=apply` after a transform executes. Its `engine` comes from the transform backend, including profile-open fallback, rather than the requested global selector. `path=extended-rgb` identifies builtin analytic float RGB, `bounded-device` identifies the legacy builtin device path, and `external` identifies an external CMS call. `src` and `dst` are internal CMS pixel-format enum values; `ok=1` records apply success. This proves that invocation executed, not that later loader/frame stages preserved its output. With the loader topic disabled, the apply record is also silent.

The tag audit checks offsets and lengths before reading payload signatures, limits detailed records to 64 per parse, and then emits `event=tag-audit-truncated`. Repeated parsing can produce repeated records. With the loader trace topic disabled, this audit is skipped and no new diagnostics are emitted. Trace selection does not change profile acceptance, fallback, or output pixels.

The diagnostic fixture `tests/data/colormgmt/input/custom/rgb_trace_ignored_tags.png` preserves the PNG pixels and original profile tags from `rgb_parametric_012.png`. Its iCCP profile adds D2B0 and D2B3 mpet payloads containing a three-channel identity matrix element, plus a private tag whose signature contains ESC. Profile size, tag offsets, compressed iCCP data, and PNG CRC are updated. It exercises unsupported paths and escaped logging while retaining the original usable normalization path; it is not an mpet conformance fixture.

## Default-on migration and measurements

`img2sixel` and `lsqa` set the global loader CMS default to `auto` when its environment value is absent or empty. Explicit `none`, backend-specific settings, and CLI choices retain their precedence. This is a CLI behavior change; direct library loader defaults remain disabled. Existing scripts requiring byte-identical legacy interpretation should specify `--cms-engine=none` in both tools. Profile-aware checks should select the same CMS engine on encoding and assessment, and test the unmanaged path only as an intentional control.

The migration keeps fixed unmanaged palette/background fixture tests explicit about `none`; it does not regenerate their expected values from the new implementation. Separate default tests omit the engine option and verify an observable difference from `none`. Historical quantization/precision figures describe controlled experiments at their recorded revisions, not the new CLI defaults. The shared environments in `plot_lookup_policy_speed.py` and `plot_quality_curve.py` now explicitly retain `SIXEL_LOADER_CMS_ENGINE=none` for those policy sweeps unless overridden. For other historical reproduction scripts, inspect their recorded commands and supply the corresponding CMS setting rather than inheriting today's default. The [PNG loader comparison](builtin/png.md#reproduce-the-measurements) already specifies `cms_engine` per case and is unaffected by the CLI default.

The default change itself was remeasured with the builtin decoder, one thread, raster Floyd–Steinberg diffusion, seven interleaved samples after warmup, and the same binary with explicit `none` versus `auto`. On this build `auto` uses builtin CMS. Times include fresh process startup, decoding, quantization, SIXEL encoding, and stdout capture; they are not isolated CMS costs. All quality values use an `auto`-managed reference in lsqa, including the unmanaged encoding control. The [raw record](cms-default-measurements.json) contains commands, versions, input/source/output hashes and every sample.

| Input | CMS none, median ms | CMS auto, median ms | Managed-reference MS-SSIM, none | Managed-reference MS-SSIM, auto |
| --- | ---: | ---: | ---: | ---: |
| Snake PNG | 71.15 | 85.96 | 0.988798 | 0.990314 |
| Snake JPEG | 73.53 | 109.19 | 0.990440 | 0.990493 |
| Embedded extended-sRGB JPEG, 64 px fixture | 26.49 | 26.37 | 0.778410 | 0.997297 |
| Parametric ICC PNG fixture | 25.74 | 25.64 | 0.989310 | 0.996289 |

These samples demonstrate both the correction benefit and the cost. The profiled JPEG control is visibly outside the normal quality gate; that low control score is not a lowered acceptance threshold. The ordinary JPEG also becomes slower: builtin CMS enablement selects float decoding even without an applicable ICC conversion. Small-fixture times are dominated by startup and are not evidence that conversion itself is free. These are local measurements, not cross-platform speed guarantees or an independent validation of builtin ICC accuracy.

## Choosing an engine

Enable loader CMS when the source profile matters: `img2sixel --cms-engine=auto image.png`. CMS defaults to `auto` in `img2sixel` and `lsqa` for participating loaders. For varied third-party ICC profiles, prefer a build with Little CMS (`lcms2`) and verify that the selected loader supplies the original source color model to it. Choose `builtin` when avoiding an external CMS dependency matters and the actual profile corpus has been validated against the supported subset below. Neither engine can repair an incorrect source profile or recover source channels already discarded by a decoder.

**Successful image loading is not proof of successful color management.** Unsupported or unusable metadata can lead to a format-specific fallback and a displayable image with different colors. Also, requesting `lcms2` does not require that dependency to be present: an unavailable engine resolves through `auto`. Reproducible color output requires checking the build and loader as well as the command line.

This guide compares libsixel's integration, not every feature of the underlying libraries. [Little CMS documents broad ICC v2/v4 support](https://www.littlecms.com/color-engine/), including features beyond libsixel's loader interface. The [color-space guide](../concepts/colorspace.md) explains source interpretation, `cms_target`, `-X`, `-W`, and `-U`; those encoder options do not substitute for reading an embedded profile.

## Decoder and CMS are independent choices

`builtin` names both an image-loader component and a CMS engine. They are independent. The builtin PNG decoder can use lcms2; the libpng decoder can use builtin CMS. The global CMS selection participates in the builtin, libpng, libjpeg, libwebp, and libtiff components. Other frameworks can have their own color behavior.

```sh
# Same decoder, different requested CMS engines.
img2sixel -Lbuiltin:cms_engine=builtin:cms_target=linear:prefer_8bit=0! image.png
img2sixel -Lbuiltin:cms_engine=lcms2:cms_target=linear:prefer_8bit=0! image.png
```

The final `!` closes the loader chain. It does not require a successful ICC conversion or make an unavailable CMS engine an error. Loader-specific `cms_engine` settings override the process-wide `--cms-engine` default. `auto` chooses lcms2 when compiled in, otherwise ColorSync when available on macOS, otherwise builtin. Profile opening and the standard profile factories also try builtin when the selected external backend fails, including an explicitly selected external engine. This is not a retry through every engine: a failed lcms2 profile open does not next try ColorSync. Transform creation requires matching source/destination profile backends and does not retry a failed external transform through builtin. A loader can separately fall back to another metadata interpretation or unmanaged pixels. An explicit engine name therefore does not currently guarantee actual execution by that backend.

Autotools detects lcms2 by default and accepts `--with-lcms2` / `--without-lcms2`; Meson exposes the `lcms2` feature option. Inspect the configuration result and, for Autotools builds, `HAVE_LCMS2` in `config.h`. Pin the build, dependency version, loader, CMS settings, and encoder settings when exact reproducibility matters. See [platform support](../platform-support.md).

## Supported profile structures and practical differences

The builtin parser and evaluator are in [`icc-parse.c`](../../src/icc-parse.c) and [`icc-apply.c`](../../src/icc-apply.c). Acceptance depends on the actual tags, channel counts, direction, and available conversion path; an ICC version number or a familiar profile name alone is insufficient.

| Area | builtin CMS | lcms2 through libsixel |
| --- | --- | --- |
| RGB and grayscale | RGB colorant matrix plus channel tone response curves (TRCs), grayscale white point/TRC, and supported LUT paths. | Delegates compatible input profiles and transforms to Little CMS. |
| CMYK and Lab | Supported profile paths exist; CMYK LUT conversion includes byte, 16-bit, and float source interfaces. These work only where the loader retains and passes the corresponding samples. | The wrapper maps CMYK byte/16-bit/float and Lab float formats, subject to the same loader boundary. |
| Profile connection space (PCS) | XYZ or Lab. The conversion code connects through D50 XYZ and the project's sRGB basis. | Little CMS owns profile connection and intent processing. |
| Curves | `curv`, `para` function types 0–4, and the implemented `segm` subset. | Little CMS parses and evaluates its supported curve representations. |
| LUT payloads | `mft1`, `mft2`, and implemented `mAB`/`mBA` curve, matrix, and CLUT stages. Forward A2B and reverse B2A slots 0–2 are represented. | Little CMS handles its supported ICC pipelines and optimization. |
| D2B/B2D | Looks up slots 0–2 but only parses the same supported LUT payloads. This is not general ICC floating-point multi-process-element support. | Broader ICC pipeline support depends on the linked Little CMS version and transform compatibility. |
| Dependency | In-tree implementation with no external CMS library dependency. This says nothing about the selected image decoder's dependencies. | Requires a build linked with lcms2. |

Builtin CMS is therefore more capable than a gamma-only correction or an RGB matrix-only converter. Conversely, accepting some LUT profiles does not make it a full ICC implementation.

## Cases builtin does not fully support

- **Other input color models:** the profile parser dispatches RGB, GRAY, CMYK, and Lab. XYZ as a device input, CMY, YCbCr, and multicolor input signatures such as five- or six-ink profiles are outside that dispatch. XYZ as a PCS is supported and is a different role.
- **Arbitrary multi-process elements:** there is no `mpet` payload parser. A D2B tag name alone does not establish support for a standard floating-point processing pipeline. D2B3/B2D3 are not in the slot inventory. A profile requiring those paths needs another supported path or cannot be applied by builtin.
- **Unimplemented curves or stages:** parametric function types outside 0–4 and payloads outside the implemented curve/LUT grammar cannot be evaluated merely because the enclosing file is ICC. A usable alternate path can still be selected.
- **Distinct absolute-colorimetric intent:** builtin maps both `relative` and `absolute` to slot 1. It does not implement a separate intent-dependent media-white adaptation step. Selecting `absolute` therefore must not be interpreted as an lcms2-equivalent paper-white simulation.
- **Full device-link, named-color, spectral, or iccMAX workflows:** the builtin API is not a general implementation of these workflows. Nor does selecting lcms2 expose all of them through `img2sixel`; the loader wrapper has a fixed set of pixel formats and targets.
- **Unbounded scene-referred ICC processing:** ICC device curves and CLUT stages retain their bounded domains. The builtin facade preserves extended values when its float destination is analytic sRGB or a synthetic RGB definition; this does not make arbitrary ICC pipelines unbounded. HDR metadata interpretation and tone mapping remain loader-specific.

There is no loader option here for an arbitrary output/printer ICC profile, a proofing profile, gamut warnings, or black-preserving separation. Little CMS offers additional facilities, but this wrapper creates ordinary transforms and does not enable `cmsFLAGS_BLACKPOINTCOMPENSATION`. Do not infer black-point compensation or soft proofing from `cms_engine=lcms2`.

## Rendering intent and fallback

`cms_intent=perceptual|relative|saturation|absolute` can be expressed as an ordered `+` list. The default attempt order is perceptual, relative, saturation, absolute. An inner `!` suppresses appending omitted intents; see the [loader grammar](README.md) for how this combines with the loader-chain terminator.

Builtin turns intents into deduplicated LUT slots: perceptual → 0, relative/absolute → 1, saturation → 2. RGB/gray-to-sRGB paths can subsequently fall back to matrix/TRC conversion when those slots cannot be applied. Thus an exclusive intent list is not a guarantee that conversion fails unless the profile contains that exact LUT, and a matrix profile need not produce different results for every intent. Builtin does not synthesize a new perceptual gamut map just because `perceptual` was requested.

The lcms2 wrapper tries creating a transform with each allowed intent using normal flags. If all fail, it retries with `cmsFLAGS_NOOPTIMIZE`. Intent support and any internal profile fallback then belong to Little CMS. These are different mechanisms from builtin's slot evaluation; a matching intent name does not imply identical output.

When investigating a mismatch, inspect the selected format path and available loader-contract diagnostics, then compare against an independently converted reference. A zero exit status or an intent-order trace alone is insufficient evidence.

## Quality: what can change visibly

For a supported matrix/TRC RGB profile, builtin can perform meaningful profile-aware conversion, including sources whose primaries differ from sRGB. Little CMS is not automatically visibly better for every such image. For less common profiles and intent-dependent conversions, its broader implementation is a reason to prefer it, while still validating the specific loader and profile combination.

Builtin samples parametric and segmented curves into 4096-entry, 16-bit tables and interpolates table values. Its CLUT evaluator interpolates the surrounding grid corners; its conversion stages also clamp values. Little CMS can use a different evaluation and optimization path. Differences can therefore appear in dark gradients, saturated patches, LUT transitions, and wide-gamut colors even when both engines successfully apply a profile. Equality of ICC tag support is not bitwise equivalence or proof of equal colorimetric accuracy.

The largest error may instead be a skipped profile: decoding Display P3 or another source RGB space as ordinary sRGB can change color interpretation before quantization starts. More palette colors, float precision, or Oklab dithering cannot correct that interpretation error. Conversely, a valid conversion still ends at the output gamut and SIXEL palette quantization; SIXEL carries no ICC profile for the terminal to recover the original colors.

For float-capable loader paths, `prefer_8bit=0` preserves the selected typed CMS target; `prefer_8bit=1` requests an 8-bit gamma RGB boundary. Float storage reduces additional rounding but cannot recover source precision, clipped colors, or the builtin curve tables' sampling precision. Keep this setting and the actual output frame format fixed when attributing differences to an engine.

## Speed and memory: workload-dependent tradeoffs

No controlled builtin-versus-lcms2 timing result is established by the coverage listed below. It would be misleading to promise that builtin is faster because it has fewer dependencies, or that lcms2 is always faster because it optimizes transforms. The following are implementation-based expectations to test, not measured rankings:

| Cost | Expected influence |
| --- | --- |
| Profile parsing and transform setup | Builtin allocates curve/LUT storage and samples parametric curves. lcms2 creates and may optimize a transform. Setup can dominate many small images. |
| Per-pixel evaluation | Builtin matrix/TRC paths and multi-stage CLUT paths have different costs. A CLUT with three inputs visits up to 8 corners; four inputs up to 16. Large images can favor an optimized reusable transform, but require measurement. |
| Precision and frame buffers | RGB float32 payload uses 12 bytes/pixel versus 3 for RGB888, before alpha, temporary buffers, and metadata. Extra conversions and memory traffic can dominate the engine difference. |
| Decoder and encoder | Enabling CMS can change decoder fast-path eligibility; resize, quantization, dithering, and output serialization can hide CMS costs in end-to-end time. |
| Animation and batching | Profile/transform reuse depends on the loader path. Measure actual frame handling rather than assuming reuse across files or frames. |

The wrapper uses `cmsDoTransform`; it does not by itself install Little CMS acceleration plugins. Do not transfer published plugin speedups to this integration without verifying the build and execution path.

A useful comparison holds the decoder fixed, uses explicit builtin/lcms2 selection on a build verified to contain lcms2, and measures both setup plus conversion and the complete `img2sixel` pipeline. Use the same profile bytes, intent, target, precision, dimensions, alpha policy, resize, palette, dithering, and thread settings. Redirect SIXEL to a sink when timing so terminal rendering is excluded; capture it separately for output-size and quality comparison. Report repeated-run medians and variation, dependency/compiler versions, host, and whether caches are warm.

Compare decoded managed pixels against an independently prepared color-managed reference before palette reduction, including neutral ramps, near-black gradients, saturated colors, RGB matrix profiles, and CMYK/LUT profiles where the loader supports them. Report color error in a stated common color space, including worst cases; supplement with final SIXEL MS-SSIM and stream size. A high MS-SSIM score against a baseline made by the same engine proves regression stability, not independent ICC correctness. Skipped profiles must be reported as unsupported/fallback cases, not counted as fast successful conversions.

### Original ColorSync gamma representation

`SIXEL_LOADER_CMS_COLORSYNC_NATIVE_GAMMA=1` selects the original pure-gamma curve representation for the ColorSync input-to-linear helpers above. The default is `0`: keep the equivalent `para3` workaround enabled. Unset and empty values use the same default. This environment-only compatibility setting is registered with a strict boolean type and no assigned short option or public `setopt` flag. It is also accepted through the existing `--env NAME=VALUE` mechanism; there is no dedicated CLI flag or loader suboption.

With value `1`, eligible RGB `curv` and pure-power `para` payloads retain their original bytes. The independent identity-blue protection still exchanges original source sample bits and their corresponding TRC/XYZ payloads together when required; compatibility mode does not disable that protection. Eligible gray `curv` and type-0 `kTRC` payloads use the unprepared native profile. The borrowed profile and the caller's original ICC bytes remain unchanged. Both generic direct-linear and strict ColorSync RGB entry points honor this setting; gray uses the generic direct-linear entry. The normalized range limits equivalent curve spelling; the original-curve component permutation is also eligible for finite extended RGB triplets. Profile-version, matrix, whitepoint and forward-LUT eligibility limits remain in force.

The setting is read once during each ColorSync source preparation, not cached when the source profile is opened. Reusing a borrowed profile with `0`, then `1`, then `0` therefore restores the initial conversion behavior. Only exact `0` and `1` are accepted. An invalid nonempty value makes this CMS helper return failure with a diagnostic before publishing changed source samples. A loader may retain its existing unmanaged fallback after a CMS failure; this setting does not turn every loader's fallback into a fatal CLI error. Other CMS engines do not consume the setting, and ordinary `create_transform`/`do_transform` calls do not invoke this preparation. In particular, conversion from the canonical linear representation to a P3 output definition is outside its scope.

Compatibility tests compare against a direct native transform on the same OS, using the original ICC or an independently permuted original-tag/sample reference when identity-blue protection applies. They do not freeze the current OS's dark-toe values or require normal and compatibility outputs to differ. If Apple later evaluates both curve representations identically, equality to the contemporaneous native reference and comparisons of the actual prepared TRC/XYZ/whitepoint payloads and source sample bits remain the contracts. Mixed-domain comparisons treat positive and negative output zero as the same color value; source and rollback bits remain exact. Normal mode retains the independent gamma/matrix numeric tests above. The observed curve-representation difference does not establish Apple's internal intent or a perceptual-rendering policy.


### TIFF original byte RGB and Gray input

Eligible opaque UINT8/VOID RGB, MINISBLACK and MINISWHITE now use original scanlines under the [libtiff direct-byte contract](libtiff.md#original-byte-samples-and-final-publication). ICC success establishes extended canonical linear float before final target conversion. Absent, disabled, inapplicable or failed ICC retains exact original RGB888/GAMMA bytes; unmanaged float publication is not this branch's contract. Source/profile compatibility is checked before the shared helper, including builds without Little CMS. Optional CMS failure preserves the entire caller float source before exact byte reconstruction, while mandatory decode failure terminates without RGBA retry.

The [literal specimens and oracle tables](../../tests/data/color-numeric/tiff-byte.json) are generated from original integers and raw ICC tags using rational normalization, independent matrix/Bradford calculations and Decimal power evaluation. The float and native relative allowances remain the existing declared test budgets, with exact black and no absolute floor for analytic dark samples. The data cover all byte levels for fallback, independent orientation mapping, actual engine application, qualified partial work and nonfinite-result rejection. A resolved background leaves eligible opaque source samples unchanged, intentionally avoiding the convenience reader's former alpha-255 one-level attenuation. The float allocation still occupies 12 bytes per pixel when its fallback payload is compacted to 3 bytes per pixel.

Final image differences depend on downstream operations. Retained extended P3 values can affect interpolation before palette reduction; explicit byte preference intentionally restores that byte boundary. Unmanaged fallback retains its prior byte representation because changing the representation alone can select a different existing precision/lookup path and change final pixel assignment. Numeric source accuracy, intermediate gamut retention and final perceptual quality are separate observations. No universal visible improvement, new perceptual reference, relaxed threshold, or downstream lookup-policy change is implied.

### TIFF original integer alpha

The [original integer alpha contract](libtiff.md#original-integer-alpha-and-composition) reads associated/unassociated RGB and Gray samples before libtiff's RGBA convenience conversion. MINISWHITE reverses storage polarity before unassociation. Original integer ratios round once to binary32; the adapter retains above-one source values while each CMM keeps its existing device-domain behavior. CMS establishes finite canonical linear RGB before external-background composition and target conversion. Alpha remains separate during optional CMS work, and only complete results are published.

The [independent source, ICC and composition tables](../../tests/data/color-numeric/tiff-alpha.json) distinguish original-ratio rounding from stored-F32 composition. Canonical values use the existing triplet-relative budgets with exact black and no absolute floor. Composition checks first qualify actual no-background canonical F32 against that independent ICC oracle, then isolate the background operation. Gamma/final-byte targets follow composition; other working-target tests are controls against the existing converter rather than independent mathematical proofs of that converter. Fault tests execute real native work before rejection, qualify the changed scratch prefix, preserve original color and alpha, reject partial publication, and require complete same-input recovery. Their finite-result postcondition is distinct from whether a native void/boolean API reported apply success.

Unmanaged 8-bit all-255 alpha keeps exact RGB888/GAMMA, including with a background. Every unmanaged UINT16 alpha input retains RGBFLOAT32/GAMMA, including all-65535 alpha, without first reducing color or coverage to bytes. Original UINT16 alpha 1/65535 stays nonzero; only zero becomes an omission mask. Other unmanaged 8-bit source fractions and actual composition retain gamma float storage; this marker does not establish calibrated device primaries. A source/device profile never transforms the separately encoded external background. The adapter's ratio operation requires no new high-precision runtime library. The bounded original integer ratio (numerator and denominator at most 65535) is divided in binary64 and rounded once to binary32; independently rounded normalized operands are not equivalent. Tests include 128/257 as a distinguishing witness. Canonical Gray boundary cases verify both successful ColorSync source groups by their complete original float words and exact apply count, distinguishing partitioning from retry or backend fallback. Early byte clipping and downstream precision selection remain separate possible causes of final image differences.

### TIFF IEEE floating-point samples

For format, CMS connection and precision coverage, see the [TIFF loader support table](libtiff.md).

For the existing eligible TIFF scanline path, finite 32-bit IEEE floating-point samples retain their stored range before color management. With no applicable ICC conversion, this includes CMS disabled/`none` even if the file contains an ICC profile. Eligibility remains limited to contiguous strips, orientation 1–4, exactly three RGB samples or one MINISBLACK/MINISWHITE sample, and no extra samples. RGB preserves every source word; MINISBLACK copies the source word into all three channels. Negative zero, subnormals, negative values and values above one are preserved. Orientation changes coordinates, not sample values.

MINISWHITE continues libsixel's existing unit-relative polarity convention, `1-x`, extended to finite stored values outside `[0,1]`. It computes in double and rounds the result to float32. Under binary32/binary64 round-to-nearest/ties-to-even, this gives the correctly rounded value of exact `1-x`: the middle exponent range fits double exactly; values very close to zero still round to one; for very large magnitudes the unit displacement cannot change the float32 result. Both signed zeros map to one, and one maps to positive zero. This narrow operation needs no new high-precision arithmetic library. Other rounding modes and flush-to-zero execution environments are not newly guaranteed.

Without a successful applicable ICC conversion, the published representation is `RGBFLOAT32` with the existing `GAMMA` marker. IEEE floating-point storage alone does not establish linear light, sRGB primaries, calibrated colorimetry or normalization to `[0,1]`. [TIFF 6.0, Section 19, pages 80–81](https://image-js.github.io/tiff/media/TIFF6.pdf#page=80) defines sample type separately from bit depth and defaults SMin/SMax to the data type's full range; Section 20 describes RGB without additional colorimetry as device-specific. The `GAMMA` fallback and MINISWHITE `1-x` convention are libsixel policies, not universal colorimetric interpretations of floating-point TIFF. This path does not newly interpret SMin/SMax, WhitePoint, PrimaryChromaticities or TransferFunction, rescale exposure, or change target negotiation. Explicit `cms_target` and byte preference retain this path's existing unmanaged float publication behavior.

NaN or either infinity in either managed or unmanaged input produces a TIFF error before frame delivery, with no partial callback and no RGBA retry. This intentionally replaces the earlier NaN publication and infinity endpoint clamp. A scanline failure after a decoded prefix likewise publishes no callback and does not retry RGBA. Temporary allocations are released, and the same loader component can decode a subsequent valid image. This is a loader publication/recovery contract, not failure atomicity inside external libtiff or a general memory-exhaustion recovery guarantee.

An applicable embedded RGB or Gray ICC profile is converted directly to canonical linear sRGB through the shared transactional helper. Success publishes `LINEARRGBFLOAT32`/`LINEAR`, including finite negative and above-one output. There is no adapter input clamp or bounded gamma-sRGB intermediate. The selected engine still owns its ICC device-domain rules: retaining source words does not require every TRC/LUT to accept or identically extend negative or above-one device coordinates.

Invalid/mismatched profiles and failed direct-linear conversions publish every original device sample as `RGBFLOAT32`/`GAMMA`; MINISWHITE retains the existing polarity-adjusted samples. This intentionally replaces the former bounded managed-failure fallback. The adapter does not retry the legacy ICC apply on partially converted input. The helper's existing scratch publication and finite-result checks protect original samples; shared profile-factory and explicit-engine fallback rules are unchanged. This is not a new promise of low-level CMS failure atomicity or a universally color-correct fallback.

ColorSync classifies original source pixels before pure-gamma preparation: the Gray component, or the complete RGB triplet, must lie in `[0,1]` for default equivalent `para3` spelling. An outside neighbor no longer suppresses preparation of normalized dark pixels. A triplet with any component outside that interval retains all its original curves, including those for its in-range components. The independent identity-blue component permutation remains eligible for finite extended RGB values and in compatibility mode. Its reference is a low-level native transform with the original TRC/XYZ payloads and source components exchanged together, independently of production preparation; unpermuted native output can itself be batch-dependent for an affected profile. Gray compatibility and profiles needing no preparation use the original whole batch.

The Gray16 integer contract is described separately below. Target negotiation, alpha/extra samples, new layouts, other loaders and the separate Lab/LogLuv contracts are unchanged. The [literal raw record](../../tests/data/color-numeric/tiff-float.json) supplies exact source/polarity expectations. The [managed fixture record](../../tests/data/color-numeric/tiff-managed.json), [serializer](../../tools/generate_tiff_managed_fixtures.py) and [separate byte-reader oracle](../../tools/tiff_managed_reference.py) derive normalized/extended matrix and TRC references without a CMM. Fixtures and references are generated offline.

Managed numerical tests retain the per-triplet relative allowance `64 * 2^-24`. The ColorSync allowance composes it with the destination inverse's infinity-norm fixed-point perturbation allowance `norm * 4q / (1 - norm * 3q)`, where `q=1/65536`. Tabulated LittleCMS TRCs have a separate declared `norm/65535` absolute quantization allowance. Analytic dark samples have no absolute floor and black is exact zero. These budgets derive from representation/operation assumptions, not the largest observed error; they are test allowances, not proofs of opaque native arithmetic. Failure probes qualify real processed samples, unchanged remainder, result-scratch release, zero legacy retries, independent original values and normal recovery. Builtin in-place RGB traverses from the end, so partial output is not universally a prefix.

Retaining values protects later processing, including interpolation before a bounded display output. Direct rendering may hide the difference because a later output boundary clips the same values. This contract does not assert a universal perceptual improvement, select a physical rendering for every unmanaged TIFF, or guarantee that huge finite samples remain representable through every later nonlinear operation.

### TIFF Gray16 samples

Eligible UINT16 MINISBLACK/MINISWHITE TIFFs use the existing contiguous-strip path: one channel, no extra samples, and orientation 1–4. The loader normalizes the original unsigned word by 65535 in double, applies `1-x` for MINISWHITE, then stores the result in all three float32 channels. `SAMPLEFORMAT_VOID` retains its existing UINT interpretation. This integer normalization is distinct from preserving raw IEEE floating-point samples.

With an applicable embedded ICC, Gray16 passes these original normalized samples to the shared direct-linear helper. Only a complete finite result is published as `LINEARRGBFLOAT32`/`LINEAR`; it is not converted through an intermediate sRGB gamma buffer or decoded a second time. The shared ColorSync gray source preparation and native-gamma compatibility setting apply under their existing eligibility rules.

If that helper fails, the TIFF adapter preserves the complete normalized, polarity-adjusted source as `RGBFLOAT32`/`GAMMA`. It does not retry the legacy ICC parser/apply. This includes failure after a native transform writes a prefix or reports success with a nonfinite result. Compared with the former Gray16 gamma path, a successful legacy retry is deliberately no longer used. Shared profile-factory and engine fallback policies are unchanged. No ICC, an invalid/incompatible profile, or disabled CMS retains the existing normalized-source fallback.

The existing managed-TIFF [serializer](../../tools/generate_tiff_managed_fixtures.py) also emits two small Gray16 fixtures. Its [separate byte reader](../../tools/tiff_managed_reference.py) derives original words, exact rational normalization/polarity, nearest binary32 source words and stored-ICC values independently of a TIFF library or CMM. Tests check every component and frame metadata, use the relative allowances above with exact black and no absolute floor for analytic dark samples, and qualify partial work and recovery separately from the fallback values. Retaining these values is not a guarantee of visible improvement after final palette quantization. Other bit depths, layouts, alpha handling, profile support and target negotiation are unchanged by this Gray16 connection.

### TIFF unsigned RGB16 input

The libtiff loader converts eligible unsigned 16-bit RGB samples directly from their embedded ICC definition to the shared linear-sRGB destination. Eligibility remains limited to three RGB components in contiguous strips, orientations 1–4, and no extra samples. `SAMPLEFORMAT_VOID` retains its existing interpretation as unsigned integer. Original words are normalized by 65535 and stored as float32 before CMS; orientation changes only their coordinates. A successful conversion publishes `LINEARRGBFLOAT32` with `LINEAR` coordinates, preserving the CMS result's negative and above-one components. The adapter does not round-trip this result through gamma-sRGB or apply the old bounded gamma-to-linear helper.

With CMS disabled, no embedded ICC, an unusable profile or a failed shared conversion, this branch publishes the original normalized source bits as `RGBFLOAT32` with the existing `GAMMA` marker. These unmanaged device values are not a color-correct replacement for an unavailable ICC conversion. A failed direct-linear conversion does not retry the adapter's legacy ICC helper. Existing shared profile-factory behavior is unchanged; this is not a general guarantee that every native profile-construction failure is fatal or prevents all common-layer fallbacks. The ColorSync preparation failure caused by an invalid native-gamma setting retains its diagnostic while the TIFF loader keeps its existing successful unmanaged-frame fallback.

The direct-linear RGB16 path does not expand TIFF gray, IEEE float, Lab, byte, alpha, planar, tiled or orientation 5–8 support. TIFF CIELAB16 has the separate signed-word contract below. Eligible IEEEFP32 has the separate source-preservation and direct-linear contract above; the libtiff RGBA8 fallback remains a distinct precision boundary. TIFF WhitePoint/PrimaryChromaticities/TransferFunction metadata is not newly interpreted by the RGB16 path, and multi-directory handling is not added.

The [literal fixtures and independent values](../../tests/data/color-numeric/tiff-rgb16.json) come from an [offline serializer and oracle](../../tools/generate_tiff_fixtures.py) that does not call libtiff, libsixel or another CMM. It evaluates the original ICC fixed-point TRC/XYZ tags and the first binary32 normalization of each integer with 80-digit Decimal arithmetic and a cofactor inverse, then rounds the expected linear result to binary32. The original six-pixel P3 fixture and its 18 expected components are retained; separate dark/knee and ordinary sRGB fixtures supplement it. Runtime tests require the public frame, coordinates, exact unmanaged source bits, actual libtiff selection and actual requested CMS application, rather than deriving expected values from a production CMS roundtrip.

Numeric tests reuse the existing per-triplet magnitude policy. The builtin/LCMS2 relative allowance is `64 * 2^-24` (`3.814697265625e-6`), matching `color_gray_float_relative`; the ColorSync allowance matches `color_rgb_power_relative` (`0.00032384445817172029`) and its fixed-point matrix/float composition. Each component's error is bounded by the maximum absolute expected component in that pixel times the allowance. There is no absolute floor for dark pixels, and black must be exactly zero. These are declared test allowances, not proven error bounds for opaque native CMS arithmetic. A preparation-failure test requires the ColorSync-specific diagnostic as well as original bits and the unmanaged frame type, so merely disabling CMS cannot satisfy it. Partial-write native-apply failures are a separate shared-helper atomicity concern.

Canonical frame accuracy and final displayed SIXEL quality are separate measurements. Retaining an out-of-range linear component does not by itself prove an improvement after display-gamut handling, palette reduction and dithering.

### TIFF CIELAB16 signed input contract

For eligible high-precision TIFF input with `PhotometricInterpretation=8` (CIELAB), L is an unsigned 16-bit value, normalized internally as `L/65535`. The a/b words are two's-complement signed 16-bit values: physical a/b is `signed_word/256`, and the shared `LAB_F32` representation is `signed_word/32768`, equivalent to physical a/b divided by 128. This is the storage convention documented by [libtiff's TIFFCIELab16ToXYZ](https://gitlab.com/libtiff/libtiff/-/raw/v4.7.2/libtiff/tif_color.c). The container type and the interpretation are separate: retaining the decoded bit pattern in `uint16_t` is valid, provided a/b is subsequently interpreted with this signed rule. The loader widens the word to `int32_t` and subtracts 65536 at or above 32768, avoiding an implementation-defined narrowing cast. File byte order does not change the decoded values.

| Component and stored word | Physical Lab value | Internal normalized value |
| --- | --- | --- |
| L `0x0000` / `0xffff` | 0 / 100 | 0 / 1 |
| a/b `0x0000` | 0 | 0 |

The loader applies this storage contract before handing samples to a CMS or the existing no-ICC fallback. A successful ICC conversion follows the direct-linear publication contract below; an untagged input uses the existing D65 Lab fallback and publishes `RGBFLOAT32`/`GAMMA`. These output policies are separate from signed-word decoding. The contract does not add ICCLAB (`PhotometricInterpretation=9`), change float32 Lab heuristics, or expand the existing strip/orientation/extra-sample eligibility. It requires no new high-precision arithmetic dependency.

The contract, decoder, fixtures, oracle and public-frame tests must agree. The [offline generator](../../tools/generate_tiff_lab16_tests.py) fixes literal raw words and their physical values from this storage contract, then derives expected RGB with independent Lab/XYZ/matrix/transfer formulas. Expected values are independent of the implementation under test, not independent of the storage contract; they are never obtained by reversing the decoder or measuring another CMM. The [fixture/value record](../../tests/data/color-numeric/tiff-lab16.json) retains source words, normalized values, profile hash, endian fixture hashes and numeric intervals. `python3 tools/generate_color_fixtures.py --check` verifies deterministic regeneration together with the other color fixtures.

Public-frame tests protect a/b zero, sign boundaries, one storage LSB, unsigned L endpoints, both byte orders, metadata and actual requested CMS execution. Four untagged tests cover all signed extrema and additional +/-64 physical chroma values that distinguish division by 32768 from division by 32767. Six ICC tests cover the three engines in both byte orders, checking eleven interior/neutral/L-endpoint pixels numerically and all fifteen pixels for finiteness. Their existing path-specific allowances remain unchanged: builtin relative 64-binary32-unit roundoff, LCMS one encoded Lab bin plus the relative allowance, and ColorSync the existing canonical/stored-linear-profile interval. Extreme-chroma equivalence across all native engines is not asserted by these ICC tests. The stricter untagged public values protect one-LSB preservation even where an ICC quantization interval could accept its loss. These are value and route contracts; final palette quantization and perceptual image quality are separate measurements.

### TIFF Lab direct-linear publication and recovery

Eligible TIFF CIELAB16 and float32 CIELAB inputs retain their established storage-to-facade interpretation. The facade carries `L/100`, `a/128` and `b/128`. When an applicable embedded Lab profile converts successfully, the loader publishes the complete finite result directly as linear sRGB in `LINEARRGBFLOAT32`/`LINEAR`. Finite negative components and components above one are retained without adapter clipping or an intervening gamma RGB representation. The selected CMS still owns profile evaluation and its own device-domain rules.

The shared linear helper publishes output only after the entire transform succeeds and every output component is finite. Source/profile mismatch, failure to allocate the CMS result buffer, failed transform creation or application, and a successful native call producing non-finite output leave every original normalized source sample unchanged. No second CMS transform is attempted by this helper. A recoverable failed Lab conversion therefore enters the existing D65 Lab-to-gamma-RGB fallback using those original Lab samples and publishes `RGBFLOAT32`/`GAMMA`. The same fallback applies when no applicable profile is available. This does not promise recovery from allocation failures that prevent TIFF decoding or frame construction itself.

This publication guarantee belongs to the linear helper and this TIFF caller. Low-level CMS operations and the older sRGB helper retain their own failure contracts. The change does not expand alpha/extra-sample, strip, orientation, ICCLAB or float-input eligibility. The CIELAB16 two's-complement storage table, literal raw inputs and untagged conversion contract remain unchanged. The result buffer costs twelve bytes per pixel (94.92 MiB at 3840 by 2160), in addition to existing decoder and native buffers; it requires no new arithmetic library.

Normal numerical and metadata tests invoke the ordinary library through the public loader. Failure tests compile the actual CMS and TIFF source under test-only names and replace selected dependency calls locally. They demonstrate publication and recovery after a deliberately injected failure; they do not claim a naturally failing finite profile or failure atomicity in the external CMS. Neither runtime options nor environment-controlled fault switches are added. Injection qualification (a real converted prefix or the identified result allocation) and source/frame preservation are asserted separately. A successful native call containing NaN or infinity separately protects the helper's finite scan.

The independent linear expectations start from prescribed physical Lab values and D50 Lab-to-XYZ equations. Builtin uses the canonical inverse RGB matrix with its existing triplet-relative 64-binary32-unit allowance. LCMS propagates the existing one encoded Lab bin through monotone XYZ intervals and signed inverse-matrix rows, then adds that same relative allowance. ColorSync retains canonical, independently serialized matrix and D50-row-normalized matrix interpretations with its existing `max(1, triplet magnitude) * 64 * 2^-24` allowance. These are scoped test intervals, not a universal native-CMM error bound. No gamma encode/decode or unit-range clamp participates in these linear expectations.

Retaining extended linear values protects intermediate processing. This contract does not guarantee a perceptual improvement after final palette quantization, equality between CMS engines, or a corpus-wide image-quality improvement.

### Normalized float input units at the LCMS boundary

The common `CMYK_F32` representation stores ink amounts in `[0,1]`; `LAB_F32` stores `L/100`, `a/128`, and `b/128`. For an LCMS transform into `RGB_F32`, the adapter converts these to the native formatter units: ink percentages, or physical `L`, `a`, and `b`. Linear and gamma RGB destinations use the same input adapter. This is a representation conversion, not an additional color transform.

A bounded 256-pixel stack buffer copies and scales a complete input batch before native conversion. Separate inputs remain byte-identical. Exact aliases are supported for these two source layouts because CMYK-to-RGB contracts storage and Lab-to-RGB preserves it; bytes outside the RGB output span remain unchanged. Source and destination byte-count overflow is rejected before any output write. This does not establish support for partial overlaps or other expanding aliases.

The adapter adds no device-domain or intermediate RGB clamp. Native handling of out-of-domain and non-finite device inputs is retained. The native sRGB parametric inverse uses a linear extension for negative values; this change does not replace that extension with the builtin endpoint's sign-symmetric transfer function. Other CMS engines and Lab/CMYK destination-unit contracts are outside this adapter.

[`tools/generate_lcms_input_tests.py`](../../tools/generate_lcms_input_tests.py) independently reads the original identity Lab LUT8 and the existing synthetic affine CMYK LUT16. The numerical tests compare against intervals propagated from one encoded input grid bin, two u1.15 PCS bins for the CMYK LUT, and the existing 64-binary32-unit-roundoff triplet allowance. Lab intervals pass through the physical Lab-to-XYZ equations; signed inverse-matrix rows propagate XYZ intervals to RGB. Gamma intervals use the native sRGB inverse's mathematical definition. These intervals include the unquantized ideal, so a future engine with less quantization error also passes. They are scoped test allowances for these profiles, not a universal native-CMM error proof. The verified LCMS table quantization residual is not treated as an input-unit defect.

Each source/target/alias condition checks 521 pixels, with different sample sequences across batch boundaries, actual LCMS application, complete separate-input immutability and output/alias-tail guards. Independent public-frame tests cover profiled PSD32 main composites, one-layer missing composites, two-layer normal composition, and the original float Lab TIFF. The PSD fixtures retain inverted binary32 ink planes and exercise half-opacity linear composition in the two-layer case. The TIFF test follows the direct-linear publication contract and retains finite extended RGB values. These value contracts are separate from perceptual image-quality measurements.

### LCMS expanding exact aliases

For an LCMS destination of `RGB_F32`, the source formats `GRAY_8`, `RGB_8`, `RGBA_8`, `CMYK_8`, `CMYK_16` and `GRAY_F32` require separate input and output buffers. A call with identical starting pointers is rejected before native conversion and before any buffer write. This applies to every positive pixel count, including one pixel: the previous incidental one-pixel success is now rejected consistently with larger images. Transform creation and separate-buffer conversion remain supported.

The native [LCMS 2.19 tutorial](https://github.com/mm2/Little-CMS/blob/lcms2.19/doc/LittleCMS2.19%20tutorial.pdf), page 14, guarantees shared buffers only for matching input/output formats. Passing these expanding layouts directly to its forward conversion can overwrite unread input while the facade reports success. The preflight emits `LSXCMS2|event=reject|engine=lcms2|reason=expanding-alias|src=...|dst=4`, followed by the normal apply trace with `ok=0`. The existing null/zero-count behavior, other backends, same-format transforms and the adapted `CMYK_F32`/`LAB_F32` exact aliases keep their own contracts. This rule does not define partial-overlap behavior, other destination formats or general failure atomicity.

The twelve format/destination tests first require successful separate conversion with independent values and intact source/output guards, then require whole-arena preservation for rejected aliases at 1, 2 and 521 pixels. [`tools/generate_lcms_alias_tests.py`](../../tools/generate_lcms_alias_tests.py) reuses the existing P3, affine CMYK and gamma-2 gray specimens. Linear allowances retain the existing RGB/CMYK absolute float budget, the two-bin PCS allowance for interpolated CMYK samples, and the gray relative budget with exact black. Gamma intervals propagate those linear bounds through the native sRGB inverse, including its linear negative extension, with a triplet float-operation allowance. They are declared fixture-specific allowances, not values learned from the production transform. This low-level rejection does not establish a current CLI image-quality improvement.

### Normalized Lab float input at the ColorSync boundary

The common `LAB_F32` contract is `L/100`, `a/128`, and `b/128`. A ColorSync transform into `RGB_F32` copies L and maps each opponent component to `value * (128 / 255) + 0.5` before native conversion. Native float Lab has a neutral opponent coordinate of 0.5 in this path. This mapping differs from both LCMS physical Lab units and ICC LUT unsigned coordinates with an offset of 128. Linear and gamma RGB destinations share this representation adapter.

A 256-pixel stack batch retains all source components before writing its RGB result, preserving separate inputs and same-start exact aliases. Existing byte-count overflow checks run before conversion. The adapter adds no clipping, alternate CMS or device-domain rejection. Native non-finite rejection still returns failure; a later batch failure can leave earlier batches converted, so this low-level operation does not promise atomic output on failure. Other source/destination formats, partial overlaps, factory definitions, rendering-intent selection and the existing ColorSync gamma compatibility option keep their separate contracts.

[`tools/generate_colorsync_lab_tests.py`](../../tools/generate_colorsync_lab_tests.py) defines fixed independent linear and parametric-sRGB target ICCs for four numerical input/alias conditions. Neither the targets nor their expected values come from the production profile factories. Original Lab samples, neutral endpoints, lightness-knee neighbors and opponent-axis samples exercise 521 pixels with different sequences across the 256-pixel boundaries. Independent Decimal Lab/XYZ, serialized matrix and signed parametric-inverse equations supply value intervals. Those intervals retain both ideal and legitimate stored-profile interpretations, with a scoped binary32 arithmetic allowance; they are not a universal ColorSync error bound or a native-output golden.

The separate TIFF public-frame test exercises the real linear-sRGB factory and direct-linear publication. Its expectation uses the original samples, independently derived ideal sRGB and the fixed linear target's serialized matrix interpretations. It never learns an expected matrix or output from the factory during the test. Native profile differences on another OS require a scoped review rather than automatic reference replacement. The existing generated-linear-primary test separately checks the linear factory against fixed independent P3-to-sRGB values. Direct-native passthrough comparisons protect compatibility behavior, not independent factory color accuracy.

### Normalized Lab float input to builtin RGB endpoints

The CMS facade represents `LAB_F32` as `L/100`, `a/128`, and `b/128`. Before the builtin float RGB endpoint evaluates an ICC device table, it maps each normalized a/b component with `(value * 128 + 128) / 255` and bounds that device coordinate to `[0,1]`. The signed facade representation is not itself a LUT coordinate. This boundary applies to both linear and analytic gamma RGB destinations, including aliased input/output buffers. Legacy device transforms retain their existing input normalization; they must not receive a second mapping.

The [original float Lab TIFF](../../tests/data/colormgmt/input/custom/lab_high_precision_icc.tiff) contains a v2 Lab-to-Lab profile with identity `mft1` tables. Its numeric tests distinguish the original normalized samples, encoded LUT inputs, physical XYZ under PCS D50, signed float RGB endpoints, and the direct-linear TIFF frame. The loader-independent CMS tests run even when libtiff is disabled. They do not establish a general TIFF float Lab encoding rule, expand TIFF Lab input eligibility, or add absolute-intent/media-white processing. LUT8 PCS encoding is defined in [ICC.1:2001-04, section 6.5.8 and Annex A](https://www.color.org/specification/ICC.1-2001-04.pdf).

### Independent TIFF ICC references

[`tools/generate_tiff_icc_tests.py`](../../tools/generate_tiff_icc_tests.py) reads the original TIFF raster/profile bytes without libtiff or a CMM. Curve expectations follow [ICC.1:2022 Table 68](https://www.color.org/specifications/ICC.1-2022-05.pdf#page=85), including clipping to the specified curve range. Vector comparisons scale to the largest expected component magnitude, while scalar curves scale to their expected magnitude. Black is exact and there is no absolute dark floor. The Lab quality test retains its separate existing SIXEL reference. ## LogLuv stored-coordinate and exposure policy

For TIFF LogLuv (`PhotometricInterpretation=32845`) with SGILOG or SGILOG24 compression, three contiguous channels, strips, no extra samples and orientation 1–4, the libtiff loader requests `SGILOGDATAFMT_FLOAT` and converts the decoded numerical XYZ coordinates directly into the canonical linear-sRGB destination basis. It preserves the stored exposure scale and finite negative or above-one RGB components. The published default is LINEARRGBFLOAT32/LINEAR. `cms_target` selects a subsequent float frame representation; `prefer_8bit` is an explicit final byte boundary. Disabling ICC/CMS does not disable native XYZ interpretation.

This is a stored-coordinate loader policy, not an assertion that every file contains unadapted absolute scene colorimetry. The D65 white in the destination matrix specifies the output RGB basis, not the source illuminant. The loader performs no chromatic adaptation, WHITEPOINT reconstruction, normalization by luminance, StoNits multiplication, ICC reinterpretation or tone mapping. In particular, an optional E-normalized authoring convention can encode intended white as XYZ=(1,1,1); preserving those coordinates will not render that vector as neutral sRGB white. This can visibly differ from libtiff's former approximate E-neutral, gamma-2.0 display path. The policy does not establish perceptual superiority for arbitrary input images.

The codec's FLOAT pseudo-tag selects the application interface; it does not mean that float XYZ triples are stored in the file. SGILOG and SGILOG24 quantize log luminance and chromaticity differently, and the loader preserves the decoded cell centers rather than undoing that loss. The float decoder also maps nonpositive encoded luminance to black; the loader cannot recover it. This differs from retaining negative RGB coordinates derived from positive decoded XYZ. StoNits, when present, calibrates decoded Y=1 to cd/m². The relative RGB frame has no corresponding absolute display-luminance contract, so the tag does not rescale its pixels. WHITEPOINT and embedded ICC similarly do not alter this native-coordinate mapping; no profile is applied to XYZ as if it were RGB or to the already converted RGB a second time.

Unsupported tile, planar, extra-sample or orientation layouts retain existing fallback behavior and its limits; fallback does not imply support for every malformed or rotated layout. Eligibility is checked before the FLOAT pseudo-tag changes decoder state. Once that request begins, failed interface validation, size checks, allocation, scanline reads, finite-value checks or final target conversion fail the load without a callback. The loader does not retry the RGBA decoder after a partially changed or consumed LogLuv decode. Only this native LogLuv route applies the new post-initialization target step; other TIFF routes retain their contracts.

The regression oracle separates codec quantization from loader arithmetic: prescribed XYZ values and actual packed words determine decoded centers independently, then a matrix derived from sRGB primaries and destination white determines expected linear coordinates. Encoding error is not absorbed by widening the existing floating-point arithmetic budget. The [libtiff codec source](https://gitlab.com/libtiff/libtiff/-/raw/v4.7.2/libtiff/tif_luv.c) and [original LogLuv description](https://www.anyhere.com/gward/pixformat/tiffluv.html) describe the storage and calibration conventions.

### Behavioral contract tests

Generated ColorSync RGB profiles preserve the requested primary matrix: each primary's XYZ column is supplied in the CoreGraphics calibrated-RGB layout. The linear-sRGB output probe checks actual P3 ICC transformation against independent 8/16-bit source oracles, including negative and above-one components, with an absolute 0.0001 linear-component bound for the generated profile's rounding. This CMS-only probe does not establish that a PNG loader preserves those components.

Builtin float transforms into analytic sRGB or a synthetic RGB definition connect through physical XYZ D50. Original parametric RGB TRC coefficients are evaluated without the legacy 16-bit table approximation, native RGB white points are adapted once, and finite negative/above-one intermediate RGB is preserved. ICC device curves and LUT domains remain bounded; byte export and arbitrary ICC output-device endpoints retain their existing bounded contract. The independent 8/16-bit P3 sample tests use an absolute 0.0000005 linear-component bound, including float input/storage rounding. These CMS-only guarantees do not imply that every loader, alpha compositor, or frame conversion already preserves the result.

The floating-point `sixel_cms_convert_profile_to_linearrgb()` helper requests linear sRGB directly from the selected profile backend. It accepts RGB or replicated gray source samples, packs gray into the CMS's one-channel float format, and publishes only a complete finite RGB result. ColorSync may apply two disjoint groups when normalized and extended pixels need different preparation. A failed group leaves the caller's original samples intact for the loader's existing metadata-fallback policy; failure never starts another group or retries converted pixels.

The gray oracle is a complete D50 input profile with the independent kTRC definition `y = x^2`. Gray tests include black, the smallest positive 16-bit samples, dark values, adjacent samples around the native gamma-2 toe at 1/16, midtones, and white for six stored exponents from 0.5 through 4. Black must be exactly zero. Positive values use a relative error budget without an absolute floor: 64 binary32 unit roundoffs for normalization, curve/matrix evaluation, and storage; ColorSync additionally allows the independently propagated gain error from one s15Fixed16 bin per PCS-white and output-matrix coefficient.

The matrix term assumes each coefficient error is at most one bin. The float budget is a test-design allowance, not a proven error bound for ColorSync's private `pow` or matrix implementation. The two relative terms combine as `(1 + matrix_budget) * (1 + float_budget) - 1`, including their product. The budget and inverse-matrix norm are recorded in [gray-samples.json](../../tests/data/color-numeric/gray-samples.json). This neutral-gray contract scales with brightness and therefore detects complete loss of even the smallest sample; it does not reuse the absolute P3 RGB tolerance.

By default, for a ColorSync gray source with a valid ICC v4 pure-gamma `kTRC` (`para` type 0 or a positive one-entry `curv`) and no device-to-PCS LUT, this helper uses a private native profile copy with the equivalent type-3 parameters `[g, 1, 0, 0, 0]`. This spelling preserves `x^g` for the normalized nonnegative PNG samples; it does not define a general negative-domain extension. ColorSync otherwise inserts a linear toe into this tag form, changing dark samples even with best conversion quality. The adapter validates the exact tag length, reserved fields, positive exponent, profile version, and source range, then applies the normalized group natively and releases the copy. A mixed call can also apply a separate original-curve extended group. Single-gamma `curv` accepts a 14-byte payload or a 16-byte payload with two zero alignment bytes. The u8Fixed8 exponent is mapped exactly to s15Fixed16 by integer scaling; no floating-point library or source-sample recalculation is involved. RGB pure-power preparation accepts the same `curv` forms, including mixed parametric/curv channels, and serializes the decoded exponent after any sample/matrix channel permutation. Fifteen-byte tags and nonzero padding retain unprepared native behavior. It does not change the caller's profile or rewrite v2, table, segmented, LUT, or already-piecewise curves.


The generic direct-linear entry and the strict native entry share RGB source preparation for ICC v4 Input/Display profiles with XYZ PCS, complete matrix/white tags and no A2B0–A2B2 or D2B0–D2B3 forward LUT. By default, for a triplet entirely in `[0,1]`, exact positive pure-power curves in parametric forms 0, 3 (`[g,1,0,0,0]`), and 4 (`[g,1,0,0,0,0,0]`), or the single-gamma `curv` forms above, use equivalent type 3 parameters. This prevents the native pure-gamma toe from changing the declared power. When blue is exactly identity and another channel is not, preparation also exchanges blue with red (or green if red is identity), moving both the original float bits and the corresponding XYZ/TRC payloads together. This permutation also applies to finite triplets outside the normalized domain, but those triplets retain their original curve bytes in every channel. All-identity profiles and profiles with nonidentity blue need no sample exchange; an already-type-3 profile with no exchange uses the original source directly.

Preparation retains the caller's profile and its ID. An owned native copy has its ID cleared, and all other tags and header fields except serialized size are preserved. The copy outlives its borrowed transform. Sample exchange allocates a buffer only when needed and uses bit copies, without a transfer decode, coefficient recalculation, clamp, or intermediate byte quantization. Missing or ineligible tags keep their original native interpretation; failure to copy an existing required tag, create or verify a replacement, allocate needed storage, or finish a finite native result fails atomically. The strict entry preserves global engine state and uses ColorSync; the generic entry still requires a compatible destination backend. Neither entry retries through another CMM.

The [RGB power fixture record](../../tests/data/color-numeric/rgb-power.json) fixes the original binary32 samples, serialized s15Fixed16 exponents and XYZ columns, and independent linear-sRGB expectations. It covers all eight identity placements in three pure forms, exponents adjacent to one, uniform fractional/integer exponents, and a different source white with wide primaries. Black is exact; other triplets use maximum component error divided by maximum absolute expected component, with the same independently derived native relative allowance as the gray tests. The bound applies to these matrices and original 16-bit sample vectors, including their smallest positive samples. It is not a guarantee for arbitrary floating-point ICC inputs: native ColorSync can still lose subnormal results or accumulate substantial error under large matrix coefficients and cancellation, even when its input bits are preserved. Named sRGB/ordinary Display P3 piecewise curves, gray, v2, forward-LUT and nonpure curves are outside this RGB preparation. Out-of-range RGB triplets are excluded from curve rewriting, while the equivalent permutation retains their original curves.

For a component permutation `P`, exchanging both the curve results and their matrix columns preserves `(M P^-1)(P f(x)) = M f(x)`. Each original curve still receives its own original component. This equivalence does not define a new negative power or change the native curve extension. The serialized source ICC, borrowed profile and source sample words remain unchanged; only a private profile and bit-preserving sample order are used at native entry. These controls address a specific native identity-blue failure and do not guarantee arbitrary native profiles or arithmetic.

A mixed eligible call stable-packs at most two groups and scatters their completed results back to original pixel positions. Normalized-group failure or nonfinite output prevents the extended group from starting. Extended preparation, allocation, creation or apply failure likewise discards the entire result. The first transform is deleted before its prepared profile and sample buffer are freed; the second profile is prepared only afterward. There is no per-pixel transform creation or retry after failure. Native profile/factory selection rules otherwise remain unchanged.

Grouping has a real cost. For four-byte samples, mixed adapted RGB adds `24*N` bytes for source packing and grouped output, plus up to `12*max(U,N-U)` for a needed permutation, where `U` is the normalized pixel count. Mixed Gray adds `16*N` bytes. Pure extended RGB requiring permutation adds `12*N` bytes and a private native profile. A mixed non-target RGB profile still incurs `12*N` bytes of packing before eligibility is known (Gray: `4*N`), including that allocation-failure boundary, although it uses one native apply. Classification, packing, scattering and additional native setup are not free. Improved linear values may disappear at final palette quantization; these contracts do not assert universal perceptual improvement.

The independent [curv fixture record](../../tests/data/color-numeric/curv-samples.json) reads stored exponents and XYZ values back before calculating expected colors. Native numeric coverage is limited to the listed normalized samples, matrices, and gamma values up to four, using the existing relative matrix/float budget with exact black. Exhaustive integer exponent encoding covers all positive u8Fixed8 words, but does not imply native numeric accuracy for every such gamma.

The independent [color fixture generator](../../tools/generate_color_fixtures.py) supplies descriptive/copyright tags and the D50 media white for its normal ICC v4 fixtures. The Display P3 matrix profile also records its D65-to-D50 chromatic adaptation; the forward-only LUT uses Input (`scnr`) class, while the paired LUT retains Display (`mntr`) class. These structural corrections leave the encoded matrix, TRC, and LUT payloads and their independently computed numeric expectations unchanged. The `minimal-*.icc` files preserve the exact older M0 envelopes for permissive builtin acceptance only; neither their acceptance nor native profile verification substitutes for testing an actual color transform. The [fixture manifest](../../tests/data/color-numeric/manifest.json) records the separate roles and byte hashes.

ColorSync integer Gray8, RGB/RGBA8, and CMYK8/16 input to float RGB uses an explicit adapter path: normalize the original integer channels by 255 or 65535, retain the RGBA alpha layout without applying a color transfer to alpha, then apply ColorSync to homogeneous float buffers. This avoids the observed native mixed-depth conversion failure. The adapter processes bounded batches and reads aliased expansions from the end; it does not select another CMS or quantize through RGB8. Trace reports `event=source-promotion` separately from successful `event=apply` with the original API formats. Direct tests pass original byte/word arrays, use 521 pixels to cross batch boundaries, and verify backend identity and output guards. Gray8 tests separately retain a gamma2 byte26/253 pair and use an independent identity Gray profile for all 256 byte values, both fixed linear and gamma targets, and counts 1, 2, 255, 256, 257, and 521. Their [independent record](../../tests/data/color-numeric/colorsync-gray8.json) models ideal neutral D50 and stored target matrix/TRC interpretations with a relative triplet `64*2^-24` margin and exact black. This checks integer normalization and buffer handling; it does not assert raw native gamma2 dark-curve conformance or a CLI image-quality improvement.

ColorSync integer-promotion and Lab-unit scratch adapters require the native ICC source colorant count to match their input layout before any source or destination write. The count comes from the native profile data-space signature; RGBA alpha is not a colorant. XYZ and matching 3CLR/4CLR profiles remain native even though the common profile-domain enum reports UNKNOWN. Unavailable, short or unrecognized native headers cannot establish a safe scratch layout and are rejected by these adapters. Creation and the non-adapter paths keep their backend decisions. This check does not establish semantic equivalence between different color spaces with the same number of components. A rejected adapter call reports `reason=native-source-channels` with its native and expected counts and a failed apply result. [Independent numeric controls](../../tests/data/color-numeric/colorsync-channels.json) retain the existing precision intervals; [XYZ controls](../../tests/data/color-numeric/colorsync-channel-scope.json) derive values from stored ICC colorants. The [Apple header API](https://developer.apple.com/documentation/colorsync/colorsyncprofilecopyheader%28_%3A%29?language=objc) returns host-endian fields; the ICC data-space field is defined by [ICC.1](https://www.color.org/specification/ICC.1-2022-05.pdf).

For RGB_F32 output, recognized source pixel formats must match a known source-profile domain: Gray8/Gray_F32 require Gray, RGB8/RGBA8/RGB_F32 require RGB, CMYK8/CMYK16/CMYK_F32 require CMYK, and LabF32 requires Lab. A backend may reject transform creation; otherwise the shared apply preflight rejects a mismatch before any source or destination write, including exact aliases. Its `reason=source-profile-format` trace identifies the actual engine, source and destination formats, actual profile domain, and expected domain. UNKNOWN profile domains, unrecognized format enums, and other destinations retain their backend rules, including the ColorSync native-channel check above and the builtin byte convenience conversions. Matching profiles retain their existing numeric intervals and engine selection; no new transfer function, precision mode or clipping rule is introduced. [Independent matched controls](../../tests/data/color-numeric/profile-format.json) protect all three engines and nine formats for both RGB float targets.

Builtin PSD32 composite, missing-composite layer, and two-layer decoding retain original-input recovery after a rejected ICC transform. [Independent fallback values](../../tests/data/color-numeric/profile-format-caller.json) derive device RGB from the original stored CMYK inks, decode sRGB, and apply normal layer opacity in linear light. Correct-profile controls use the [existing ColorSync affine-PCS intervals](../../tests/data/color-numeric/profile-format-valid-caller.json). The public frames retain linear RGB_F32 values and their dimensions; an invalid ICC has no implied colorimetric ground truth.

The builtin PSD layer decoders retain their original-input fallback when the ICC transform fails: CMYK8 returns gamma RGB bytes with integer rounding, while CMYK16 returns linear RGB floats after the device fallback and sRGB decoding. [Independent typed expectations](../../tests/data/color-numeric/colorsync-channel-caller.json) check both this result and the public frame format for inconsistent ICC metadata. This fallback is a defined recovery behavior, not a colorimetric reference for an invalid profile.

The independent CMYK fixture is a synthetic D50-referred affine input model, not a real printer characterization. Its complete v4 Input profile contains A2B0/A2B1, identity mft2 matrix, D50 white, and descriptive/copyright tags. Explicit `relative!` selects A2B1 for comparison with the original integer samples and independently computed physical XYZ; perceptual processing has no numeric oracle here. Integer-affine CLUT vertices avoid depending on a particular multidimensional interpolation choice. Builtin float PCS and external vertex samples use a 0.0000005 RGB bound; ColorSync instead uses its existing 0.0001 generated-profile precision bound. Interpolated external LUT samples additionally allow two u1.15 PCS bins propagated through each absolute row sum of the independent XYZ-to-linear-sRGB inverse matrix. The [CMYK record](../../tests/data/color-numeric/cmyk.json) gives the calculation, source8/source16 integers, profile hash, and expected XYZ/RGB. A separate 256-entry input-curve knee retains an observable distinction between original word 32768 normalized by 65535 and an incorrect divisor of 65536; its expected values are derived from the explicit table interpolation formula. This bound is specific to fixed-point LUT interpolation and is not applied to matrix/TRC tests or MS-SSIM thresholds.
