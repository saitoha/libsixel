# libtiff image loader

The `libtiff` adapter reads a TIFF image through libtiff, with precision-preserving direct readers for selected layouts and an RGBA convenience path for other supported combinations. TIFF is a family of sample organizations and codecs: successfully reading one TIFF does not establish support for all compression, photometric, alpha, or planar combinations.

```sh
img2sixel -L 'libtiff!' image.tif
img2sixel -L 'libtiff:cms_engine=builtin!' image.tif
```

`!` fixes the backend for inspection. Compression availability depends on the linked libtiff build. This adapter processes the current image directory and does not enumerate pages into an animation; `-T` is not a TIFF page selector here.

The [selected Display P3 output path](../encoder/output/output-colorspace.md#display-p3-selected-cpu-float-path) connects opaque static RGB samples through builtin CMS, CPU float K-means and exact lookup to final P3 RGB101 SIXEL. Its explicitly selected libtiff cases do not extend this guarantee to every source domain or encoder policy.

## Precision and fallback inside the adapter

| Route | Scope |
| --- | --- |
| High-precision scanlines | Selected contiguous RGB/grayscale 8/16-bit integer or float32 layouts, separate-strip RGB/Gray UINT16, and selected 16-bit/float32 CIELAB layouts, without extra alpha samples. Supported orientation and scanline-layout checks also apply. |
| Original integer layouts | RGB/Gray UINT8/UINT16 or VOID strips or two-dimensional tiles, contiguous or separate, orientations 1–8; one declared associated/unassociated alpha extra is optional. Low-bit Gray and indexed ColorMap16 also retain original source values. |
| `TIFFReadRGBAImageOriented` | The general libtiff conversion fallback for combinations outside the direct path. Its RGBA result is an 8-bit representation; later promotion to float32 does not recover discarded source precision. |
| Loader-manager fallback | A different backend may be tried only according to the shared failure/callback rules. This is separate from choosing libtiff's internal RGBA route. |

The established high-precision CIELAB path keeps typed Lab as an internal source representation until CMS is attempted. Successful CMS conversion publishes `LINEARRGBFLOAT32` / `LINEAR`; when ICC conversion is inapplicable or fails, the existing Lab-to-gamma-RGB fallback publishes `RGBFLOAT32` / `GAMMA` if that fallback succeeds. The emitted frame does not retain the internal Lab representation. RGB/gray paths and profile conversion have their own normalization. Inspect emitted `pixelformat` and `colorspace`; a `.tif` extension is not sufficient to infer either.

TIFF orientation is handled in the decode paths. The direct path has narrower layout/orientation eligibility than the convenience reader, so changing tags can change both geometry handling and precision route. This backend does not expose the JPEG-style `orientation` suboption in the current registry.

## Color and alpha

`cms_engine=...` (`E`) selects the TIFF CMS engine; the environment fallback is `SIXEL_LOADER_LIBTIFF_CMS_ENGINE`, then shared CMS policy. Embedded ICC use depends on photometric interpretation and source/profile compatibility. The adapter contains separate handling for grayscale, RGB-like RGBA data, original CMYK components, and high-precision/Lab paths. Do not assume all TIFF photometric models share an identical transform.

Eligible RGB/Gray8/16 alpha-bearing layouts use original samples under the [original alpha contract](#original-integer-alpha-and-composition). Other accepted alpha layouts retain the RGBA convenience path and its precision limitations. Request [alpha/background policy](alpha-policy/README.md) explicitly when comparing decoders; successful compressed-image decoding does not establish preservation of original association or sample depth.

The `libtiff` loader reads TIFF through the linked libtiff library. Its adapter implements selected high-precision scanline paths and uses libtiff's RGBA8 decoder for other accepted inputs. Successful TIFF decoding does not establish that an embedded ICC profile was applied or that the original precision and gamut survived.

This page records the adapter's implemented and missing paths. The detailed numerical and failure contracts remain in [Loader Color Management](color-management/README.md). Loader selection and fallback between components are described in [Image loader architecture](README.md).

## Format and color-management support

“Implemented” below identifies an adapter path, subject to its stated conditions and the selected CMS engine's profile support. “Not implemented” identifies a missing adapter path even when libtiff can decode the image. “Unverified” means that the table does not establish acceptance or numerical correctness for that condition. These statuses distinguish an implementation omission from an unavailable optional library or an explicitly disabled CMS.

The **high-precision layout** is contiguous strips, orientation 1–4, no extra samples, and exactly three RGB/Lab samples or one grayscale sample per pixel. Compression support is supplied by the linked libtiff codec. `SAMPLEFORMAT_VOID` retains the adapter's unsigned-integer interpretation. RGB/Gray UINT16 and CIELAB16 also accept separate strips under those same channel, extras and orientation conditions. The LogLuv row has its own codec and sample conditions.

A failed high-precision operation is distinct from an unsupported combination: after a supported decode has begun, errors can terminate the load instead of trying RGBA8 again. In particular, native LogLuv checks layout eligibility before requesting its floating-point codec interface and does not retry RGBA8 after that state change.

## Missing CMS integration and fallback

LOGL source precision and color management remain unsupported. Floating-point Lab outside the established contiguous/no-extra/orientation 1–4 gate, ICCLAB/ITULAB depths other than eight bits, arbitrary N-ink separations, and unsupported extra-sample declarations remain outside the implemented original-source paths. A libtiff RGBA fallback, where accepted, does not establish source precision or a Lab/CMYK ICC connection for these unsupported models. Native float layouts rejected by libtiff are decoding limitations, not readable-but-unmanaged paths.

The byte ICC helpers intentionally do not apply a Lab/CMYK source profile to already rendered RGB. Supported integer Lab/CMYK layouts now bypass those helpers and supply their original components to the common CMS. The [original-source contract](#original-lab-and-cmyk-coordinates) defines the applicable formats and fallback behavior.

For the implemented 16-bit and float32 RGB/Gray paths, successful ICC conversion publishes `LINEARRGBFLOAT32` / `LINEAR`. With no applicable conversion, they publish their original normalized integer or polarity-adjusted floating-point samples as `RGBFLOAT32` / `GAMMA`. Lab has its own format-specific fallback, including D50 linear decoding for byte Lab. The fallback `GAMMA` marker does not establish calibrated sRGB primaries for a device-specific source. The shared helper publishes only a complete finite result and preserves original samples on failure; it does not make every embedded profile acceptable.

`cms_target` and `prefer_8bit` are not evidence that a particular TIFF branch performed a transform. Native LogLuv, byte Lab, successfully managed eligible RGB/Gray8, the newly connected integer Lab/CMYK layouts and decoded opaque YCbCr8 have an explicit final target-negotiation step; the other paths retain their own publication contracts. Alpha handling after RGBA8 decoding likewise cannot recover the samples lost at the byte boundary.

## Original byte samples and final publication

The direct byte route accepts unsigned 8-bit RGB3 or MINISBLACK/MINISWHITE1 in contiguous strips, without extra samples, in orientations 1–4. Existing VOID-as-UINT interpretation remains supported. Declared byte alpha uses the separate route below, including all-255 alpha. Palette, YCbCr, low-bit, planar/tiled and orientation 5–8 inputs retain their separate limitations.

Each original byte is normalized once into float32. MINISWHITE polarity is applied before its Gray ICC curve. An RGB source requires an RGB profile and a grayscale source requires a Gray profile, consistently with and without external CMMs. A complete, finite ICC result establishes LINEARRGBFLOAT32/LINEAR; the existing frame converter then honors `cms_target` or the deliberate final byte boundary requested by `prefer_8bit`. Negative and above-one managed values survive until an explicitly selected byte conversion.

With CMS `none`, absent, invalid or mismatched ICC, or failed optional CMS work, the complete normalized original source survives. The adapter reconstructs those original bytes exactly and publishes RGB888/GAMMA. It does not publish unmanaged float merely because its decoder used a float workspace, nor does it negotiate a requested target after failed interpretation. This preserves the existing unmanaged downstream precision/lookup selection. The GAMMA marker does not assert calibrated sRGB source primaries. Mandatory decoder allocation/read errors terminate the selected decode without callback or RGBA retry.

A resolved background leaves eligible opaque samples unchanged. Bypassing the RGBA convenience path intentionally removes its former alpha-255 right-shift attenuation, which could darken a component by one byte level even for an opaque input. The alpha route below also bypasses blending for alpha 255.

The decoder allocates 12 bytes per pixel plus a scanline. CMS retains its separate transactional float result and, for Gray, its packed source. Although unmanaged fallback has a 3-byte-per-pixel payload, the compacted allocation retains its original 12-byte-per-pixel capacity until release. This is not a memory reduction and adds no arbitrary-precision runtime library. The [numeric and final-output distinction](color-management/README.md#tiff-original-byte-rgb-and-gray-input) also applies: more accurate intermediate samples do not guarantee a visible improvement after palette quantization.

## Original separate UINT16 strips

The separate-strip reader accepts RGB3 and MINISBLACK/MINISWHITE1 UINT16, including the existing VOID alias, in orientations 1–4 without extra samples. It reads every row of one plane before advancing to the next plane, so compressed multi-row strips need no backwards codec seek. Native-endian source words are normalized once into float32; Gray retains its original one-channel ICC domain despite three-channel frame storage. MINISWHITE reverses the integer polarity before the final float rounding. RGB requires an RGB profile, and Gray requires a Gray profile; this same compatibility guard also applies to contiguous integer sources.

Successful matching ICC conversion publishes the complete canonical LINEARRGBFLOAT32/LINEAR frame. CMS none, absent/invalid/incompatible ICC, optional CMS allocation/factory failure, partial apply failure, or a nonfinite result retains every original normalized word as RGBFLOAT32/GAMMA. A selected separate16 zero/negative/short scanline size, source allocation failure or later row/plane read failure is terminal, with no callback or RGBA retry. The same component and unchanged borrowed input remain usable after the fault. This route retains the existing opaque16 canonical publication under `cms_target` and `prefer_8bit`; it does not introduce the byte/alpha routes' target negotiation.

This specific separate16-strip reader delegates separate8, tiles and integer orientations 5–8 to the [integer layout reader](#original-integer-layouts-and-palette-expansion). Declared integer alpha uses the common alpha policy. IEEEFP32 separate storage and other excluded combinations retain their existing path and live libtiff acceptance. The [literal source table](../../tests/data/color-numeric/tiff-separate16.json) fixes exact original words and integer-only rational-to-binary32 expectations. A matching contiguous16 result qualifies adapter consistency with each CMM; the existing independent CMM numerical tests continue to own arithmetic accuracy.

The visible source allocation is `12N + 2W` bytes for `N` pixels and width `W`. Shared CMS scratch raises the source/result overlap to `24N + 2W` for RGB and `28N + 2W` for Gray; the published payload is 12 bytes per pixel, compared with the RGBA route's final three-byte RGB payload. These counts exclude libtiff, CMM internals and downstream encoder storage. The normalization requires no arbitrary-precision runtime dependency.

Retained source precision can change interpolation and palette selection. Compare final output under identical resize, palette and dithering settings, and distinguish source-value changes from the switch between byte and float processing. A same-byte-level control through the float route is needed before attributing all final differences to the low eight source bits. The contracts guarantee original source retention and adapter consistency, not a universal perceptual improvement.

## Original integer layouts and palette expansion

The integer reader retains source RGB/Gray UINT8/UINT16 or VOID in contiguous/separate strips and two-dimensional tiles, with orientations 1–8. RGB has three color samples; Gray has one. One declared associated or unassociated alpha extra is accepted for these 8/16-bit sources. Additional or unspecified extras, signed/32-bit sources, other photometrics and three-dimensional tiles remain outside this reader and use the existing eligible paths or libtiff fallback. A particular runtime's rejection does not impose rejection on other libtiff versions.

Orientations 5–8 transpose the physical image dimensions from `(W,H)` to `(H,W)`. Their source-to-display coordinates are `(y,x)`, `(H-1-y,x)`, `(H-1-y,W-1-x)` and `(y,W-1-x)`, respectively. Color, original alpha, mask, CMS dimensions and final target conversion share this displayed stride. Separate strips are consumed plane by plane in codec-sequential order. Tiles are read as complete decoded tiles, also plane by plane, and only pixels inside the image dimensions are copied; padded edges do not become image pixels.

MINISBLACK/MINISWHITE 1/2/4-bit inputs expand their original levels before CMS. Packed samples follow the decoded MSB-first order selected by the current `TIFFClientOpen("r")` default; file `FillOrder` has already been handled by libtiff and must not cause another reversal. This bit order is separate from decoded UINT16's native byte order. Every legal low-bit Gray level has an exact RGB888 fallback value. A successful matching Gray ICC conversion retains linear float before final target negotiation.

Palette indices of 1/2/4/8/16 bits address the original three UINT16 ColorMap arrays. Each selected map word is divided by 65535 once into RGBFLOAT32, without reducing the index or extracting the map's high byte. These expanded RGB coordinates require an RGB ICC. Absent, invalid, incompatible or failed CMS leaves the complete normalized RGBFLOAT32/GAMMA source; successful conversion publishes canonical linear float before the requested target or explicit final byte preference. Neither fallback nor palette expansion claims that an unknown device profile has sRGB primaries.

Integer alpha reuses the [same publication and composition rules](#original-integer-alpha-and-composition) across layouts. Original integer color numerators are exactly representable in F32 while later planes are decoded; the final integer/color-alpha ratio is rounded only after all planes complete. Source storage is 12 color bytes per pixel plus one or two original alpha bytes when present and one scanline or complete tile buffer. Existing CMS scratch and native codec allocations are additional. This representation needs no arbitrary-precision runtime library.

After this source reader accepts a layout, invalid row/tile strides, zero or short buffer sizes, allocation failure, and a failed or short later read terminate the load without a partial callback or RGBA retry. A later load on the same component remains possible. Reading raw integer tiles also avoids RGBA convenience-reader failures on some otherwise valid uncompressed tiles. It does not add acceptance to the separate floating-point routes. Existing opaque16 canonical target publication is unchanged; byte/alpha and palette paths negotiate the target only after complete successful interpretation.

The [literal layout cases](../../tests/data/color-numeric/tiff-layout.json) and [generator](../../tools/generate_tiff_layout_fixtures.py) retain original sample, orientation, alpha and rational-to-binary32 expectations. Numerical source/metadata/publication tests use the actual adapter and selected CMS; a same-engine reference from independent original source values qualifies adapter connection, while shared CMS numerical tests own CMM arithmetic. A non-square multi-tile separate-alpha input, a 16-bit palette-index input and a reversed file FillOrder control cover addressing and packing boundaries.

## Original integer alpha and composition

RGB4 and Gray2 UINT8/UINT16/VOID source samples with one declared associated or unassociated alpha extra retain their original source samples under the integer strip/tile, contiguous/separate and orientation 1–8 gate. Unassociated components are divided by the integer maximum (255 or 65535). Associated components are divided by original alpha, with one binary32 rounding after the integer ratio; alpha zero yields zero without division. MINISWHITE first reverses storage polarity, `(maximum-c)`, then reverses association. This is the adapter's libvips-compatible Gray convention, not a claim that every TIFF writer uses the same association order. RGB and Gray convenience decoders do not have interchangeable association behavior.

Ratios above one survive the adapter boundary. The selected CMS engine still applies its existing profile/device-domain rules: preserving a source ratio does not promise that every backend TRC extrapolates it. Matching RGB/Gray ICC conversion publishes a complete finite canonical linear RGB result. Original alpha remains separate throughout CMS; failure restores the full straight-source color buffer without changing alpha or input ICC bytes.

The loader composites fractional alpha over an available background in linear light. The background uses its own selected gamma/linear encoding and never passes through the foreground's ICC profile. With `clear`, `keep` or effective `auto`, exact-zero alpha remains a mask even when a background is present; partial alpha can still be composed. `composite` fills zero alpha when a background exists and otherwise retains the mask. Without a background, nonzero alpha retains straight foreground color because SIXEL cannot carry fractional alpha. Orientation moves color and mask together. Alpha equal to its original maximum (255 or 65535) bypasses blending entirely. Only exact zero is masked: nonzero UINT16 alpha, including 1/65535, is never first quantized to a byte.

Successful CMS and composition precede `cms_target` and explicit final byte preference. With absent, invalid, mismatching, disabled or failed CMS, 8-bit all-255 input publishes exact RGB888/GAMMA under either association. Unassociated 8-bit input without composition also remains byte. UINT16 input always retains RGBFLOAT32/GAMMA, including all-65535 alpha; this agrees with the existing no-alpha16 representation. Associated 8-bit fractional input or actual composition also publishes RGBFLOAT32/GAMMA, preserving source fractions; target negotiation does not turn this unmanaged fallback into calibrated color. For its background calculation the unmanaged route uses the existing assumed sRGB transfer convention, without claiming known device primaries.

Mandatory scanline/color/alpha allocation or read failure terminates this accepted route without a callback or RGBA retry. Storage is 12 color bytes plus one or two original alpha bytes per pixel and a scanline, plus the existing CMS scratch. The UINT16 path reads native-endian scanline words. The alpha allocation becomes the binary mask only after composition, or is released; forward compaction consumes each UINT16 alpha before writing its one-byte mask, preserving all unread alpha words. Byte fallback retains the 12-byte color allocation capacity until frame release. Original-ratio conversion needs no arbitrary-precision runtime dependency; the [literal fixture generator and oracle](../../tools/generate_tiff_alpha_fixtures.py) use rational/Decimal reference calculations offline.

These guarantees cover only the stated 8-bit and 16-bit integer layouts. The six established RGB/Gray IEEEFP32-alpha witnesses remain rejected without a callback; this route does not add float-alpha acceptance. Other sample depths, photometrics, layouts and the legacy RGBA ICC helper retain their separately documented boundaries. Preserving numeric values can affect resized palette output, especially when an early byte conversion would clip extended values, but it does not establish universal perceptual improvement.

## Original Lab and CMYK coordinates

The integer layout reader accepts CIELAB8/16, ICCLAB8, ITULAB8 and four-ink CMYK8/16 in contiguous or separate strips and two-dimensional tiles, with orientation 1–8. It reads native-endian decoded words before any convenience RGB rendering. Separate planes are read in codec order; orientations 5–8 transpose the output dimensions and color/alpha coordinates together. Supported extra samples consist of exactly one declared associated or unassociated alpha channel, after the three Lab or four ink components. Other extra-sample declarations, non-CMYK InkSet values and ink counts other than four do not enter this source contract. Compression availability remains the linked libtiff codec's responsibility.

CIELAB8 lightness is `L_byte/255` in the common normalized Lab representation. Chroma bytes are signed two's-complement physical a/b values divided by 128; they are **not** the offset-binary ICCLAB8 representation. CIELAB16 retains the [signed-word contract](color-management/README.md#tiff-cielab16-signed-input-contract). ICCLAB8 and ITULAB8 retain their [distinct scales and optional ITU Decode ranges](color-management/README.md#tiff-icclab8-itulab8-and-separate-cielab16). A malformed present Decode array is rejected before reading pixels. Associated Lab is unassociated after decoding the signed/offset coordinates; source alpha remains independent of the color transform.

TIFF CMYK stores positive ink amounts, normalized by 255 or 65535 (by original alpha for associated samples); it does not use the Adobe JPEG complement convention. The shared facade receives packed CMYK_F32, and its own backend adapter handles native CMM units. Only a CMYK profile is applicable. An independent RGB float destination protects all four original components against a failed apply, including a failure after writing a prefix or a nonfinite reported-success result. Successful Lab/CMYK conversion produces finite extended canonical linear RGB. No adapter unit clamp or byte rendering intervenes between the source transform and composition/final target negotiation.

Unapplied or failed Lab ICC conversion retains the complete Lab source for format decoding. Eight-bit Lab uses the existing D50 PCS-to-linear-RGB fallback without gamut clipping. CIELAB16 keeps its established bounded D65 Lab-to-gamma fallback; this compatibility behavior is not a wide-gamut guarantee for unmanaged CIELAB16. The older opaque scanline routes retain their existing target policy; newly connected layouts negotiate the selected target after canonical linear publication. Native float Lab normalization and its layout limits are unchanged.

Unmanaged CMYK uses the existing uncalibrated multiplicative RGB approximation. Eligible byte input produces exactly `floor((255-C/M/Y)*(255-K)/255)`. With no ICC candidate and no precision-requiring association/composition, it allocates byte source storage directly and contracts four source channels to RGB bytes. An invalid/incompatible/failed ICC can also recover those exact byte values after inspecting normalized input. UINT16 and fractional associated input remain float. Neither this fallback nor its GAMMA tag claims a calibrated printer-to-sRGB conversion.

Alpha uses the [existing integer composition and mask policy](#original-integer-alpha-and-composition) after source color interpretation. Finite out-of-gamut linear values survive composition; only exact-zero source coverage becomes a binary mask. Source reads and mandatory allocations fail without frame publication or RGBA retry. Optional CMYK CMS destination allocation or transform failure uses the complete original-source fallback, and subsequent loads on the same component recover. Storage is three Lab or four CMYK floats per source pixel when color work is needed, plus original alpha and a row/tile buffer; CMYK transformation adds a private three-float destination. The unprofiled eligible byte route uses four source bytes per pixel, not a float image.

The [literal fixture generator](../../tools/generate_tiff_device_tests.py) writes TIFF samples without a TIFF encoder and derives expected values using Decimal Lab/PCS and affine CMYK ICC equations. Tests observe exact normalized CMS inputs, complete output values/metadata, actual selected engine, masks, target conversion and same-component recovery. The numerical intervals reuse the existing [Lab engine contracts](color-management/README.md#tiff-lab-direct-linear-publication-and-recovery) and CMYK LUT PCS precision budget; composition/transfer checks account separately for final binary32 rounding. These are value/path contracts, distinct from the existing MS-SSIM regression tests.

## Decoded YCbCr RGB8 publication

For an already accepted unsigned or VOID YCbCr8 image with three samples and no extras, the adapter retains libtiff's component conversion into opaque RGBA8. It then normalizes those decoded RGB bytes into a private float RGB buffer and accepts only an RGB embedded profile. Complete successful CMS conversion publishes extended `LINEARRGBFLOAT32` / `LINEAR` before final `cms_target` / `prefer_8bit` conversion. This removes the second byte endpoint after CMS. It does not preserve the original YCbCr component precision, undo libtiff's first rounding or clipping, redefine YCbCr coefficients/range/subsampling, or expand libtiff's input acceptance.

CMS none, absent/invalid/incompatible profiles, optional float-buffer/profile failure and failed conversion retain every original decoded RGBA8 byte. This route does not retry the legacy byte CMM after a failure. The current opaque fallback becomes RGB888/GAMMA through the existing alpha strip, without negotiating a managed target. A GAMMA marker on an unmanaged device source does not establish calibrated sRGB primaries. Other YCbCr sample/extras combinations retain the legacy route.

The [selected-sample oracle](../../tests/data/color-numeric/tiff-ycbcr.json) independently fixes the default-coefficient decoded RGB8 values for the tiny existing witness, rational binary32 inputs and stored RGB ICC arithmetic. Tests separately observe literal original strips, the actual libtiff raster, the actual CMM input, complete public frames and same-component recovery. Native CMM controls qualify adapter equivalence; builtin has an independent 64-u32 triplet-relative arithmetic bound. Existing shared-CMS fault tests own internal transactional and finite-result guarantees. One actual CLI test then observes exact current sRGB RGB101 output; these value assertions are separate from perceptual image-quality thresholds.

## Legacy RGBA ICC publication

Accepted TIFF inputs outside the direct readers may use libtiff's RGBA8 convenience decoder. Optional ICC conversion on this route commits color only after the entire byte conversion succeeds. A failed apply, including one that wrote a prefix, retains every decoded source RGBA byte and performs no adapter retry. Optional CMS scratch or transform-creation failure follows the same whole-source fallback; mandatory decode allocation/read failures retain their separate error behavior.

Both build variants enforce the same profile-space gate. MINISBLACK/MINISWHITE require a Gray profile. RGB, palette-expanded RGB, decoded YCbCr RGB, and the existing unknown-photometric fallback require an RGB profile. An incompatible profile performs no apply and retains the complete decoded frame. This decoded-RGB policy does not implement an original-YCbCr ICC connection.

The helper always preserves original decoded alpha, including when a successful CMM writes different alpha into temporary output. This guarantee ends at the helper exit. Eligible declared integer alpha now uses the original-source reader and shared mask/composition policy; it no longer enters this legacy public path. Other accepted legacy alpha layouts still have separate limitations. No original high-depth detail lost by the RGBA decoder is recovered. The helper retains its byte endpoint; eligible opaque YCbCr8 now bypasses it through the decoded-RGB float route above.

In a build with Little CMS available, the shared legacy helper also serves the selected builtin and ColorSync engines. Its RGB-like branch uses an initialized RGBA scratch of four bytes per pixel and copies only successful RGB results back; Gray retains its existing one-plus-three-byte scratch. The helper used when Little CMS is unavailable retains its temporary three-byte RGB buffer and opens/closes a profile for the compatibility guard before the existing converter opens it again. Matching profiles therefore incur one additional parse, without overlapping guard and conversion profile lifetimes. These costs preserve transactional output and add no arbitrary-precision arithmetic dependency.

The [literal sample tables](../../tests/data/color-numeric/tiff-legacy.json) cover RGB8 separate strips, low-bit Gray, palette, decoded YCbCr and accepted byte-alpha sources and four incompatible-profile counterparts. Helper tests independently check original strip samples and palette words, actual CMS input and complete helper RGBA. All represented families now call the actual RGBA decoder and CMS helper directly for helper fault coverage. The layout tests own integer original-source-to-public-frame contracts, and decoded-YCbCr tests own that new public path. The obsolete YCbCr public byte-format and no-target assertions are replaced by complete float/fallback/target assertions; original helper alpha and failure assertions remain. Successful direct byte-CMM references qualify adapter connection and publication; they are not independent proofs of CMM arithmetic. Real-prefix rejection, optional allocation/factory failure, same-component recovery, and deliberately corrupted scratch alpha distinguish these contracts from ordinary successful decoding. Final quantization may hide a helper error; exact byte and apply observations are required in addition to image comparisons.

## Implementation and verification references

[`loader-libtiff.c`](../../src/loader-libtiff.c) owns memory-backed TIFF access, direct-path eligibility, the RGBA fallback, ICC processing, and frame handoff. The [libtiff test category](../../tests/loader/libtiff/) contains RGB/indexed/gray/alpha and compression fixtures, high-depth and Lab cases, CMS comparisons, and malformed-input checks. Perceptual tests are quality evidence, not proof that a particular precision path or metadata transform ran. Exact frame/metadata checks and diagnostics are needed for that distinction.

For the common downstream representation and resize promotion rules, see [pixel-format precision](../concepts/pixelformat-precision/README.md).

The owning adapter is [`src/loader-libtiff.c`](../../src/loader-libtiff.c): `tiff_try_load_integer_alpha()` selects declared integer alpha and `tiff_try_load_high_precision()` selects the other native scanline paths, `load_tiff()` selects RGBA8 fallback, and the two byte ICC helpers enforce their photometric gates. The direct-linear conversion and publication helper is in [`src/cms.c`](../../src/cms.c).

The [TIFF test directory](../../tests/loader/libtiff/) contains numerical, metadata, recovery and quality tests. Their documented contracts and reciprocal test links are maintained in [Loader Color Management: test coverage](color-management/README.md#test-coverage). Independent sample-value tests protect arithmetic and source retention; image-similarity tests cover their stated perceptual floor. Neither the directory's existence nor a CMS engine name proves coverage for an unimplemented or unverified row above.

### CLI numeric and structural tests

The selected original RGB16 ICC input passes through the exclusive libtiff loader and actual builtin CMS, orientation 6 maps 3x2 to 2x3, and nearest resampling enlarges it to 8x12. Scalar float processing, Heckbert, gamma working/output coordinates and no dither expose the existing sRGB RGB101 wire boundary. The [derived expectations](../../tests/data/color-numeric/cli-color-wire.json) use original integers, independent F32 rounding and the stored-ICC mathematical oracle. The wire reader applies palette changes at paint time and checks every final pixel, full coverage, dimensions and the opaque default P2. This is distinct from source/frame precision and MS-SSIM observations and does not qualify Display-P3 device output or all layouts and resamplers.
