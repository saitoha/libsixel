# PNG color metadata and ColorSync compatibility

This document owns PNG source-color interpretation across CMS-aware loaders, including builtin and libpng. [Loader color management](color-management/README.md) owns CMS engine selection, targets, supported profiles, and the other formats' test entry points. Container metadata selection precedes profile evaluation; changing the CMS engine does not select a different PNG precedence policy.

### Fixture values and provenance

All specimens are 64 × 16, eight-bit, noninterlaced PNGs, with color types 0 (grayscale), 3 (indexed), and 2 (RGB). Within each model the IHDR, palette, and inflated raster bytes stay constant. The embedded profiles are `linear-gray` or `linear-srgb`; `sRGB` has rendering intent 0; `gAMA` is 25000 (0.25). The cHRM white point is (0.34570, 0.35850), with primaries (0.70800, 0.29200), (0.17000, 0.79700), and (0.13100, 0.04600). These conflicting declarations make priority observable; they are not interchangeable encodings of ordinary sRGB.

All matrix references are unquantized sRGB RGB16 PPM images from [independent source equations](../../tools/generate_cms_quality_references.py), with [input/output hashes](../../tests/data/colormgmt/reference/analytic-quality.json). The published source-priority policy selects sRGB, the stored ICC matrix/TRC, or the gAMA/cHRM fallback. Original samples use `1 / gAMA`; RGB primaries and white points pass through XYZ and Bradford adaptation to D65, while neutral grayscale remains neutral. No loader, encoder or CMM supplies these expected pixels. Only the final display reference is clipped and rounded to UINT16; its serialization error is at most half a UINT16 code. The tests compare every decoded display-sRGB component before palette quantization, allowing 0.51 RGB byte levels for an 8-bit rounding boundary plus reference serialization and floating-point roundoff. This is a small-image color-value contract; it does not measure structural image quality or replace the float32 and extended-range contracts below. Offline `--check` permits one UINT16 code for arithmetic ties.

The matrix records the project's Apple-compatible source-interpretation policy. Its expected samples are calculated from the fixture declarations and that published policy, rather than captured from a particular Apple release. Live platform comparisons must record the OS, input profile, output colorspace, and raster precision.

## Source interpretation policy

PNG source interpretation is a shared loader policy, including the builtin decoder. It was aligned with Apple's ColorSync image-loading behavior; it is not a libpng-only rule or a consequence of selecting `cms_engine=colorsync`. The image decoder chooses the source declaration before the selected CMS engine evaluates a profile. On Apple systems the complete reference path includes ImageIO's metadata interpretation and CoreGraphics/ColorSync drawing into sRGB; calling ColorSync with an already selected ICC profile cannot reproduce that container-level choice by itself.

For the supported PNG declarations, the compatibility decision is ordered as follows:

| Order | Declarations and applicable interpretation | Source choice |
| --- | --- | --- |
| 0 | A supported, usable `cICP` declaration is present. | Use its source interpretation; all lower-priority color declarations, including the three-chunk exception below, are suppressed. |
| 1 | `iCCP`, `sRGB`, and `cHRM` coexist, with or without `gAMA`. | Use the sRGB interpretation; skip the embedded ICC transform and gAMA/cHRM conversion. |
| 2 | Otherwise an applicable `iCCP` profile is available to the selected engine. | Use that ICC transform. In particular, `iCCP+sRGB` without `cHRM` still takes this branch. |
| 3 | No ICC transform applies and `sRGB` is present. | Use sRGB; lower-level `gAMA` and `cHRM` do not replace its transfer function or primaries. |
| 4 | No higher-priority interpretation applies. | Use the supported `gAMA` transfer and `cHRM` chromaticity fallback for that format path, or its default sRGB assumption. |

This is source interpretation, not permission to skip structural parsing or alpha/background processing. Using sRGB may still require transfer decoding to linear storage, composition, or conversion to the requested `cms_target`. Conversely, `cms_engine=none` disables the libsixel metadata transform. Profile validation, source-channel compatibility, and fallback after rejected or unsupported metadata remain explicit loader boundaries; the order does not guarantee that every decoder accepts the same malformed profile or every isolated cHRM declaration.

The [PNG Third Edition specification](https://www.w3.org/TR/png-3/#11sRGB) recommends avoiding simultaneous `iCCP` and `sRGB`; this is not an unconditional prohibition. Its [general color-chunk priority table](https://www.w3.org/TR/png-3/#4Concepts.ColourSpaces) orders understood declarations as cICP, iCCP, sRGB, then cHRM/gAMA. The three-chunk exception above records libsixel's established Apple-compatible handling of overlapping declarations, which differs from that general table. Builtin/libpng understand the SDR cICP subset below; the three-chunk exception applies only when no usable supported cICP takes priority. Do not simplify it to either “ICC always wins” or “sRGB always overrides ICC”: each changes one of the first two rows.

The [March 2026 builtin alignment](https://github.com/saitoha/libsixel/commit/95ddf26b67f8f8619cac90faabb2cf459631a07c), [raw-chunk priority fix in libpng](https://github.com/saitoha/libsixel/commit/56e53f27a7f2b2ab719aa414af994b92e628c415), and [April no-lcms parity fix](https://github.com/saitoha/libsixel/commit/157db06319e557abab3bfb660dad958c5019ee6d) record deliberate cross-loader and cross-build compatibility work. Metadata getters can suppress or synthesize declarations, so their results alone must not silently change the original coexistence decision. Preserve the validated-profile boundary while retaining the relevant original chunk flags.

## cICP source definitions

PNG's [`cICP` chunk](https://www.w3.org/TR/png-3/#11cICP) carries four H.273 code points, not an ICC profile. The tuple is `(primaries, transfer, matrix, full range)`. The shared CMS owns the mapping from supported tuples to format-independent named RGB definitions; PNG code owns extraction, structural validation, and precedence. Neither loader implements a separate P3 matrix or transfer evaluator.

| Decimal tuple | Adopted definition | Work required |
| --- | --- | --- |
| `(1, 13, 0, 1)` | sRGB | Suppress lower-priority declarations. Retain eligible RGB/palette byte paths; decode the transfer when precision or composition requires it. |
| `(12, 13, 0, 1)` | Display P3, D65, sRGB transfer | Convert original samples through shared CMS to extended linear sRGB, before composition and the configured CMS target. |

A usable declaration has exactly four payload bytes, a correct CRC, and no duplicate cICP in the header before the first IDAT. It must precede PLTE and IDAT. Unsupported tuples, bad length/CRC, duplicates in that header, or cICP after PLTE do not select a source; lower-priority metadata retains its existing behavior. A chunk after IDAT is not adopted or moved before image data. This ancillary-metadata rule does not override a decoder's rejection of independently malformed image structure. The bounded scanner works with libpng versions that have no cICP getter.

PQ, HLG, other primaries/transfer combinations, and narrow-range samples remain unsupported. They are not silently treated as P3 or sRGB cICP; the next usable declaration, or the existing untagged default, supplies the interpretation. Such fallback is compatibility decoding, not an assertion that HDR colors are reproduced correctly. mDCV/cLLI and HDR-to-SDR tone mapping remain outside this support. `cms_engine=none` disables adoption of cICP along with the other source color metadata.

Builtin CMS retains the analytic named definition without an intermediate ICC quantization. For lcms2/ColorSync, the shared facade serializes that definition into an ICC profile and opens it with the selected engine. Failure to construct or apply an adopted P3 definition fails loading; it must not reinterpret its samples as unmanaged sRGB or retry another CMS. Alpha remains coverage and never passes through the color transform. File bKGD inherits the selected source definition, while an explicit background keeps its own declared space.

Static builtin PNG expands a P3 indexed source through its precision-preserving sample path because its retained palette is byte sRGB. Static libpng transforms the original palette to float before expansion. Both retain extended canonical coordinates despite a byte precision preference. Eligible sRGB cICP palettes remain bytes. libpng APNG applies the same source definition before its linear float canvas. Builtin APNG also applies the adopted cICP definition before a linear float RGB canvas with a separate continuous alpha plane. Its [animation precision contract](builtin/png/README.md#apng-pipeline) defines promotion, blending, disposal, and final callback delivery.

## Maintaining the tables

The [matrix generator](../../tools/generate_png_cms_matrix.py) reads the existing TAP commands, verifies the complete model/chunk/decoder product, validates PNG chunk presence and CRCs, checks that raster data stays constant, and groups actual reference bytes by the controls. It rejects input/reference remapping. It does not regenerate image references or run a decoder to invent expected output.

```sh
python3 tools/generate_png_cms_matrix.py --write
python3 tools/generate_png_cms_matrix.py --check
```

Review fixture or expectation changes before regenerating. The documentation static check rejects stale tables, missing cases, and remapped references. Keep the source-choice interpretation and fixture descriptions synchronized when changing metadata values or adding a new reference class.

### Original samples and extended linear RGB

These PNG probes normalize the original integer samples and compare all RGB channels, including negative and above-one linear components, with the independent matrix/TRC oracle. The CMS-disabled controls retain source interpretation. Profile acceptance alone does not satisfy the managed cases: each requires a successful float CMS apply and the selected loader. A preference hint of zero must still preserve the source gamut.

The earlier cHRM-only numerical fixture uses D65 and custom primaries `(.67,.32)`, `(.265,.69)`, and `(.15,.06)`. The [integer-grid boundary tests](../testing/png-chrm-boundaries.md) additionally cover Display-P3 red `(68000,32000)` on the PNG scale of 100000, adjacent inside/outside points, and rotated green/blue boundaries. The libpng adapter accepts zero XYZ Z when the source definition is nonsingular. It computes `100000 - x_integer - y_integer` before converting that numerator to double; a negative numerator, out-of-range coordinate, zero y, or singular primary matrix retains the applicable metadata fallback. Exactly collinear primaries are classified from the original integer coordinates before floating inversion. For signed grid area A, the normalized primary determinant is `100000*A/(yR*yG*yB)`: a nonzero A has determinant magnitude at least `1e-10`, while exact zero can leave a floating residue beyond the old `1e-12` inverse cutoff. The integer guard changes only that zero classification, accepts either nonzero sign, and leaves the subsequent floating solve and matrix application unchanged. Image RGB and file-background RGB use the same accepted matrix. These direct conversions have a fixed absolute per-component test budget of `2e-7`, separate from native ICC controls.

The floating `png_get_cHRM()` result remains the validation gate. Recovering its PNG integers by nearest rounding does not require the optional fixed-point getter API and does not revive raw cHRM bytes that libpng withheld. Supported libpng versions can withhold additional lower-level metadata with an invalid chunk; fallback follows the getters actually available. Original chunk presence is retained only for the established metadata-priority decision. The libpng adapter can apply cHRM without gAMA using the sRGB transfer function; the builtin decoder's paired gAMA/cHRM rule remains separately documented. The end-to-end boundary oracle uses D65: it does not establish non-D65 adaptation accuracy or remove the existing float32 step before matrix multiplication.

### cICP numeric contracts

These tests construct four-pixel PNGs in memory. Expected P3 coordinates use an independently derived D65 matrix `inverse(M_sRGB) * M_P3` and the specified sRGB transfer, not the production CMS or an image-quality score. Builtin float absolute tolerance is `2e-6`; native-engine and serialized-ICC fallback tolerance is `2e-4`, accounting for ICC fixed-point serialization and native transform approximation. Byte output, format/space tags, masks and identity palette retention are exact. Engine-specific tests also require the requested engine's successful apply trace; identity tests forbid redundant CMS application. The conflicting linear ICC used in precedence tests is setup data, never the numeric oracle.
