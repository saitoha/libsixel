# Builtin PNG source precision

The static, nonindexed PNG entrance retains original color samples before applying color management. It normalizes eight-bit values by 255 and sixteen-bit values by 65535, then sends RGB float samples to the selected CMS with a linear-sRGB destination. This path uses builtin, Little CMS, or ColorSync through the same profile facade. The presence of liblcms2 does not determine which engine evaluates an embedded ICC profile.

Successful conversion produces extended linear RGB: negative and above-one components remain available for composition and later processing. Untagged opaque eight-bit images retain the ordinary byte path. Sixteen-bit samples and alpha processing use float storage. Direct gAMA/cHRM normalization without liblcms2 also retains float storage; converting that loaded frame to the encoder working view consumes a color-conversion slot in the worker budget. Tests of scheduling without color conversion explicitly disable CMS. The byte-only keycolor optimization excludes sixteen-bit input even with CMS disabled, so a keycolor setting cannot silently reduce color or alpha to eight bits.

These contracts apply to `sixel_frompng_load_nonindexed()` in [frompng.c](../../../src/frompng.c), also used for an embedded PNG raster in BMP. Indexed palette conversion and the builtin APNG byte canvas retain their separate boundaries; this change does not turn the APNG canvas into linear float storage. See the [PNG loader overview](png.md).

## Source selection and fallback

The [shared metadata policy](../png-color-metadata.md#source-interpretation-policy) remains in force. In particular, the coexistence of iCCP, sRGB, and cHRM selects sRGB, while iCCP plus sRGB without cHRM still selects the applicable ICC profile. CMS disabled means these metadata transforms are disabled. Builtin requires usable gAMA before using isolated cHRM; cHRM alone retains its default sRGB interpretation. The libpng cHRM-only numeric expectation is therefore not the builtin expectation.

The existing build-dependent fallback is preserved. Without liblcms2, iCCP presence suppresses the gAMA fallback even when that profile is unavailable. With liblcms2, the alpha path may use gAMA after an unavailable ICC/chunk-profile conversion when sRGB is absent; the opaque path retains its original source samples in that case. This documents current compatibility behavior, not a reason to reinterpret an image halfway through composition. Existing late-chunk boundaries are also preserved; acceptance is not PNG conformance validation.

## Alpha, background, and target

Alpha is coverage from the original integer sample. It is never passed through a color TRC. Linear RGB composition occurs after source interpretation, and zero-alpha coverage remains a separate mask according to the selected transparency policy. Hidden RGB and the mask follow the same orientation transform.

File bKGD values use the same selected profile as the image. Both transformations must succeed before their results can be used together. If image conversion succeeds and background conversion fails, or the reverse, both return to their original integer samples before the same fallback decision. An explicit background instead uses its declared gamma/linear definition and is never passed to the source ICC profile. The original decoder buffers remain alive until conversion and composition finish.

The requested `cms_target` is applied after composition. A gamma float view retains extended values through the signed sRGB transfer. An explicit RGB888 view widens the canonical float sample to double, evaluates gamma in double, then clips and rounds at the byte boundary. It does not store an intermediate gamma float value. Both a preliminary linear byte view and a gamma float store can change the final byte. For example, the direct gAMA path maps the original sixteen-bit sample 33524 with gAMA=45455 to linear float 0.22884844243526459. Its gamma value rounds directly to byte 132; first storing gamma as float gives 0.5156862735748291 and byte 131. A caller that explicitly requests a gamma float view still receives that float value. The independent [PNG target fixtures](../../../tests/data/color-numeric/png-byte-target.json) record the original samples and each storage boundary.

## Independent numeric checks

The [source fixture generator](../../../tools/generate_color_fixtures.py) uses original integer RGB/alpha samples, stored ICC coefficients, and independent Decimal matrix/TRC calculations. The existing map8 ICC probe is also derived from its original RGBA8 samples, its stored 1024-point curv table, and its stored XYZ matrix; [its manifest](../../../tests/data/color-numeric/legacy-png-icc.json) records the unchanged image/profile hashes and computed expectations.

Builtin and Little CMS cases compare the requested output against independent source-derived values. ColorSync canonical samples are checked against the independent ICC expectation with its native linear tolerance. For ColorSync target cases, a first load must pass that canonical check with identical source, engine, background, alpha, and orientation settings. Independent signed-TRC and byte-rounding equations then project those validated native float samples to the requested target. This separately checks CMS linear accuracy and target conversion; it does not claim the final gamma value has the same absolute error bound as linear RGB.
